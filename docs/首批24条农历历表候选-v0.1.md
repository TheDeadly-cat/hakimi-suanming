# 首批 24 条农历历表候选 v0.1

> 状态：已形成可执行的权威历表对照与独立实现差分基线；24 条仍全部为 `candidate`，人工 `verified=0`，不能称为已签字金标。

## 1. 本轮结论

- 冻结了 **24 个唯一公农历日期对**，每个日期对同时执行“农历转公历”和“公历转农历”，共 **48 个方向断言**；两个方向不重复计算金标数量。
- 24 条都逐行绑定香港天文台公历/农历对照表及稳定定位，并记录下载时间与原始字节 SHA-256。
- 当前 `lunar-typescript@1.8.6` 适配器对 48 个方向断言全部匹配。
- Windows .NET Framework 4.8 的 `ChineseLunisolarCalendar` 作为不同来源谱系的独立实现，尝试反解 24 条公历日期：**23 条位于其支持范围并匹配、1 条超出其下界而不支持、0 条分歧**。仓库已提供只读脚本实际重跑并比对冻结记录。
- 这只证明“当前实现与冻结历表及另一实现一致”。.NET 结果目前是运行级差分，不会自动把案例升级为 `cross_checked`；内容寻址审核包与双人裁决预检虽已实现，但还没有两位真实复核人的逐案声明与经维护者纳入的新版本 fixture。因此当前 `cross_checked=0`、`verified=0`，农历 24 条发布额度仍未通过。

## 2. 来源层级

| 层级 | 当前来源 | 用途 | 能否单独升级金标 |
| --- | --- | --- | --- |
| 编算规则依据 | [GB/T 33661-2017《农历的编算和颁行》](https://std.samr.gov.cn/gb/search/gbDetailed?id=n4aXcLrEnvA%3D&mode=p) | 说明采用的农历编算规则背景 | 否；它不是本批逐日对照表 |
| 权威逐日对照 | [香港天文台公历/农历日期对照表](https://www.hko.gov.hk/en/gts/time/conversion.htm) | 冻结 1901、1903、1995、2012、2023、2025、2100 年日期行 | 否；仍需独立来源与人工复核 |
| 机器可读载体 | [DATA.GOV.HK 公历与农历对照表](https://data.gov.hk/en-data/dataset/hk-hko-rss-gregorian-lunar-calendar-conversion-table) | 对 2023 年文本表与 CSV 做同机构双载体核对 | 否；文本与 CSV 同属香港天文台谱系，不能冒充两个独立来源 |
| 独立实现差分 | [.NET ChineseLunisolarCalendar](https://learn.microsoft.com/en-us/dotnet/api/system.globalization.chineselunisolarcalendar) | 用另一实现反解 24 条公历日期，并以仓库脚本核对冻结运行结果 | 否；软件一致性不是权威人工裁决 |
| 被测实现 | `lunar-typescript@1.8.6` | Web/PWA 当前固定版本转换适配器 | 否；不能用同一库的往返自证 |

DATA.GOV.HK 的[使用条款](https://data.gov.hk/en/terms-and-conditions)允许在遵守署名等条件下浏览、下载、分发和重用数据。本项目只冻结用于测试的少量日期行及其来源摘要，不把整张历表复制成产品内容。

## 4. 可重复执行的工程证据

- 冻结数据：`packages/gold-standard/fixtures/calendar-conversion-candidates.v1.json`
- 严格 Schema、来源谱系约束、摘要与验证报告：`packages/gold-standard/src/lunar-conversion.ts`
- 24 对/48 方向、来源防伪和发布计数测试：`packages/gold-standard/src/lunar-conversion.test.ts`
- 审核包、双人裁决、重签篡改、原型污染、来源谱系、时间链与重放测试：`packages/gold-standard/src/lunar-review-workflow.test.ts`
- 公历转农历纯日期 API：`packages/time-core/src/index.ts` 中的 `resolveGregorianCalendarDate`
- 固定负例：`packages/time-core/src/index.test.ts` 中 5 类无效闰月、月份越界与转换后超界错误码测试
- .NET 重跑脚本：`packages/gold-standard/scripts/check-dotnet-calendar.ps1`；执行 `npm run audit:calendar:dotnet`，结果不一致时返回非零退出码
- 专用命令：`npm run test:gold`

验证报告必须把以下数字分别展示，不能合并：

```text
authorityReferencedCaseCount = 24
matchedDirectionAssertions = 48
independentImplementationMatchedCaseCount = 23
independentImplementationUnsupportedCaseCount = 1
crossCheckedCaseCount = 0
verifiedGoldCaseCount = 0
calendarQuotaPassed = false
projectReleaseGatePassed = false
```

当前 fixture 继续锁定 `candidate-only-v1`。内容寻址审核包与双人裁决 envelope 已实现，但协议通过不代表现实身份或人工签字；在真实裁决被维护者核验并纳入新的版本化 fixture 前，Schema 仍会拒绝任何 `verified` 状态。候选摘要绑定数据集版本、日期断言、逐条观察和来源材料快照；数据集与审核包摘要另行绑定完整来源、材料 SHA-256 和冻结差分运行。裁决还必须绑定复核人实际使用的审核包摘要，预检固定返回 `countsAsVerifiedGold=false`。

设置页入口为“设置与诊断 → 农历转换候选审核”。流程是：导出或载入当前 24 对审核包 → 预检该审核包 → 预检明确绑定其摘要的双人裁决。审核文件只按严格 JSON 读取；核心层按 UTF-8 字节限制大小，并在 Zod 前拒绝原型污染键、访问器、自定义原型、循环/稀疏结构和非 JSON 数据。SHA-256 仅证明内容未变化，不是数字签名。

## 5. GitHub 复用裁决

- 继续固定使用 MIT 许可的 `6tail/lunar-typescript` 作为被测候选实现，但只通过自有 `time-core` 适配层暴露允许字段。
- `lunar-javascript`、`lunar-java` 等同作者、同数据谱系实现不能作为它的独立证明。
- 不整站搬运八字项目；页面、品牌、数据契约、证据模型和研究工作流继续自建。
- `solarlunar-es` 虽为 MIT，但数据来源不够清晰，只能作为未来诊断票，不能进入权威计数。
- `ytliu0/ChineseCalendar` 为 GPL-3.0，不复制进当前非 GPL 产品。
- `sxtwl` 的仓库许可信息不够明确，不复制或随产品分发。
- `.NET ChineseLunisolarCalendar` 当前只用于冻结差分结果，不把其实现代码搬进 Web 包。

## 6. 已知限制与下一门槛

香港天文台说明，远期历表中若朔或节气非常接近午夜，未来采用更新天文资料时可能出现一天修订；其页面特别列出若干远期风险日期。因此每条候选都保留来源版本、访问时间和材料摘要，依赖或资料升级时必须并列复算，不能静默覆盖旧 Revision。

下一步按以下顺序推进：

1. 为每个案例逐条绑定第二独立来源谱系；运行级软件差分不自动改变案例证据状态；
2. 使用已实现的内容寻址审核包与双人裁决 envelope，让两位不同现实身份的复核人逐条检查香港天文台定位、独立差分和冻结摘要；
3. 对第 1 条 .NET `unsupported` 案例另补第二独立资料或明确退回补证，不能把“不支持”伪装为匹配；
4. 将接受、替换或拒绝决定经维护者核验后写入新的版本化 fixture 与裁决记录；
5. 只有满足两个独立来源谱系、双人声明和裁决记录的条目，才允许从 `candidate` 升为 `verified`；
6. 补普通月、闰月、无效闰月、未知时辰及非中国时区语义的浏览器 E2E。

在这些步骤完成前，产品仍只显示“显式转换 / 工程候选”，不显示“已验证万年历真值”。
