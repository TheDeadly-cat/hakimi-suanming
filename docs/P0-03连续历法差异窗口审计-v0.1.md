# P0-03 连续历法差异窗口审计 v0.1

> 状态：工程诊断候选，未裁决；`countsAsVerifiedGold=false`、`verifiedGoldDelta=0`。

## 1. 为什么从 7 个随机点扩成连续窗口

P0-03 的 20,000 例差分在 2089 与 2097 年发现 7 个 `.NET ChineseLunisolarCalendar` 和当前适配器相差一日的输入。逐点抽样不足以判断差异是单日错误、整月偏移，还是月首边界选择不同，因此本轮冻结两个包含前后控制日的闭区间：

- `2089-09-03` 至 `2089-10-04`，共 32 日；
- `2097-08-06` 至 `2097-09-06`，共 32 日。

每个窗口恰好包含 1 个分歧前控制日、30 个连续分歧日和 1 个分歧后控制日。两窗合计 64 日：60 日分歧、4 日控制；原报告的 7 个差异输入必须全部落在窗口中并绑定原报告摘要 `fbb761568b71178138c460b5ecdfc2b634690efe58d4349defff3d7117ab3130`。

这些日期是诊断观察，不是 64 个新的金标准槽位。项目级 `calendar_conversion` 配额仍固定为现有 24 条，连续窗口数据集即使结构合法也必须被 360 发布总账以 `NON_COUNTING_DATASET` 拒绝。

## 2. 四类材料及其角色

| 材料 | 角色 | 本轮用途 | 不能证明什么 |
|---|---|---|---|
| 香港天文台 2089/2097 公农历对照表 | 官方历表，同一 HKO 谱系 | 提供逐日农历日期；与当前适配器一致 | HKO 明确这两个远期朔日可能有一日差异，不能把表值描述成无不确定性的最终真值 |
| USNO Moon Phases API v4.0.1 | 独立政府天文事件计算 | 给出朔的分钟级 UT 时刻，直接检查是否跨越固定 UTC+8 午夜 | 它不是中国农历完整历表，不能单独决定月序、闰月或完整公农历映射 |
| Unicode ICU 78.3 Chinese Calendar | 独立软件实现 | 以 `Asia/Shanghai` 当地中午重放逐日日期，与 HKO/当前适配器做软件交叉检查 | 软件一致不等于权威裁决，也不构成人工签字 |
| .NET Framework 4.8 `ChineseLunisolarCalendar` | 独立软件实现 | 保留最初触发差异的完整月段观察 | 分歧实现自身不能作为支持自己结论的正向权威材料 |

当前适配器仍为 `lunar-typescript@1.8.6`。HKO 文本表和 DATA.GOV.HK 数据属于同一来源谱系，只能算一条权威谱系，不能重复计数。

## 3. 两个朔日的关键证据

香港天文台在公农历转换表首页的备注中明确指出，远期月相与节气计算可能有数分钟不确定性；当朔或节气接近午夜时，对应日期可能相差一日。其列出的具体朔日包括 `2089-09-04` 与 `2097-08-07`。

USNO API 的分钟级输出为：

| 事件 | USNO UT | 固定 UTC+8 换算 | 对窗口的含义 |
|---|---|---|---|
| 2089 年 9 月朔 | `2089-09-04 15:59 UT` | `2089-09-04 23:59` | 分钟值倾向 HKO / ICU / 当前适配器的 9 月 4 日月首，但距午夜仅约 1 分钟 |
| 2097 年 8 月朔 | `2097-08-07 16:01 UT` | `2097-08-08 00:01` | 分钟值倾向 .NET 的 8 月 8 日月首，但同样距午夜仅约 1 分钟 |

这两行说明两组差异不能用“某个软件总是对、另一个总是错”归因；它们更符合远期朔时刻在固定 UTC+8 午夜附近的天文计算不确定性。USNO API 只给到分钟，本轮不得据此虚构秒级精度。

## 6. 双审与第三方裁决协议

本轮不能复用“一个文件内有两个复核字段”的简化结构。完整流程必须生成四类独立、内容寻址的工件：

1. 候选审核包：绑定 64 日窗口、所有来源快照、原 P0-03 报告和逐日摘要；
2. 独立审核 A：控制日必须给出 `confirm_control`；分歧日可给出 `support_hko_current_icu` 或 `unresolved`，并绑定审核人身份记录摘要。当前 v1 虽保留 `support_dotnet` 格式值，但在没有匹配正向权威历表时会被预检拒绝，不能只凭软件差分形成已解决结论；
3. 独立审核 B：与 A 使用不同 reviewer ID 和不同身份记录摘要，独立完成全部 64 日；
4. 第三方裁决：裁决人必须不同于 A/B，绑定两份审核摘要并逐日给出生效结论。A/B 不一致时可选择至少一份有效审核明确支持的结论；若两份都未支持，则不能凭空改成已解决。

禁止“全部接受”快捷字段；64 日每一天都必须有明确判断。分歧软件输出不得冒充权威材料，来源工件和定位信息缺失、两位审核人不独立、裁决人重合、任意日期未决或重放旧审核包，都必须失败关闭。

由于 HKO 对这两个朔日主动声明一日不确定，而 USNO 分钟级结果分别倾向不同边，当前合规结论固定为：可以形成 `candidate` 或 `engineering_diagnostic_unresolved` 诊断资产，但不能冒充项目总账中的正式 `cross_checked`，也不能进入 `verified`。即便未来四个文件全部通过结构预检，仍保持 `countsAsVerifiedGold=false`、`verifiedGoldDelta=0`，直到取得足以处理远期朔时刻不确定性的新增权威材料、现实身份复核和维护者版本化整合。

在线重放命令还会从两份 HKO UTF-8 文本表解析月名/逐日名并核对 64 行 HKO 观察，重建 USNO 两事件规范化 envelope，复核父 P0-03 计划/报告摘要及 7 个触发绑定；不是只看四份下载文件的 SHA-256。离线命令 `npm run test:audit:p0-03:calendar-windows` 则覆盖窗口缩短、重签元数据、改写来源 URL 与 HKO 月首解析负例。

网页入口为 `/settings/calendar-divergence-audit`。页面只有在复算冻结 payload 摘要成功后才显示逐日数据，并提供导出/载入候选包、预检审核 A、预检审核 B、预检第三方裁决五个本地入口；按钮按前置工件失败关闭。即使 64 日结构上全部解决，当前 API 仍固定 `identityVerified=false` 与 `eligibleForCuratedIntegration=false`，不会自动写入 fixture 或总账。
