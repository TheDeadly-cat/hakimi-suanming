## 3. 初版 P1：冻结品牌曾经失真

最初生成过一份 12,328-byte child。它没有被接纳为 frozen identity：library 在导入后仍动态读取 `Object.hasOwn`，判别性毒化可让 `deepFreeze` 跳过嵌套 authority，同时 full-load 的 WeakSet brand 仍返回真。初版实测结果为：

```json
{"brandBefore":true,"nestedFrozen":false,"mutatedAuthority":true,"brandAfter":true}
```

这证明“品牌为真”当时没有真实蕴含嵌套不可变，属于 P1，而不是可忽略的测试实现差异。修复后：

- 捕获 `Object.hasOwn` 并通过捕获的 `Reflect.apply` 使用；
- `mapArray` 改为索引循环与捕获的 `Array.prototype.push`，不再触发 `Array[Symbol.species]`；
- 直接捕获并调用 `RegExp.prototype.exec`，不通过会再次动态解析 `.exec` 的 `RegExp.prototype.test`；
- `find`、`some`、`Object.entries`、`String.includes`、Hash `update/digest` 等 child closure 使用捕获的 primordial；
- 定向 post-import poisoning 下同时完成 parent full-load、child 两种 hash 模式 full-load、深冻结、mutation rejection 与 truthful brand 断言。

同一判别性 `Object.hasOwn` PoC 的最终结果为：

```json
{"targetedCalls":0,"brandBefore":true,"nestedFrozen":true,"mutationRejected":true,"mutatedAuthority":false,"brandAfter":true}
```

`targetedCalls=0` 表示 child 使用的是模块导入时捕获的原始函数，没有再次解析被替换的全局属性。

## 4. 后续 P1：CLI wrapper 绕过与最终主入口门

冻结修复后的第一次独立终审又发现，writer／verifier 虽拒绝可见 preload、loader、`NODE_OPTIONS`、`NODE_PATH`、错误 cwd 与额外参数，却没有证明自己是 Node 主入口。wrapper 动态导入 verifier 时曾可得到 `offlineFollowupArtifactMechanicallyVerified=true`；动态导入 writer 可走到 `EEXIST`，说明业务模块和写入路径已经被触达。

第一轮补丁只比较 resolved `process.argv[1]` 与脚本路径，仍不足：wrapper 可先把可写的 `argv[1]` 伪造成目标 CLI 的真实路径，再动态导入。该中间态同样没有被当作最终通过。

最终入口合同为：

1. 首先要求 Node 24 的 `import.meta.main === true`；
2. 再把 resolved `process.argv[1]` 与 `fileURLToPath(import.meta.url)` 作附加绑定；
3. 两个门都在 visible preload／loader 检查和业务模块动态导入之前；
4. 回归 wrapper 显式把 `argv[1]` 设置为真实 filesystem target path，同时用对应 file URL 执行 import；两入口仍由 `import.meta.main` 拒绝，business-import trap 未触发，writer 未写入，child 前后字节一致。

该门只证明当前 Node 进程把本文件标为主模块并且当前可见入口路径相符；它不证明外部 launcher／process 完整性，也不排除进入主模块前环境已被篡改、preload 已执行后擦除痕迹。因此本账仍不声称 launcher attestation、network attestation、mutation epoch、跨文件原子、interval integrity 或 ABA exclusion。
