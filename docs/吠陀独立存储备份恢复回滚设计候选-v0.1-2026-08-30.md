# 吠陀独立存储、备份、恢复与回滚设计候选 v0.1

日期：2026-08-30

## 结论

本轮新增一份吠陀独立存储、备份、恢复、mutation epoch、容量与回滚的 requirements-only 设计候选。它把 ADR-0001 和既有运行时提案中列出的六个接口逐项写成可复核的输入、输出、证据要求、fail-closed 条件、不变量与非主张，因此只能声明：

- `designCoverage=6/6`；
- `designMaterialCandidateComplete=true`；
- 六个接口的设计材料已经出现。

这不是存储实现、数据库或 schema，不是备份、恢复、回滚执行，也没有产生任何 receipt。历史父产品化要求账没有被本工件改写或 supersede；父账中的第 5 项仍为 `required_absent`，重新评审材料仍为 `3/7`，`formalRereviewRequirementSatisfied=false`，重新评审没有触发。

## 传递 current 材料闭包

除 4 个直接上游外，候选还逐字固定旧 verifier 实际读取或显式作为材料绑定的 16 个去重传递端点：六合同 draft／requirements、runtime dependency license evidence、source-rights requirements、expert plan、两份外部研究审计、input structural evidence、high-risk policy，以及 input structural evidence 明确绑定的三份 helper 源文件。机械账因此是 `direct=4`、`transitive=16`、`total=20`。

这 20 个端点都由本候选自己的 held-fd reader、严格路径检查和本地 SHA-256 独立复核；旧 verifier 的 Hash／TextDecoder 污染不能再把传递 child 的磁盘漂移伪装成 current。三份 helper 只证明检查时的磁盘文件身份，不证明 Node 实际加载的是同一字节。其余被 import 的 verifier 模块、Node 内建原语、`@babel/parser` 已加载字节和启动链也不在材料 pin 清单内，继续由 `loadedModuleByteIdentityVerified=false`、`nodeLoaderIntegrityVerified=false`、`runtimeLauncherIdentityVerified=false`、`runtimeIntrinsicIntegrityVerified=false`、`postImportPollutionExcluded=false` 分账。

20 次端点观察仍是顺序快照，不是一个原子集合；`totalContextEndpointSnapshots=20` 不改变 `crossFileAtomicSnapshot=false`、`intervalMutationExcluded=false`、`abaExcluded=false` 或 `mutationEpochAvailable=false`。

## 六个接口只完成设计材料覆盖

候选覆盖以下六个既定接口：

1. `separate_vedic_storage_namespace_interface`：定义独立命名空间、产品身份与拒绝跨体系写入所需的材料；
2. `storage_capacity_budget_interface`：定义容量 ceiling、测量、批准和超限阻断所需的材料；
3. `mutation_epoch_receipt_interface`：定义 epoch 身份、边界、参与者与 receipt 所需的材料；
4. `backup_interface`：定义独立备份输入、输出、完整性与失败关闭所需的材料；
5. `recovery_interface`：定义恢复选择、验证、隔离和失败关闭所需的材料；
6. `rollback_interface`：定义回滚目标、执行、验证与证据保存所需的材料。

`6/6` 表示上述六份 requirements-only 设计材料均存在，不表示接口已实现或被产品调用。当前仍必须保持：

- `runtimeImplementationInstances=0`；
- storage implementation、独立 namespace、database、schema、runtime 与 backend 均未出现或未选择；
- backup executions、recovery executions、rollback executions 均为 `0`；
- mutation epoch、backup、recovery、rollback receipt 均为 `0`；
- 没有真实用户数据、生产数据迁移或正式仓储边界证据。

因此这份候选不能回写父账的 `required_absent`，不能把 `3/7` 改为 `4/7`，也不能产生中央 registry、准入或发布效果。

## Mutation epoch 与原子性边界

本候选只定义未来 mutation epoch receipt 应包含什么，当前没有创造 epoch 或 receipt：

- `mutationEpochAvailable=false`；
- `mutationEpochReceipt=null`；
- `crossFileAtomicSnapshot=false`；
- `parentRuntimeAndDesignAtomicSnapshot=false`；
- `intervalMutationExcluded=false`；
- `abaExcluded=false`。

固定路径 endpoint 的机械观察不能外推为跨文件原子快照，不能证明读取区间 mutation 已排除，也不能证明 ABA 已排除。

## 分账与仍为红的授权

这份候选只增加工程设计材料证据。它不增加浏览器或真实运行时证据，也不建立：

- 来源正文、exact quote、locator、binding 或 source authority；
- 内容真值、传统权威、科学有效性或预测准确率；
- 现实专家身份、资质、彼此独立性、原始意见或 expert authority；
- 作品层、版本层、载体层许可依据、再分发权利或法律结论；
- 存储、备份、恢复、回滚、PWA、Service Worker、Chrome／Edge、公开主机或 Release Evidence；
- 发布就绪、部署成功、回滚确认或公开发布授权。

因此本候选能够直接投影的 `contentTruthEstablished=false`、`expertTruthEstablished=false`、`rightsLegalConclusionEstablished=false`、`releaseReady=false`、`publicDeploymentAuthorized=false`、`expertClaimsAuthorized=false` 必须继续分账并保持为红；来源权威同样没有由本候选建立。机械 verifier 通过也只能证明当前候选结构与固定上游身份一致，不能替代内容、专家、权利、运行时或发布结论。
