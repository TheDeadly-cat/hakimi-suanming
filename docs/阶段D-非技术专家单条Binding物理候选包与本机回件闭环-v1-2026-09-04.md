# 阶段 D：非技术专家单条 Binding 物理候选包与本机回件闭环 v1

日期：2026-09-04

## 结论

本轮把既有的“单条 Binding、A/B 两位专家、无代码填写”合成演练推进到了一条可由来源协调进程实际验证和启动的**本机物理候选链**：候选包可在仓库外生成；来源侧会核对 P、PM、S 三层外部 pin 和所选席位实体字节；专家只看到普通中文表单；提交经过同源、单次、完整回件预检；协调侧可把私有内存中的完整回件与 SHA-256 sidecar 写入新的仓库外目录。

这仍不是现实专家正式 intake。当前必须继续标记：

- `physicalExpertSurfaceReady=false`；
- 现实专家 `0/2`；
- 正式冻结 Binding `0/12`；
- `expertClaimsAuthorized=false`；
- `publicDeploymentAuthorized=false`；
- 默认发布治理保持 `legacy-v13 / targetSchema 13 / migrationId null`。

本轮没有使用真实姓名、出生资料、联系方式、资质文件、真实专家意见或受保护来源正文。

## 这条链现在能做什么

### 1. 仓库外生成互相隔离的 A/B 候选包

`single-binding-integrated-package-builder.mjs` 生成一个 pair root，并固定：

- pair precommit（P）；
- A、B 两个不同的 seat manifest（SA、SB）；
- pair manifest（PM）；
- A、B 不同的 seat session nonce；
- coordinator 包；
- 精确文件 allowlist 与实体字节摘要。

依赖关系保持 P → SA/SB → PM，不建立哈希环。包内 `START` 命令只会拒绝直接启动；包内不附带可自行运行的 server，避免专家误从未经来源验证的目录启动代码。

### 2. 来源协调进程只服务经过验证的所选席位

`single-binding-integrated-physical-package.mjs` 会从包外接收预期 P、PM、S、cycle、pair、seat 与 nonce，随后：

- 拒绝错误 pin、错误席位、跨 cycle/pair、额外文件、symlink、junction、hardlink 和路径重定向；
- 用 held handle 重验实体身份与字节；
- 不导入或执行候选包自己的 JavaScript；
- 只把经过验证的所选席位字节复制到私有内存；
- 从来源代码启动随机 loopback、内存型 server；
- 只开放精确静态 allowlist 和一个严格回件端点。

对面专家席位不会被当前专家 server 暴露。

### 3. 专家不需要懂 AI、JSON、SHA-256 或代码

physical mode 隐藏了协调员字段、hash、JSON、session、Binding 技术名、下载控件和进度账。专家只需要完成普通中文步骤：

1. 阅读固定材料和一个问题；
2. 选择同意、有条件同意、不同意或无法判断；
3. 写明理由；
4. 写明适用条件；
5. 写出反例或还需要的证据；
6. 选择高风险表达应保留、改写还是暂缓；
7. 给出修改建议；
8. 如实披露是否使用聊天机器人、排盘软件或其他软件工具；
9. 阅读系统逐字回显；
10. 确认后提交。

专家可以自己输入，也可以口述给协调员逐字录入。口述模式要求声明“逐字录入、未摘要”；协调员不能把专家原话润色成另一种结论。

### 4. 回件捕获与 ACK 丢失重试

回件端点校验精确 Host、Origin、一次性 token、Content-Type、Content-Length、无 chunked transfer，并对完整回件先执行严格预检。第一次接收后：

- 同一份精确字节再次提交时返回幂等 receipt；
- 字节发生变化时拒绝；
- 浏览器即使在服务端已接收后丢失 ACK，重试也不会生成第二份不同意见。

浏览器测试已经模拟“第一次服务端接收成功，但客户端看不到响应”的情形，并确认重试收敛到同一 SHA-256 与长度。

### 5. 回件只能写入新的仓库外目录

写入器要求调用方再次提供完整回件 raw SHA-256 pin，并且：

- 输出 parent 和目标必须在仓库与候选 pair root 之外；
- parent 绑定真实路径与 `dev:ino` 身份；
- mkdir 前后、每个文件写入后、handle 关闭后和返回前重复检查 parent/output/source identity；
- 两个文件均使用 exclusive create，写完执行 file sync；
- 成功时目录只能包含完整回件与 `.sha256.txt` 两个文件；
- 只有所有写入、关闭和最终重验成功后，私有内存 capability 才被消费和清零；
- 同一 capability 的并发 writer 只能有一个获得 reservation；writer 进行中不能被 release。

写入失败且 handle cleanup 已确认时，原私有回件仍可重试；若 handle cleanup 不能确认，capability 保持 `cleanup_failed`，release 和第二次写入都拒绝，避免假称“引用已清除”。

## 仍然没有建立的物理安全性质

下列项目均明确保持 false 或未建立：

- 没有给真人专家使用的隔离浏览器 profile 启动器；
- 没有证明输出目录或文件 ACL 只允许指定协调员读取；
- 没有跨两个文件的原子提交；
- 没有证明目录项已执行持久化 flush；
- 失败时不自动删除部分输出；
- 部分输出可能包含敏感回件字节；
- handle cleanup 无法确认时不提供自动恢复；
- 没有真实专家身份、资质、独立性或同意记录；
- 没有真实私有证据库接入。

因此，当前候选链只适合合成数据和继续做工程硬化，不能直接发给现实专家处理真实材料。

## 真人专家应该怎样参加

### 专家负责专业判断，不负责工程证明

领域专家只需要回答：

- 这条规则在他熟悉的流派中是否成立；
- 成立需要哪些条件；
- 有哪些反例；
- 当前来源是否足以支持这条表达；
- 哪些说法对用户风险太高；
- 应怎样改写，或为什么应暂缓。

专家不需要判断 hash、Schema、server、代码实现或 AI 架构。工程协调员负责包身份、输入冻结、逐字保存、文件校验和浏览器启动；来源/权利审查人负责作品、版本、载体和许可。三种责任不能互相代替。

### 一次 15–25 分钟的单条 Binding 流程

1. 协调员先冻结同一份材料、问题和机器摘要。
2. 专家 A 在看不到 B 意见的情况下独立完成中文表单。
3. A 逐字核对并提交；协调员只保存回件和 sidecar，不评价对错。
4. 专家 B 用另一席位独立完成同一问题，同样不能先看 A。
5. 两份原始意见都封存后，协调员才生成逐字段并列比较。
6. 一致项记录为一致；分歧按流派、输入、底本、解释、工程错误、高风险表达或无法判断分类。
7. 不多数表决、不平均、不混成折中意见，也不让生成模型选择赢家。
8. 未解决分歧继续 `defer`；如需补材料，各自补充，原始意见不覆盖。

### 专家说“AI 和专家准确度差不多”应怎样处理

这可以作为待检验假设，不能成为授权结论。专家复核和准确度实验是两条不同的账：

- **Binding 复核**检验规则、条件、来源充分性、流派边界和风险表达；
- **准确度研究**需要另行冻结案例、可观察结果、盲法、评分规则、AI 版本、提示词、输入信息、专家作答条件和统计方法。

排盘事实、来源引用和明确规则应用可以按客观答案计分；主观人生叙述如果没有预先定义的可观察结果，只能研究一致性、可用性、置信度校准或用户盲评，不能把“觉得准”直接写成准确率。专家和 AI 都可能出错，也都不能自动获得权威。

如果未来做对比，最低应满足：

- 专家与固定 AI 得到相同信息和相同时间窗口；
- 案例与评分标准在看结果前冻结；
- 评分者看不到答案来自专家还是 AI；
- 不用同一位专家既出题、作答又给自己打分；
- 同时报告错误、无法判断、过度自信、来源错误和高风险表达；
- 不用一次小样本胜负授权产品对外宣称“更准”。

## 下一道可执行门

在联系真人专家处理真实材料前，优先补齐：

1. 来源协调端的隔离浏览器 profile 与明确的网络禁用/允许策略；
2. 私有输出目录 ACL、失败清理或恢复能力、两文件提交与目录持久化策略；
3. 不含代码术语的协调员 runbook 与专家一页说明；
4. 现实专家知情同意、隐私、身份/资质与独立性核验流程；
5. 用两名真实专家但仍只用合成材料完成 onboarding；
6. onboarding 无误后，才选择 1 条 Binding 做首个真实来源与专家闭环。
