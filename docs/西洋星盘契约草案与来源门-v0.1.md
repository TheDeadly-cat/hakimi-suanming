# 西洋星盘契约草案与来源门 v0.1

> 日期：2026-08-10  
> 状态：能力探针；已实现隔离 UTC 位置诊断与独立占星规则层竖切（黄道落位、整宫/等宫/波菲利宫位、相位枚举），未实现严格星历证据、保存、检索或备份  
> 发布边界：不进入现有八字数据库、full v1.2、路由、Service Worker 或普通构建依赖

## 1. 本轮产物

隔离包 `packages/western-astrology-contracts-draft` 固定了未来西洋星盘适配器必须提供的结构，并对可由同一工件内部重算的关系做失败关闭校验：

- 精确到分或秒的公历民用时间、IANA 时区、DST 分支和地理坐标；
- 每个天体的提供者目标 ID、`body_center` / `system_barycenter`、地心/地表观测原点；
- ICRF 基准、输出黄道、光行时/像差/太阳引力偏折、黄道体系、宫制和相位规则；
- UTC、TAI、TT、UT1、TDB、闰秒、EOP 与三种 Julian Day 的完整时间回执；
- 星历/框架/闰秒/EOP 工件摘要、请求与生效选项、返回 flags、零后备声明；
- 行星位置、宫头、角点、相位、逐字段来源和失败关闭回执。

包的 `exports` 固定为空，不含任何星历二进制、kernel 或 Swiss Ephemeris 代码。结构样例明确标记为 `synthetic_contract_fixture`，只声明 `fixture_structure` 覆盖，不是实际星盘、天文参考值或专家真值。样例中的摘要只是满足 SHA-256 字符串格式，并以 `format_only_contract_draft` 明示未由内容计算。

## 2. 当前范围与事实分层

现有冻结 IANA 时区工件支持 1900～2100，因此草案输入和 profile 先取这个交集；星历覆盖更宽不能绕过民用时间解析边界。

天文事实层记录时间尺度、参考系、观测原点、天体位置和速度；占星规则层单独记录热带/恒星黄道、岁差方案、宫制、相位角、orb 与入相/出相算法。JPL、NAIF、IERS 或 IAU 的天文资料不为占星解释背书。

特别是，DE440 的基础 planetary SPK 对部分外行星直接提供的是系统质心。没有额外卫星 SPK 或其它明确数据时，不能把 `system_barycenter` 改名成行星实体中心。每个天体都必须在 profile 和结果中保存实际 provider target。

## 4. 必须失败关闭

- 未知时辰、日期占位中午、缺坐标、DST gap/overlap 未决、超出任一工件覆盖区间：拒绝。
- topocentric profile 缺海拔：拒绝；经度固定东正西负、纬度为地理纬度。
- profile 要求 `body_center` 而实际数据只有 `system_barycenter`：`TARGET_CENTER_UNAVAILABLE`。
- profile 目标没有出现在内容摘要所绑定的 planetary/satellite 工件 target inventory：拒绝。
- 星历引擎缺文件后切换低精度算法、请求/生效 options 任一键值不同、产生任一 backend warning、返回 flags 与请求不一致或任何 `fallbackUsed=true`：拒绝。
- 所选宫制失败后自动替换 Porphyry 等其它宫制：拒绝并丢弃填充值。
- 恒星黄道缺少岁差方案/数值，热带黄道却携带岁差值：拒绝。
- 相位天体不存在、顺序不稳定、角度/orb 与 profile 不一致、超出容许度：拒绝。
- 相位夹角不能由两端黄经重算、有向 orb 符号不一致、入相/出相与瞬时相对黄经速度不一致：拒绝。
- 本地墙时、UTC offset 和 UTC 瞬时不一致，或 UTC/UT1/TT/TDB Julian Day 与声明的 DUT1、TAI−UTC、TDB−TT 不一致：拒绝。
- 闰秒/EOP 回执没有绑定 profile 中覆盖输入日期的精确工件，或实际加载工件集合相对 profile 有缺失、额外项、重复项或任一字段不同：拒绝。
- 许可证或数据使用权未审清：只能返回 `LICENSE_NOT_CLEARED` 失败回执，不形成成功工件。

## 6. 当前仍未解决的真实适配器阻断

- 当前只验证 `timeZone` 字符串形状；真实计算仍必须调用项目冻结的 tzdb resolver，验证 zone membership、DST gap/overlap 和内容寻址 snapshot ID，不能相信浏览器当前时区数据。
- `TAI−UTC`、DUT1、极移和 EOP 状态仍是回执声明；草案能验证它们与各 Julian Day 自洽，但不能证明数值确实来自所列闰秒/EOP 文件。真实适配器必须按内容摘要读取并给出样本/插值证据。
- `1900-01-01` 至 UTC 闰秒制度建立前的民用时间不能套用现代整数闰秒表；真实适配器若没有冻结的历史 UTC/TAI 漂移模型，必须把该日期段失败关闭，不能用当前 offset 倒推。
- profile target 现在必须命中星历工件声明的 target inventory，inventory 也必须绑定同一工件内容摘要；但草案没有读取真实 kernel，仍不能证明手写 inventory 是正确提取结果。真实适配器必须用确定性 kernel inventory 提取器生成并复核清单；外行星实体中心仍必须由额外 SPK 或等价工件证明。
- 成功 fixture 现在要求请求/生效 options 精确相同且 backend warnings 为空；但 `returnedFlags` 仍缺 provider 专用语义解析。当前已经固定 `solarGravitationalDeflection=false`，接 JPL/SPICE 前仍要验证 `J2000`/ICRF 标签、光行时和恒星像差 flags。
- 宫制仍没有真实后端返回码、极区失败样例或双实现差分；不能接受 Swiss 在错误返回后填入的 Porphyry 值。
- 权利字段仍是草案账本引用，不构成法律结论；Toolkit、kernel、EOP、代码和公开服务用途必须分别审查。
- 所有 digest 仍只做格式校验，未实现 canonical JSON 序列化与内容重算，因此不得把样例摘要当成完整性证据。

## 7. 下一道门

首个许可证可研究的本地原型已经落为完全隔离的 UTC 天文位置诊断；它只生成 `differential_diagnostic`，不生成严格星盘或成功回执。宫制与相位仍须独立版本化。任何真实引擎进入生产前，还要补数据工件下载/校验、离线复算、双实现差分、专家规则审核、存储/备份 Schema 和 Edge/Chrome 故障矩阵。

### 7.1 首个隔离 UTC 天文位置诊断

`packages/western-astronomy-engine-adapter-draft` 已锁定 [`astronomy-engine@2.1.19`](https://github.com/cosinekitty/astronomy/tree/v2.1.19)，仅用于隔离的 Node 天文位置探针和 Browser/Node 工程一致性页，不直接成为本契约的成功适配器：

- npm 版本固定为 `2.1.19`，annotated tag object 为 `03084ee684bdcc490273fe85f9df4f1c8fb66199`，peeled commit 为 `61dc07020aaa6885d2c7f688a4d82beaf6edb9ef`，npm SRI 为 `sha512-8yWKNf7UeNbH458h3sAJ6ZgAjE5jTXp/mNNRFoC20j2SHwZIjAQeEsBB2Q3uCFRaTCCJRv33K2XhkhZQMXoX6w==`。npm tarball 的八个文件中没有独立 `LICENSE`；本包从 peeled commit 另取 1,095 字节 MIT 原文并锁定 SHA-256，不把它误称为 tarball 内文件。
- 每个请求创建全新 Node Worker，清空继承的 `execArgv` 并施加超时/内存限制。Worker 在导入引擎前核对已安装 ESM 的 412,025 字节和 SHA-256、`package.json` 的 1,078 字节和 SHA-256，再固定 `DeltaT_EspenakMeeus` 并复验 7 个 Float64 哨兵。
- 请求只接受 `1900-01-01T00:01:00.000Z` 至 `2100-12-31T23:58:59.999Z` 范围内的规范毫秒 `Z` UTC，以及按固定顺序排列的十体或非空子集；offset、本地墙时、重复/乱序天体与额外字段都在 Worker 启动前失败关闭。
- 输出只包含地心 EQJ、Astronomy Engine 的 true-ecliptic-of-date，以及 UTC ±60 秒中心差分。Moon 明确记录为直接 `GeoMoon`、无显式 backdate；其余天体记录上游迭代回溯语义，不能把十体统一称为同一种光行时修正。
- 外层固定为 `diagnostic_only`、`productionEligible=false`、`expertTruthClaimed=false`、`chartFixtureAccepted=false`、`successReceiptIssued=false`，没有 `receipt`。它明确列出仍缺的 tzdb/DST、ICRF、目标中心工件、闰秒/EOP、provider flags、瞬时速度、黄道/宫制/相位与严格回执字段族。
- 五个离线工程回归种子覆盖 1900 下边界、J2000 十体、2024 日食附近、2025 春分经度换向与 2100 上边界；这些摘要只证明固定引擎/DeltaT/投影代码的确定性，不是 JPL Horizons 或占星专家真值。
- Browser/Node 构建先重跑五个 fresh Node Worker 生成完整 raw 参考，再在真实浏览器用五个 fresh Dedicated Worker 重放同请求；主线程从 Node raw 与 Browser raw 分别重新生成稳定投影并核对关系、字段与摘要，不能把自报的投影当成执行证据。隔离页面受 `connect-src 'none'` CSP 约束，不接入正式 Web 图或任何持久化分区。
- 原始 double 保持原样且不作为成功条件。独立的 `cross_runtime_quantized_projection_v1` 对时间天数与 AU 向量/距离取 12 位十进制，对 DeltaT 秒、黄道角度、角速度与距离速度取 9 位；投影只把这些数值声明为十进制网格半步，不把它们称为 IEEE-754 总误差上限或天文精度。2026-08-10 的 Edge `151.0.4129.59` 与 Chrome `151.0.7922.77` 各两轮均为稳定投影 5/5，且锁定相同五个摘要；raw canonical JSON 为 0/5 精确一致。这里没有宣称逐字段 Float64 位模式核对。两轮后 local/session storage、IndexedDB、Cache Storage、Service Worker、cookie、意外外网请求、console warning/error 与 pageerror 均为 0。

Swiss Ephemeris 继续保持许可阻断。Browser/Node 稳定投影子门已经形成，但它不是天文精度差分。[JPL Horizons API](https://ssd-api.jpl.nasa.gov/doc/horizons.html) 固定原始响应差分仍是后续门：首个候选已收窄为 2025 春分时刻的太阳、地心 `500@399`、`VECTORS`、`UT`、`FRAME/ICRF`、`AU-D`、位置表与 `LT`，当前环境却没有从官方端点取得可锁定字节，因此没有生成合成替代物。在官方 raw body、查询清单、检索时间、URL/响应摘要、目标中心、参考平面和容差语义全部落盘前，不新增正式路由、存储分区或备份模块。

2026-08-10 对 JPL Horizons 官方端点的再次尝试（curl、PowerShell 与 Python，直连与本地代理均走 HTTPS）都在 TLS 握手阶段被网络层阻断，未取得任何可锁定字节；因此没有创建替代或合成 fixture。该阻断不影响纯几何规则层，也不改变“只能输出不带真值裁决的差分报告”的边界。

### 7.2 独立占星规则层（纯几何竖切）

在官方星历字节取得前，`packages/western-astronomy-engine-adapter-draft/src/rule-layer/` 提供第一个不依赖星历真值的西洋功能竖切。它只接受调用方提供的黄道经度与瞬时速度，并固定版本化算法 ID：

- `western-zodiac-rules/0.1-draft`：热带/恒星黄道落位；恒星必须携带岁差值，热带不得伪造岁差值；
- `western-house-rules/0.1-draft`：整宫、等宫（ASC）、波菲利与 Placidus 四种宫制，统一从 RAMC、地理纬度与 true-of-date 黄赤交角导出 ASC/MC/IC/DSC；极区或 ASC 不在地平线时失败关闭，不使用后备宫制。Porphyry 的四象限三等分由测试锁定结构不变式；Placidus 忠实移植自 Unlicense 参考实现（Phaen/CircularNatalHoroscopeJS，依据 Munkasey《An Astrological House Formulary》第 18 页及已记录的三角修正），并以赤道手工案例与 672 组 RAMC/纬度对照零差异锁定，纬度 ≥60° 失败关闭；
- `western-aspect-rules/0.1-draft`：按稳定天体顺序枚举相位，复算夹角与有向 orb，并由瞬时相对黄经速度派生 exact/applying/separating/indeterminate。

每个天体会额外分配 `houseNumber`：按十二宫头在输出黄道上的升序跨度定位，跨 0° 的宫位正确回绕。输出固定为 `astrology_rules_engineering_artifact`，声明 `diagnostic_only`、`productionEligible=false`、`expertTruthClaimed=false`、`chartFixtureAccepted=false`、`successReceiptIssued=false`，没有 `western-calculation-receipt`。规则层不计算星历位置、RAMC、岁差方案或宫制外部参考值，也不具备保存、检索或备份；把它当作天文或占星真值仍是被禁止的。当前定向证据为草案 Vitest **13 个文件 / 88 项**、隔离边界门 **42/42**，草案 typecheck 与普通构建已过。

命令行示例：

```powershell
npm run demo:western:rules -- 2025-03-20T09:01:00.000Z
```
