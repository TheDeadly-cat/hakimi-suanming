## 1. 本轮结论

本轮只推进 C，不把 D、E 或历史发布验证混入同一通过线。八字 12 条 Binding 的 readiness builder 现在直接调用完整来源候选 verifier 和完整三层权利候选 verifier，并让 verifier 所解析的依据字节与 `basisArtifacts` 哈希复用同一批读取 Buffer。公开随包材料则在读取任何正文前先完成路径、作品层、现代版本层、载体层和精确库存预检；正文读取使用 held handle、有界 `maxBytes + 1` 读取、目录链端点复核和读取后全库存复扫。

这些变化只关闭工程准入绕过，不新增正文，不把候选转成正式记录，也不作许可或法律判断。

## 2. Readiness 来源／权利信任链

`scripts/bazi-binding-freeze-requirements-lib.mjs` 当前顺序为：

1. 以受限工作区路径读取固定 basis artifact 集合；拒绝最终文件 symlink、hardlink 和非普通文件。
2. 每个 basis 文件在 held handle 上最多读取 `maxBytes + 1`，超限立即失败；读取前后复核 path、handle、realpath、size、mtime、ctime 和文件身份。
3. 从同一批 Buffer 解析工程候选账、来源候选账、权利候选账和专家候选包。
4. 先运行完整 `verifyBaziSourceBindingCandidateLedger`，再运行绑定该来源账的完整 `verifyBaziSourceRightsCandidateLedger`。
5. 只有完整 verifier 通过后，才消费本地 gate summary 和 Binding 投影。
6. `basisArtifacts` 的 bytes／SHA-256 直接从上述同一批 Buffer 计算，不再在验证后按路径重读。

这解决的是“验证旧字节、哈希新字节”和无界 basis 读取问题。basis 文件之间仍不是原子事务；Schema 13 没有 mutation epoch，端点检查不能排除区间 mutation 或 ABA。

## 3. 随包材料预读门

`apps/web/bundled-knowledge-audit.ts` 当前在正文首次读取前完成：

- manifest held-handle、有界读取、严格 UTF-8、精确字段和 `documents/` 路径检查；
- `validateBundledKnowledgeRelease` 的作品层、现代版本层、载体层和双人复核机械准入；

- 目录及递归子目录拒绝 symlink／junction，文件拒绝 hardlink 和特殊端点。

每份正文读取时会逐级捕获普通目录链，以同一 held handle 读取最多 `MAX_KNOWLEDGE_DOCUMENT_BYTES + 1` 字节，随后复核目录链、文件 endpoint 和 realpath；实际正文哈希与规范化内容均来自这份 Buffer。全部正文完成后再次完整扫描库存，并与读取前库存及 manifest 三方精确比较。
