# 农历闰月输入与转换 v0.1

> 状态：P0-02 工程工作口径；功能已接入 Web 主流程，已建立 24 条权威历表候选与独立实现差分，但人工已验证金标仍为 0，尚未通过发布门。

## 1. 用户可见语义

- 输入历法可选公历或农历；切换历法会清空日期，避免同一串数字被静默换义。
- 农历日期按 `YYYY-MM-DD` 填写，闰月使用独立勾选项，不用负月份或特殊字符让用户猜格式。
- 无效大小月或不存在的闰月会在计算前拒绝。
- 页面同时显示原始农历输入与解析后的公历民用日期；保存后命盘页、Markdown 和 CSV 仍可追溯两者。
- 未知时辰仍保持 `time=null`；日期只转换一次语义，随后 13 个代表性探针分别走 IANA/DST 解析。

## 2. 版本化转换链

```text
BirthInput（原始农历 + 闰月标记）
  → lunar-typescript@1.8.6 固定历法表
  → 公历日期
  → 公历转回农历并核对年月日/闰月
  → 原民用时间 + IANA 时区
  → DST 候选 / UTC instant
  → 四柱候选、结果哈希、Revision
```

农历转公历算法 ID：`hakimi-time-core:lunar-typescript-1.8.6-to-solar:v1`，定位到 `Lunar.ts`；公历转农历纯日期算法 ID：`hakimi-time-core:lunar-typescript-1.8.6-to-lunar:v1`，定位到 `Solar.ts`，并用 `Lunar.ts` 做往返核对。两者都锁定上游提交 `0f3e95d15e31f1a7c7b93d624542649347328a20`。转换框架明确标为 `fixed_plus08_lunisolar_date`，不宣称它已经解决不同地区历法传统的全部争议。

公历转农历公共 API 的可双向往返下界是 `1900-01-31`：更早的 1900 年公历日期会落入农历 1899 年，而当前 `BirthInput` 契约不接收 1899 年。它们会被明确拒绝，避免返回无法再交给正向 API 的半开范围结果。上界是 `2100-12-31`。

`CalendarResolution` 至少保存：

- 输入历法、原日期、闰月标记；
- 解析后的公历日期；
- 算法 ID、上游名称/版本与源码定位；
- 固定历法框架与往返校验结果；
- 工程候选警告。

公历输入也生成恒等解析快照 `hakimi-time-core:gregorian-identity:v1`，因此后续逻辑不靠字段缺失猜测数据年代。

## 3. 已有自动证据

- `1995-07-23` 农历 → `1995-08-18` 公历，UTC 与同公历输入一致；
- `2023-02-01` 普通二月 → `2023-02-20`；
- `2023-02-01` 闰二月 → `2023-03-22`；
- 不存在的 `2024` 闰正月明确拒绝；
- 农历与对应公历生成相同四柱事实，但因原始输入不同，结果哈希不同；
- 农历未知时辰生成 13 个候选，每个候选保留同一转换快照；
- 新建页显示原始农历、公历解析、UTC 与转换警告；
- Markdown/CSV 同时导出原日期、闰月、公历日期和算法 ID。
- 已冻结 24 个香港天文台权威历表日期对，并对每个日期对执行两个方向，共 48 个自动断言；当前适配器 48/48 匹配；
- .NET Framework 4.8 `ChineseLunisolarCalendar` 冻结运行记录为 23 条匹配、1 条低于其最小支持日期、0 条分歧；`npm run audit:calendar:dotnet` 会实际重跑 24 条并核对冻结记录；
- 固定负例覆盖不存在的闰月、闰月第 30 日、小月第 30 日、闰月名称错误，以及有效农历转换后越过公历上界；分别锁定 `INVALID_LUNAR_DATE` 或 `LUNAR_DATE_OUTSIDE_SUPPORTED_SOLAR_RANGE` 错误码；
- 24 条仍全部为 `candidate`，逐案例证据 `cross_checked=0`、人工 `verified=0`；来源一致和人工金标签字分开计数。

完整来源、日期表、材料摘要与限制见 [首批 24 条农历历表候选 v0.1](./首批24条农历历表候选-v0.1.md)。

## 4. 仍未通过的发布门

- 24 条候选逐案例绑定第二独立来源谱系、两位不同复核人和版本化裁决记录；当前香港天文台逐行定位已具备，.NET 仍是运行级差分，不会自动升级案例证据状态，也不代替人工签字；
- 内容寻址农历审核包与绑定具体审核包的双人裁决 envelope 已实现并接入设置页；当前 `candidate-only-v1` 仍从 Schema 层禁止预检结果伪装成 `verified`，下一步是现实双人复核与新版本 fixture 纳入；
- 浏览器端普通月、闰月、无效闰月和未知时辰的固定 E2E；
- 对非中国时区输入“农历日期”的产品语义做专家裁决；
- 转换依赖升级时的旧修订并列复算与迁移策略。

完成这些门槛前，界面只称“显式转换”和“工程候选”，不称“已验证万年历真值”。
