# 多术数融合扩展边界 v0.1

> 日期：2026-08-10  
> 状态：长期产品决定；紫微已有隔离 `4218` Browser 资料库草案，仍不代表紫微斗数或西洋星盘已进入正式产品  
> 当前发布基线：八字 Web/PWA，普通构建固定 `legacy-v13 / targetSchema 13`

## 1. 决定

哈基米长期将从八字研究台扩展为可容纳多个命理研究体系的本地优先工作台。已确认的长期体系为：

| systemId | 用户名称 | 当前状态 | 首次接入原则 |
| --- | --- | --- | --- |
| `bazi` | 八字 | `active` | 保持现有严格契约、路由、数据库和 full v1.2 备份 |
| `ziwei-doushu` | 紫微斗数 | `planned` | 独立引擎、星曜/宫位事实、规则配置、金标与备份子契约 |
| `western-astrology` | 西洋星盘 | `planned` | 独立星历、黄道/宫制、相位事实、规则配置、金标与备份子契约 |

`planned` 只表示路线已经确认，不在八字生产壳中提供可点击的伪入口，不在八字库中创建空记录，也不承诺算法准确性或发布日期。独立 `4218` 研究预览属于失败关闭的工程草案，不会把这里的产品状态改成 `active`。

当前 Web 帮助页使用展示层 `research-system-roadmap.ts` 生成这份路线说明。该目录只保存稳定 ID、`active/planned` 状态和边界文案；计划项的 `entryHref` 固定为 `null`，不带计算适配器，也不进入数据库、备份、诊断或启动协议。

## 2. 现在不做的“伪通用化”

现有 `Case`、`Revision`、`ChartFacts`、ResearchQuery、Transit、Citation chart field、十六分区数据库和 full v1.2 都是经过严格验真的八字协议。当前不得为了看起来通用而：

- 给全部旧记录批量补一个 `system` 字段；
- 把四柱、紫微宫位和西洋行星塞进一个任意 JSON `facts` 字段；
- 在 v13 数据库中预建紫微或星盘空表；
- 扩宽 full v1.2，使旧备份在没有显式迁移时改变含义；
- 让一个体系的规则、引用或专家证据替另一个体系背书；
- 生成未经实现和验收的跨体系吉凶、合盘或一致性结论。

这些做法会破坏失败关闭、不可变修订、摘要验证和历史备份语义。

## 3. 可共享的工作台能力

未来各体系可以共享产品外壳和研究动作，但必须通过版本化适配器接入：

- 本地优先、离线启动、文件交付和平台适配；
- 研究对象的别名、标签、收藏、生命周期和来源说明；
- 原始时间、地点、IANA/DST 决策与“不猜测”原则；
- 笔记、附件、文献、Citation、来源权利和审计记录；
- 保存视图、工作台最近活动和有界列表；
- 不可变 Revision、计算收据、摘要、导入预检和恢复前安全备份；
- 桌面/手机响应式壳、可访问性和未来 Android 文件能力。

共享的是研究工作流，不是计算事实。每个体系的输入、引擎、规则、事实、时间层、查询条件和专家证据必须独立版本化。

## 4. 体系专属边界

### 4.1 八字 `bazi`

继续使用当前 `hakimi-bazi-core`、四柱事实、干支关系、起运与六层运限、规则包和八字字段 Citation。当前无前缀路由和 `hakimi-bazi-research` 数据库永久视为八字兼容边界，不能在后台静默改义。

### 4.2 紫微斗数 `ziwei-doushu`

至少需要独立定义：原始输入与历法决策、命宫/身宫和十二宫、星曜与四化、安星规则配置、限运体系、引擎与历法版本、结构化字段 ID、来源与争议记录。不得从八字 Revision 推断或反向补写紫微事实。

当前已有锁定 `iztro@2.5.8` 的隔离 Node 工程适配器与 Browser Worker 预览：每次计算新建 Worker，绑定契约 `0.1.0-draft.3` / 回执 `0.3-draft`、162 项星曜注册表、20×12 亮度表、出生年支阴阳 × 排盘用性别顺逆，以及 canonical digest 接受门；官方历法证据另离线覆盖 2023–2028 的 2,192 日与 74 个农历月界。第二实现 `fortel-ziweidoushu@1.3.4` 只在 fresh Worker 中形成具名投影，差分时同时新鲜运行 iztro，并把月/时干支等语义未对齐字段列为不可比、把晚子策略未对齐直接失败关闭。Browser Worker 现返回完整的 Browser 专属工程工件，而不是 Node receipt；主线程重算四层摘要、核对当前九文件源码图，再从验真 facts/rule snapshot 派生显示。

隔离 workspace 同时保留 Node 内存 Store 的单 Revision 文件演示，并新增独立 `4218` Browser 资料库竖切。Browser 路径用独立 UUID `studyId / revisionId / parentRevisionId` 保存完整 Browser 工件，通过专用 IndexedDB `hakimi-ziwei-browser-workspace-draft` 实现显式保存、epoch/CAS、重开验真、有界最近列表和单条导出。它还可导出该独立库的完整谱系备份，选择文件后先做零写入预检，再以 create-only 单事务合并；完全相同项跳过，身份/内容冲突、陈旧 epoch、容量不足或事务中止会整批失败。`clearAll` 是唯一删除例外，并且只作用于这一个紫微草案库。它不进入 `apps/web`、八字生产数据库、full v1.2、Service Worker 或产品能力注册，也不构成专家真值；因此本节的 `planned` 产品状态不变。

### 4.3 西洋星盘 `western-astrology`

至少需要独立定义：UTC 瞬时点与地理坐标、星历版本、热带/恒星黄道、宫制、行星/点位、相位与容许度、逆行等事实、推运/行运配置、结构化字段 ID 和来源。不得用“星座”消费文案代替可复算星盘协议。

当前已有锁定 `astronomy-engine@2.1.19` 的隔离 Node UTC 位置诊断：每个请求新建 Worker，核对安装 ESM/包元数据字节、固定 Espenak–Meeus ΔT 与 7 个浮点哨兵，只输出地心 EQJ、真黄道日期位置和 UTC ±60 秒中心差分。Browser/Node 隔离门另在 Edge 与 Chrome 各两轮重放五个 fresh Worker 种子，并以版本化稳定投影取得 5/5；raw canonical 差异保留且不参与成功判定。它没有 tzdb/DST、EOP/闰秒、ICRF/目标中心工件、宫制、相位、JPL 官方响应工件或严格回执证据，顶层固定为 `diagnostic_only`，因此不是西洋星盘成功适配器，`planned` 产品状态不变。

## 5. 路由与能力发现

未来规范路由预留为：

```text
/systems/bazi/...
/systems/ziwei-doushu/...
/systems/western-astrology/...
```

现有 `/new`、`/cases`、`/cases/research`、`/compare` 等无前缀路由继续作为八字兼容路由。只有当第二个体系具备真实输入、计算、保存、重开、备份和完整的生产级失败门，并获准进入正式壳后，才显示体系切换器；隔离 `4218` 草案通过这些动作的工程竖切并不等于取得生产入口。在此之前首页只显示当前可用的八字研究能力。

2026-08-11 增补隔离 `4220` 跨体系只读并列预览（`packages/cross-system-comparison-draft`）：页面直接调用同一契约验证器，只接受冻结事实摘要 + 显式人物关联，通过后按体系渲染只读事实表；摘要失配、边界提权等一律失败关闭，零持久化、零外网，Edge + Chrome 各 3/3、共 6/6。它仍不创建体系切换器、不进入八字生产壳，也不构成“共同工作台已上线”的声明；正式共同工作台仍以第二体系取得生产入口为前提。

真正驱动产品功能的能力注册表仍然后置，并且只能描述已经可验证的能力，例如 `calculate`、`save_revision`、`query`、`compare`、`backup`。页面必须检查能力状态，不能把展示层路线目录当成执行授权，也不能仅凭 systemId 猜测功能存在。

## 6. 数据库与备份

- 本决定不修改当前 Schema，不改变普通发布身份，也不新增空分区。
- full v1.2 永久保持当前八字十六分区精确语义。
- 紫微草案已选择独立数据库 `hakimi-ziwei-browser-workspace-draft`（version 1）完成首个 Browser 持久化竖切；它不读取或改写八字库，普通 `npm run build` 继续固定 `legacy-v13 / targetSchema 13`。
- 该紫微库自己的完整 canonical JSON 备份只覆盖独立 Browser workspace；它不是八字 full v1.2，也不是未来多体系总备份。恢复前先零写入预检，恢复只做 create-only 原子合并，唯一删除路径只清空该紫微库。
- 第二体系进入正式持久化前，仍须完成生产级跨标签、容量、回滚、恢复与双浏览器/目标设备矩阵，并通过显式发布决定；不能把草案数据库静默接入现有 Schema。
- 未来多体系备份应采用上层容器，内含各体系独立验真的子工件；不能把多体系字段直接塞进旧 full v1.2。
- 跨体系人物关联若需要，应是显式、可删除的目录关系，不以姓名或出生时间自动合并敏感资料。

## 7. 跨体系研究

跨体系研究只能读取各自冻结、已验真的投影，并保留：

- `systemId`、engine、规则/星历/历法版本；
- 原始输入摘要与体系专属结果摘要；
- 来源、Citation 和证据状态；
- “事实并列”与“解释观点”的明确区分。

首个跨体系功能应是只读并列与来源核对，不是自动综合评分。任何综合规则都必须有独立版本、输入白名单、可复算输出和专属验收案例。

2. **能力探针（进行中）：** 已建立不可被生产代码导入的紫微契约、iztro 适配器、Fortel 差分、隔离 workspace、西洋契约、Astronomy Engine UTC 诊断包、独立西洋占星规则层与 `4219` 规则层浏览器预览。紫微侧已有隔离 Node/Browser fresh-Worker 工程计算、完整 Browser 专属工件、2023–2028 官方历法边界证据、少量 `upstream_regression`、双实现具名差分和独立 Browser 持久化竖切；西洋侧已有失败关闭的 UTC 天文位置诊断、Edge/Chrome 稳定投影门和独立占星规则层（黄道落位、整宫/等宫/波菲利/Placidus 宫位、行星入宫、相位枚举）、无持久化浏览器盘面预览（SVG 星盘轮 + 恒星黄道演示）与 JPL Horizons 差分离线管道，但仍不能生成严格星盘或成功回执。2026-08-10 新增 `test:e2e:western-rules-preview`：4219 规则层预览在 Edge 151 与 Chrome 各通过 1/1、共 **2/2（约 8 秒）**，覆盖热带/恒星两次计算、10 天体/12 宫/4 角渲染，并验证 localStorage、sessionStorage 与 IndexedDB 全程零写入、控制台 0 问题。详见[紫微斗数契约草案与来源门](./紫微斗数契约草案与来源门-v0.1.md)及[西洋星盘契约草案与来源门](./西洋星盘契约草案与来源门-v0.1.md)。两者都没有生产入口或专家真值；只有紫微草案拥有自己的隔离资料库与完整独立备份，它们不属于生产持久化或八字 full v1.2。

## 9. 每个新体系的最低验收线

- 输入不猜测，时间与历法歧义显式；
- 引擎、数据集和规则配置固定版本并可离线复算；
- 保存后可精确重开，不静默重算历史 Revision；
- 专家金标、工程差分和第三方对照分开报告；
- Citation/来源权利使用体系专属字段 ID；
- 备份、恢复、篡改、容量、取消和多标签失败关闭；
- Edge + Chrome 当前代码证据，发布前再补目标设备；
- 工程一致、摘要相同或竞品结果相同均不得冒充专家真值。
