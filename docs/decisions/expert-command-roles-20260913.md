# 专家检查职责与工程/正式聚合

状态：供独立PR审阅的设计决策。适用对象是当前八字专家任务包及其结构性收件进度，不改变专家资格规则。

## 三种命令

| 命令 | 退出0的含义 | 未满足时 |
| --- | --- | --- |
| `check:bazi-expert-packet-structure` | 当前任务包、索引、实际输入与readiness依赖闭包验证通过 | 缺失当前对象、篡改或范围不符均退出1 |
| `report:bazi-expert-review-progress` | 准确读出当前包及本次提供原件的结构性进度；合法0/2可以退出0 | 当前不可用、错误原件、重复席位冲突等退出1 |
| `check:bazi-expert-admission` | 正式专家准入；当前没有可信资格消费者，因此没有成功路径 | 保持已有正式命令的资格缺失/准入拒绝结果 |

原`check:bazi-expert-review-packet`继续保持正式准入行为，历史`:historical-v1`入口不变。新增明确名称不是将旧退出1改成0。结构检查不读取私有原件，也不报告收到几份；进度命令不提供私有输入时明确标注`none_supplied`，0仅表示本次输入为空，不扫描本机目录、不声称所有渠道从未收件。

进度命令可显式接受`--private-intake <请求文件>`，复用现有私有原件/身份文件校验；只输出已有安全摘要，不输出正文、身份材料、私有文件绝对路径或原始异常。结构性收到0/1/2份不会提升合格专家数，AI回件不成为真人专家意见。

请求文件沿用原格式：JSON数组，空输入为`[]`。私有根目录由该文件的父目录确定，数组项引用该目录下的原件及既有封存/身份记录；不新增可覆盖资格或私有根目录的请求字段。

## 两层聚合

Quick CI的`bazi-current-semantics`改为任务包结构和进度读取，与domain机械验证同属工程检查。新增工程聚合依赖全部工程结果，任何失败、跳过、取消或缺失都不能通过。

正式专家准入另列独立job；已有`release-gate-aggregate`继续依赖全部结果，并明确同时要求工程聚合和正式专家准入。工程聚合通过不代表整条工作流通过或获准发布。Release Evidence手动工作流增加明确的正式专家准入步骤，避免把工程状态当作资格。

既有`npm run typecheck`、`npm test`和`npm run build`调用的是正式npm生命周期聚合，仍保留正式专家门。完整工程正文使用现有`diagnose:typecheck`、`diagnose:vitest`、`diagnose:build`；Quick CI已经使用这些授权诊断入口。此次不把这些正式生命周期静默降格为纯工程检查，也不改历史固定命令清单。命令职责在此明确区分，后续若改变默认npm命令语义，必须作为明确的调用方迁移另行审阅。

## 不变条件与验收

两个只读入口必须使用现有私有品牌验证器，不能凭调用方布尔标志、计数或格式相似的对象授予成功。工作区由真实入口路径确定；未知操作、额外参数、加载器注入均在读取当前资料前拒绝。失败保留安全错误码，不打印私有错误正文。

验收包括：真实当前包结构通过；无输入进度正确报告0/2、资格仍为0；真实私有文件格式路径由既有消费者复验；正式原命令和明确别名继续拒绝；当前缺失、篡改、伪造资格、未知参数和预加载均拒绝；工程与正式聚合不会互相替代。测试中的合成原件只用于负例和数据流验证，不进入项目专家席位。

不修改current选择、原专家任务包、旧意见、旧摘要、专家人数、来源权利或现用c15ef安装。此设计和工程结果不能补出现实资格或原始专家意见。
