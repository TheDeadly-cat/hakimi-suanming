# B 阶段 v1 候选与 PWA v3 组合边界（2026-08-27）

## 当前结论

当前独立 host/provider producer 与 deployed-PWA v3 consumer **不可直接组合**。这是已确认的 B 阶段本地接口缺口，不是可以通过字段改名解决的兼容问题：

- host producer 输出 `deployed_host_http_receipt_candidate_v1`；独立 loader 的权威结果固定 `realNetworkTransportProvenanceVerified=false`、`realHostVerified=false`、`usableForAdmission=false`；
- provider producer 输出 `provider_deployment_receipt_candidate_v1`；独立 loader 固定 `rawProjectionDerivationVerified=false`、`providerAuthenticatedReceiptVerified=false`、`deploymentOperationObserved=false`；
- deployed-PWA v3 consumer 要求的是冻结的 `deployed_pwa_host_receipt_candidate_v3` 与 `deployed_pwa_provider_deployment_receipt_candidate_v3` envelope，其中 host 输入形状包含 `networkCompleted=true`、`strictGatePassed=true`、`realHostVerified=true`。

因此不能把 v1 loader 的 false 转成 v3 输入的 true，也不能放宽 v3 Schema 来接纳 v1。v3 是已冻结的离线候选合同；若未来主 consumer 原生接入可信 host/provider parser，应新增 v4，而不是原地改义 v3。

本轮已新增独立、私有、只读的 composition v1 Schema、composer/CLI、test-only fixture 与合同测试，npm 入口为 `test:deployed-pwa-host-provider-composition-candidate` 和 `verify:deployed-pwa-host-provider-composition-candidate`。composer 只生成 `deployed_pwa_host_provider_composition_candidate_v1` 机械一致性文档，不持久化现实候选包；结果固定为 `trustClass=untrusted_candidate_composition`、`status=not_admitted`、`usableForAdmission=false`，没有改变任何 admission、Release Evidence receipt allowlist 或发布授权。

## 2026-08-28 终态提交门绑定补充

composition v1 现在只接受带终态提交门的当前 v1 包：Host 必须是三个附件、receipt 与 `host-receipt-publication-commit.sha256` 的精确五文件 COMMITTED 集合；Provider 必须是五附件、receipt 与 `provider-deployment-candidate-receipt-commit.sha256` 的精确七文件 COMMITTED 集合。隐藏 pending marker、旧 tombstone、额外或缺失文件都由各自 loader 失败关闭。

composer 不只记录“loader 通过”布尔值，而是把两边完整 `terminalGateBinding` 纳入 `packageBindings.host/provider`：`path`、固定 65-byte `size`、marker 自身 `sha256` 与 `commitsReceiptSha256` 都进入 composition Schema、文档与 digest。初末两轮 loader 结果必须保持一致，固定文件集合也必须包含对应 terminal marker。

Provider A→B→A sequence 同时把每个单包的 terminal marker 固定为 `terminal-commit` role，并在统一只读验证窗口内绑定两包十四文件与三份当前源文件，共 17 个物理 identity。持久化 sequence 只保留 terminal marker 的精确四字段承诺：`path`、固定 65-byte `size`、marker `sha256` 与 `commitsReceiptSha256`；`dev`、`ino`、`realPath` 等 identity 不得越出该验证窗口。这不把该窗口解释为 Schema 13 中不存在的 application mutation epoch。

上述绑定只防止 PREPARED/失败包或 marker/receipt 分叉被组合器重新接纳。composition 仍固定 `untrusted_candidate_composition / not_admitted / unusableForAdmission`；它没有恢复 host 私有 transport provenance、provider raw→projection derivation、真实执行时序、浏览器/PWA runtime、部署/回滚、内容/专家/权利真值或任何公开发布权限。

## 为什么不能用简单 adapter

简单 adapter 无法恢复以下缺失事实：

- host writer 的进程内 WeakSet transport provenance 不存在于磁盘包；
- provider v1 的 raw projection 只是 synthetic contract，自洽不等于 provider-authenticated operation；
- v3 的 artifact/receipts/private 三根与 host/provider 各自 output root 的 exact-set、opened-handle 和 mutation 边界不同；
- 三份候选的时间只来自各自文档，不能自动成为可信时钟或真实执行顺序；
- Schema 13 明确没有 application mutation epoch，不能借组合过程倒灌 v15/v16 语义。

任何把上述缺口填成 true 的转换都会成为信任提升，而不是格式转换。

## 已落地的独立本地路线

当前 `deployed_pwa_host_provider_composition_candidate_v1` 只检查“三个候选是否至少指向同一 v13 artifact、scope 与文档时序”，没有让 v3 consumer 接纳 v1，也没有把任一 v1 producer 提升为 v3 envelope 的可信生产者。

当前 composer/verifier 按以下边界实现：

1. 亲自重新调用 host v1 loader、provider v1 loader 与 PWA v3 verifier；不得接受调用方序列化的“loader 已通过”布尔值。
2. 初次三路验证后，在终局再次运行三路 loader/verifier 并比较固定投影；结果仍只能声明多个 endpoint snapshot，没有连续跨进程 mutation epoch。
3. 绑定三包原始路径、精确文件集合摘要、receipt/evidence digest，以及当前 Schema、policy、decisions 的 raw/canonical SHA-256；摘要排序使用固定 code-unit 顺序，读取同时受单文件与包级聚合字节上限约束。
4. 对共同发布身份逐项比较完整 descriptor、Release Evidence ID、artifact-set digest、build/manifest identity、identity-lock SHA-256/lockDigest、Release Evidence size/SHA-256、`index.html`/Manifest/SW/`_headers` 摘要与 hosting policy identity。
5. 对 scope 逐项比较 candidate platform、canonical HTTPS origin、provider account/project/environment、deployment id 与 immutable deployment URL；immutable URL 不得默认等于 canonical origin。
6. 只把 provider final-readback、host probe、Edge/Chrome run 与 v3 generated-at 的顺序记为“候选文档时序一致”，不得称为可信外部时钟证明。
7. 要求 artifact、host output、provider output、PWA receipts 与 PWA private roots 互不嵌套，锁定真实目录身份，拒绝 alias/hardlink、额外文件与不闭合文件集合；composer 本身不建立持久 composition output root。
8. CLI 即使机械一致也固定 `exit 1`，直到另有显式、经审定的新版本 admission policy；不得进入正式 release lifecycle 或 receipt allowlist。

两个 composition npm scripts 当前不被 `test:release-evidence`、根 `prebuild/pretest/pretypecheck`、默认 v13 的 13 项 receipt 命令、Release workflow 或 runbook 引用，因此从正式 npm/lifecycle/workspace 命令图不可达，也不是正式 Release Evidence receipt。composition 源码作为工作区源码仍会进入 `sourceTreeDigest`；这只绑定“当前源码包含该候选工具”的身份，不能推导该工具已被正式执行、通过正式闭包或获得任何授权。

## 可建立与不可建立的字段

已实现的 composition v1 最多可以把以下机械关系记为 true：

- `hostCandidatePackageIntegrityVerified`
- `providerCandidatePackageIntegrityVerified`
- `pwaV3SemanticConsistencyVerified`
- `commonReleaseIdentityMatched`
- `commonArtifactIdentityMatched`
- `platformAndOriginMatched`
- `deploymentProjectionCrossBound`
- `candidateChronologyMatched`
- `exactPackageSetsVerified`
- `terminalEndpointSnapshotsMatched`
- `compositionDigestVerified`
- `semanticConsistencyVerified`

以下字段必须固定为 false，不能由组合关系推导：

- `sourceAndArtifactCurrentVerified`
- `networkObserved`
- `realNetworkTransportProvenanceVerified`
- `realHostVerified`
- `providerAuthenticated`
- `providerAuthenticatedReceiptVerified`
- `rawProjectionDerivationVerified`
- `deploymentOperationObserved`
- `pwaBrowserRuntimeVerified`
- `deployedPwaEngineeringVerified`
- `externalDeploymentExecutionAuthorized`
- `publicDeploymentAuthorized`
- `publicReleaseAuthorized`
- `releaseReady`
- `contentTruthAuthorized`
- `expertClaimsAuthorized`
- `rightsLegalConclusionAuthorized`
- `strictGatePassed`
- `usableForAdmission`

组合边界必须固定为：

```text
boundaryType = deployed_pwa_host_provider_composition_endpoint_snapshot_boundary_v1
verificationScope = three_independent_loader_endpoint_snapshots_no_continuous_mutation_epoch
mutationEpochCapability = absent_schema13
intervalMutationExclusionClaimed = false
abaMutationExclusionClaimed = false
samePermissionMutationExcluded = false
bundleReplayResistanceVerified = false
attemptFreshnessExternallyVerified = false
```

provider v1 loader 没有重开原 private raw、Release Evidence 或 artifact lock，因此还必须保留 `providerOriginalRawSourcesCurrentVerified=false` 与 `providerCurrentArtifactSourceReopenedByProviderLoader=false`；不能用 host/PWA 对当前 artifact 的复核倒推 provider 原始来源仍然存在或未变。

## 当前测试门与验证结果

当前独立测试文件共 12 个用例，覆盖：

- 输入字段、绝对规范路径、binding-root containment 与五个物理子根的双向隔离；
- 三个权威 consumer 的初末重复执行、共同 release/artifact/scope/deployment/chronology 投影及八项 source binding；
- artifact、origin、deployment、chronology、provenance 与 claim 漂移，以及缺失 PWA provider deployment binding；
- canonical JSON 不变时的原始 source bytes 漂移、host/provider 终点额外文件、两者 receipt 原始 bytes、共享 artifact lock、PWA private extra file 与 PWA receipt bytes 漂移；
- hard-linked PWA private input、host/provider receipt、composition id/source binding/claim 篡改与失败摘要泄露；
- CLI 缺参失败以及机械一致结果都不能变成零退出、admission、执行尝试或授权。

当前定向验证结果为 composition v1 `12/12`、其复用但不提升的 deployed-PWA v3 离线 consumer `43/43`。这些结果只建立当前本地合同的机械行为，不是正式 Release Evidence、真实网络/浏览器/provider 执行或发布验收。

共享 PWA 合成构造器已从 `deployed-pwa-evidence-v3.test.mjs` 抽到独立 `deployed-pwa-evidence-v3.test-fixture.mjs`。v3 的 43 项测试现在无条件注册，composition fixture/test 只允许导入新 fixture 模块；`--test-isolation=none` 同进程联合运行精确执行 55/55，消除了测试模块预导入与缓存导致的静默漏测。fixture 删除前会复核物理临时根与随机 workspace 的 `dev/ino/birthtimeNs/realpath` 身份。这些变化只提高测试发现与临时文件清理可信度，不改变 composition 的 `not_admitted / exit 1` 边界。

这条路线只解决候选包之间的引用一致性，不解决 producer 可信度。PWA v3 内部 host/provider envelope 的 true-shaped 候选字段仍不是由当前 v1 producer 的可信 parser 产生；v1 loader 固定关闭的 network provenance、real-host、provider-authenticated、raw projection 与 operation claims 也没有被 composition 传播或改写。现实 HTTPS、Chrome/Edge、provider deployment、A→B→A rollback、正式仓储、发布就绪与公开发布授权仍须各自独立关闭。
