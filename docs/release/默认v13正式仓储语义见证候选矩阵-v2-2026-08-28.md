## 六项操作与 16 个 capture

每个浏览器项目仍只观察 `create / edit / delete / export / restore / cancel` 六项 UI 操作，但 delete 必须有三个原生只读 capture：

1. `before_trash`：目标 Case 为 active。
2. `after_trash_before_permanent_delete`：同一 Case 已进入回收站；`deletedAt` 非空，旧 Revision 与 revision fingerprint 保持不变。
3. `after_permanent_delete`：仅在已进入回收站的前提下，目标 Case 及其完整 Revision/fingerprint 图被永久移除。

因此单浏览器 capture 数为 `2 + 2 + 3 + 2 + 5 + 2 = 16`，Edge 与 Chrome 合计 32。active-before 不能冒充永久删除的已回收前置条件。

## bounded hashed semantic witness

每个 snapshot v2 在同一个 native IndexedDB `readonly` transaction 中读取全部 16 个物理 store，并对完整 bounded inventory 生成 `bounded_hashed_case_revision_relationships_v1`：

- 全部 Case：Case ID、`latestRevisionId`、`revisionCount`、active/trashed lifecycle、完整记录摘要与排除合法 lifecycle 字段后的稳定记录摘要；
- 全部 Revision：Revision ID、Case ID、`revisionNumber` 与完整记录摘要；
- `birthFingerprints` 中全部 `recordType=revision` 的 revision fingerprint：`sourceId`、`subjectId` 与完整记录摘要。

Case、Revision 与 revision-fingerprint 三个明细集合各自最多 4096 项。标识符与记录只以 SHA-256 出现在附件中，不保留明文；集合使用 ECMAScript UTF-16 code-unit ordinal 排序，不依赖 locale。Case/Revision witness 数量分别与物理 `cases/revisions` store count 精确绑定；revision fingerprint 不与包含 `candidate_set` 的整个 `birthFingerprints` count 等同，但必须对 Revision inventory 作一一精确覆盖。

Case 另含 `editStableRecordDigest`：它只排除合法 edit 会改变的 `updatedAt / latestRevisionId / revisionCount`，保留 `deletedAt`、标题及所有其他字段；edit 前后必须相等。`candidate_set` 类型的 BirthFingerprint 不展开标识符明细，而以完整子集的 `{count, logicalContentDigest}` 聚合守卫；它与 revision-fingerprint 明细共同闭合物理 `birthFingerprints` 基数，CRUD 三项操作前后必须保持该聚合不变，未知 `recordType` 失败关闭。该聚合是额外的非披露守卫，不把 revision-fingerprint 明细错误外推为整个 store 的明细 inventory。

机械关系为：create 只增加一个 Case、第一条 Revision 与对应 fingerprint；edit 只追加一条编号连续的 Revision，旧 Revision `recordDigest` 必须保持不变，并将 Case latest/count 推进到新增 Revision；delete 必须先观察 active→trashed，再移除该 Case 的精确图。仅 URL 目标行或只比较 store count 不构成本见证。

## 15 个共有分区的内容交叉绑定

原生 snapshot 的 `recordsDigest` 继续保留：它覆盖带 `$type` 包装的 `{key,value}` 记录，不得冒充 backup payload 内容摘要。v2 另为 15 个共有物理/逻辑分区计算 `logicalContentDigest`，export target 与 restore target 的 `sharedPartitionContentDigests` 必须分别与对应 snapshot 逐分区一致；restore safety backup 也必须与 `before_commit` snapshot 一致。

独立算法 `sha256_canonical_json_multiset_v1` 定义如下：

1. 每条 plain JSON record 递归按对象键排序并生成 canonical JSON 字符串；数组内部顺序保持不变。
2. 按完整 canonical JSON 字符串作 ECMAScript UTF-16 code-unit ordinal 排序；禁止 locale 排序。
3. 将这些字符串组成 canonical JSON 字符串数组，再对 UTF-8 bytes 计算 SHA-256。

算法拒绝 accessor、cycle、sparse array、named array property、非 plain object、非有限数以及数组中的 unsupported primitive；对象中值为 `undefined` 的键只按 JSON 语义省略。缺失的共享 partition 不能静默折算为空数组。两端共同冻结的基础 known vector digest 为 `21b981965002c9b2658e08a8b9906de26963d9409f63e26ad11e6f3c4b7e70a6`；另以 `U+10000 / U+E000` 非 BMP 判别向量冻结 UTF-16 顺序，其 digest 为 `899793e09b1db200cde7180f3e52dcb63aadfc97c090734c2b0bad6648e9b4e2`，两端均分别重算。`revisionCalculationReceipts` 在 Schema 13 没有物理 store，只允许逻辑 count 0，不进入 15 项共有分区内容摘要，也不得伪造物理 store。`birthFingerprints` 是物理内部 store，不进入逻辑备份的 15 项交叉绑定。

该算法不等于 `packages/backup` 的原生 partition digest，也不改变 backup wire format。ZIP 正文仍不作为离线附件保留，所以 verifier 必须继续输出 `downloadBodiesRetainedForOfflineVerification=false`；它只能验证回执投影、snapshot 与摘要链，不能宣称离线重算了 ZIP 原文。

## 两态终态发布门

此前的补偿式 summary 发布在 final summary 已改名后仍执行可失败复核，并依赖条件性回退或持久 invalidation 收口；若复核、回退与 invalidation 连续失败，调用方可能收到失败，而磁盘仍留下旧 verifier 可接受的 final 形状。这一 commit-then-throw 分叉已从当前通用 v2 runtime、reporter 与 verifier 中删除，不能再把 v1 文档中的旧叙述理解为当前实现。

当前输出根只有两个可接受状态，且两者都精确为 5 个根条目：

- `PREPARED`：`msedge/`、`chrome/`、attempt marker、`candidate-run-summary.json` 与 `.candidate-run-summary-commit.pending`；该状态不是成功，官方 verifier 必须拒绝。
- `COMMITTED`：前四项不变，只把 pending marker 以原生同目录 rename 替换为 `candidate-run-summary-commit.sha256`；官方 verifier 只接受这一精确集合。

terminal marker 的原始字节必须精确等于 final summary 的小写 SHA-256 加一个 LF，共 65 bytes。runtime 在 commit 前完成 summary、双浏览器回执、attempt marker、目录锁、精确根集合、句柄身份与返回结果的全部可失败验证；为兼容 Windows，pending marker 句柄也必须在 rename 前成功关闭。随后不可被测试 seam 替换的原生 `pending marker → terminal marker` rename 是公开发布函数最后一个可传播失败的操作；rename 之后只允许吞错关闭已持有句柄并返回预构结果。测试入口不接受任意 callback，只能选择固定的 terminal 目标目录冲突，且 reporter 被治理禁止引用该入口，因此无法表达“先替 runtime 完成 commit、再抛错”。

独立 verifier 会重新要求精确 COMMITTED 5 项根集合，持有并重验 summary、terminal marker、receipt、attachment 与受检来源；terminal marker 必须是单链接普通文件、与全部其他受持有文件具有不同的 realpath 和 `dev:ino`，其 65 bytes、SHA-256 与 `commitsSummarySha256` 必须共同绑定 final summary。成功 API 与 CLI 都显式投影 `terminalCommitMarkerVerified=true` 和 `terminalGateBinding`；失败账只保留 `terminalCommitMarkerVerified=false`，不得伪造 binding。该门闩只消除当前进程合同里的 commit-then-throw 分叉，不证明断电持久性、目录 fsync、生产级原子 no-replace、区间 mutation 排除、ABA 排除或 Schema 13 中不存在的 mutation epoch。

## 四项 deferred 分账

四项边界全部保持 `deferred_not_executed / satisfied=false / evidence=null`：

- `two-tab`：仍需真实双标签页写协调矩阵。
- `transaction-failure`：只承接 storage transaction 在部分 mutation 后 abort 并完整回滚的运行时矩阵，reason 为 `STORAGE_TRANSACTION_ABORT_RUNTIME_MATRIX_REQUIRED`。
- `read-only-recovery`：仍需冻结且来源可核验的现实旧 v13 artifact 恢复证据。
- `cross-schema-no-backwrite`：只承接 v13→v16 shadow 与禁止 v16 自动反写 v13 的运行时矩阵，reason 为 `V13_TO_V16_SHADOW_AND_NO_REVERSE_MIGRATION_RUNTIME_MATRIX_REQUIRED`。

`transactionRollbackVerified` 只属于 transaction-failure；`crossSchemaNoBackwriteVerified` 是独立 authority，不能以 `deploymentRollbackVerified` 代替。部署 A→B→A 回滚继续是另一条证据账。
