# 独立 v13 真实 HTTPS / PWA 离线语义候选门 v2

## 当前结论

v2 已增加离线语义候选包的封闭 Schema、精确失败关闭 policy、Schema 编译入口、纯离线 verifier lib、固定参数 CLI 与合成包负面测试。verifier 只重算提供给它的字节是否内部一致；它不运行 Git、formal verifier、网络、浏览器或部署。即使内部一致，CLI 仍以退出码 `1` 返回 `status=not_admitted`、`strictGatePassed=false`。本轮没有增加任何 receipt writer、可信 receipt parser、真实执行或通过接线。因此它不是已验证的 deployed-PWA Evidence，更不是发布证据。

当前 hosting platform 仍为 `unselected`，canonical origin 仍为 `null`。policy 精确固定：

- `status=offline_semantic_verifier_only_not_admitted`；
- `executionAdmission.status=closed_missing_https_origin`；
- `semanticVerification.receiptTrustClass=untrusted_candidate_envelopes`；
- 全部真实 host、PWA runtime 与 provider receipt writer/parser capability 为 `false`；
- `externalDeploymentExecutionAuthorized=false`；
- `publicDeploymentAuthorized=false`；
- `publicReleaseAuthorized=false`。

v2 不修改 v1。v1 继续承担“在读取任何 evidence instance 前停止”的合同入口；v2 的独立复核器只读取显式隔离根中的候选字节，并冻结不可越过的终态。v2 的 semantic gate 名称明确使用 `untrusted*EnvelopeConsistent` 或 `*CandidateBytesConsistent`，不能被解释为真实 receipt 来源已可信。

## 唯一终态

v2 Evidence 的 `status` 只能是 `not_admitted`，不存在 `passed` 枚举或分支。即使未来一个合成候选包的全部 `semanticGates` 都能被重算为 `true`，仍必须同时满足：

- `executionAdmission=closed_missing_https_origin`；
- `admissionGates` 全部为 `false`；
- `claims` 全部为 `false`；
- `strictGatePassed=false`；
- `deployedPwaEngineeringVerified=false`。

未来如需打开真实执行准入，只能增加新的 policy 版本；不得修改 v2 中一个布尔值来产生通过路径。

## 固定发布身份

候选包只接受：

- channel：`default-v13`；
- database generation：`legacy-v13`；
- target schema：`13`；
- migration id：`null`；
- browser projects：按 `msedge`、`chrome` 固定；
- host verification kind：`real-network`。

Schema 13 没有 mutation epoch 能力。v2 不发明 epoch 0，也不从 PWA 观察推导 mutation epoch、内容真值、专家真值或权利结论。

## verifier 的输入域

CLI 只能接受四个显式输入：

```text
--input <private-root 内的 deployed-PWA v2 JSON>
--artifact-root <只读候选产物根>
--receipts-root <只读回执与原始 attachment 根>
--private-root <Evidence JSON 与 sidecar 根>
```

工作区是唯一 checked-in policy 根。workspace、artifact、receipts 与 private 的 `dev / ino / birthtime / realpath` 在整次验证周期内锁定；artifact、receipts 与 private 三个 root 必须位于工作区内，realpath 互异且彼此不嵌套。祖先、root 和被绑定文件不得通过 symlink 或 junction 别名跨域，树内 hardlink 也被拒绝；`.`、`..`、重复分隔符及同一 realpath 的不同拼写不能绕过附件唯一性。Evidence input 与其 `.sha256` sidecar 必须位于 private root。每个文件 binding 都必须包含规范相对路径、正字节数和原始字节 SHA-256。绑定文件通过单一打开句柄读取，并在读取前后交叉复核路径与句柄的 file identity；读取大小受 binding 或固定上限约束。

这些 root 约束只保护离线读取边界，不证明文件来源真实。

## 十项离线语义复核

独立 verifier 按固定失败顺序完成：

1. 严格读取、审计并编译 checked-in v2 Schema；精确验证 v2 policy、hosting policy 和 release decisions 仍为关闭态。
2. 验证 root realpath 隔离、regular non-symlink file、Evidence sidecar，以及 `hpwa2-*` id 和 Evidence digest。
3. 对五项 policy binding 逐项验证 role、顺序、规范路径、大小和原始字节 SHA-256；Schema、policy、hosting policy、release decisions 与 Release Evidence Schema 均以同一次稳定读取所得字节同时参与验证和 binding，禁止先使用、后换字节绑定。
4. 读取 Release Evidence、sidecar 和 artifact identity lock，重算完整 artifact inventory、artifact-set digest 与四个固定关键组件。
5. 交叉核对完整 `legacy-v13 / 13 / null` descriptor、manifest digest、build version、Release Evidence id 和 formal receipt exact envelope；formal receipt 必须绑定当前 Evidence ID、精确 12 个通过 gate、精确五项工程 claims，并禁止夹带公开授权；不得重新运行 formal verifier 并冒充 current-source 结论。
6. 读取 host receipt envelope，交叉核对 candidate platform、origin、Release Evidence id 和 artifact-set digest；只能形成候选包内部一致性结果。
7. Edge 与 Chrome 必须各有且仅有一份精确 tuple，使用不同 fresh-profile binding，且 attempt 为 1、retry/skip/flaky 为 0。
8. 对每个浏览器重算八项 attachment set；所有 receipt/attachment 路径全局互异，controller source、远端 Service Worker body 与锁定 artifact `sw.js` 分别读取后字节一致，controller/active/build/descriptor 必须交叉一致。
9. 精确重算 online root、离线 `/settings/data`、精确 case/revision、`/help` cold-start 与 reload 的观察矩阵，并分别核对 recorded Playwright 与 CDP `fromServiceWorker`；case/revision 的 before/after 必须使用不同路径、不同 capture ID、严格有序时间和精确投影结构，再比较同一 case/revision 的候选记录摘要。
10. 重算 receipt set、所有 semantic gates、claims、failures、Evidence id、Evidence digest 与终态；无论候选包是否内部自洽，v2 的 admission 与 strict gate 都保持关闭。

治理另以精确 allowlist 冻结默认 v13 全部正式 receipt ID 与命令。字符串 denylist 不是准入边界；任何新增脚本、间接别名、命令改写或 v2 verifier/evidence receipt 都不能进入 formal pre-deployment receipt set。

## Semantic consistency 不是现实真值

纯离线 verifier 最多能证明“提供给它的这些字节彼此一致”。在 receipt writer/parser 尚未取得独立可信结论时，它不能证明：

- 一个 JSON 中的 `Browser.getVersion` 确实来自本次 Edge 或 Chrome；
- recorded `fromServiceWorker=true` 确实来自浏览器运行时；
- recorded controller source 确实是该浏览器执行的脚本；
- profile 在运行前现实不存在；
- HTTPS 字符串对应真实 DNS、TLS、HTTP 主机或公开部署；
- case/revision 投影覆盖了全部真实 IndexedDB 状态；
- provider receipt 对应一次现实平台操作；
- formal receipt 仍代表当前源码与当前工作树。

摘要只能绑定字节，不能为这些字节创造来源真实性。

## 与现有浏览器证据分账

当前 Release Browser strict summary 只严格计算项目数、attempt、skip、flaky 与最终测试结果，不记录远端 origin、controller source、CDP Network 原始事件或 case/revision 候选投影，不能升级为 deployed runtime receipt。

两代 Service Worker fixture 的 summary 明确标记 `local_synthetic_fixture_only`。它可以复用 Edge/Chrome tuple、fresh profile、双标签页、controller generation 和本地离线 fallback 的测试思想，但不能作为真实 HTTPS host、同产物 deployed PWA、provider deployment、正式回滚或公开发布的回执。

## 仍不成立的结论

本轮 v2 工具和通过的合成测试没有建立：

- 已选择并审计的 hosting platform 或 canonical HTTPS origin；
- 当前正式候选 artifact package；
- 可信 host/browser/provider receipt writer 或 parser；
- 真实 Chrome/Edge PWA、Service Worker controller、离线深路由或两标签页运行时事实；
- 真实部署、回滚或公开主机确认；
- source current、发布就绪、内容真值、专家真值、权利法律结论；
- 外部部署授权、公开部署授权或公开发布授权。

因此 v2 仍属于候选合同准备态。
