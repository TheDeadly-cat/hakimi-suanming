# PR6 采集器临时签发候选边界 v1（2026-08-28）

## 1. 结论与定位

本切片只建立一个**临时、自签、默认不准入**的采集器签发候选边界。它把一次采集尝试、固定顺序的八条 transcript tuple、现有 transcript bundle 和一个终态 receipt 绑定到同一把 attempt-local Ed25519 临时密钥，并由外层 held loader 复验当前落盘端点。

即使所有机械校验均有效，结果仍固定为：

- `trustClass = untrusted_ephemeral_self_signed_collector_issuance_candidate`；
- `status = issuance_incomplete`；
- `executionAdmission = closed_missing_selected_https_origin`；
- `usableForRuntimeEvidence = false`；
- `usableForCandidateAssembly = false`；
- `formalReleaseEvidenceReceipt = false`；
- CLI `exitCode = 1`。

因此，本候选不是正式 Release Evidence，不是浏览器或运行时真值，不是部署或发布许可，也不构成任何内容、专家或权利法律结论。

## 2. 十项逻辑签发链、十一份物理 JSON 与十二文件 source family

本切片的**十项逻辑签发链记录**是：

1. 一项 attempt marker；
2. 八项按 phase-major 固定顺序生成的 tuple issuance；
3. 一项 terminal issuance receipt。

八项 tuple issuance 是 `99-collector-issuance.json` 内、由终态自签 receipt 整体覆盖的 hash-chain records，并不是八个额外的外层文件。实际落盘 exact file set 必须按下面的物理树计算，不能宣称“成功 root 恰好有 10 个文件”：

```text
<fresh-run-root>/
├── 00-collector-attempt-marker.json
├── api-transcript/
│   ├── <8 个固定 tuple JSON 文件>
│   └── bundle-manifest.json
└── 99-collector-issuance.json
```

因此，成功树的物理口径是：外层 root 恰好两个普通文件和一个真实目录；目录内恰好九个普通文件；合计十一份 JSON 文件。

中央发布治理另外冻结一个**十二文件 source family**：policy、Schema、边界文档，以及 lib、schema loader、writer、live Page adapter、loader、fixture、issuance test、live-adapter test、verify CLI 九份脚本，合计三份 docs 与九份 scripts。这是第三个独立账本。新增 adapter 与 adapter test 只进入中央 source lock，没有扩写 marker/receipt 自绑定的六项来源，也没有修改 v1 policy 或 Schema。十项逻辑签发链、十一份物理 JSON 与十二文件 source family 不能互换，也不得用同一个“10 文件”简称混指。

## 3. Opaque capsule 生命周期

写入侧只允许以下生命周期：

| 操作 | 允许的状态变化 | 必须保持的边界 |
| --- | --- | --- |
| `beginSwAbUpdateRuntimeCollectorIssuance` | 在 fresh output root 建立一次 active session | 生成 attempt-local Ed25519 密钥、`runId`、`attemptId` 和 collector nonce；先签名并发布 `00`；私钥及真实状态只留在模块内的 `WeakMap`/`WeakSet` |
| `collectNextSwAbUpdateRuntimeCollectorTupleFromPage` | 为下一个固定 tuple 内部保留一次 reservation，从调用方给出的 Page 对象采集并原子完成该 tuple | 对外输入精确只有 `{session,page}`；调用方不能提交 tuple、nonce、时间、origin、build、decoded observation 或 callback；内部固定执行同一 CDP session 的 pre `Target.getTargetInfo` → reservation nonce `MessageChannel` challenge → post `Target.getTargetInfo` → detach → internal complete |
| `finalizeSwAbUpdateRuntimeCollectorIssuance` | 在八条 tuple 全部按序完成且无 pending reservation 时终结 session | 先发布并复验现有 transcript bundle，再构造由终态自签 receipt 整体覆盖的八项 tuple hash chain，最后独占写入 `99`，执行外层复验后使 session 失效 |
| `abortSwAbUpdateRuntimeCollectorIssuance` | 使 active session 失效 | 清除内存私钥和 capsule authority、关闭 held handles；保留 attempt root，不删除、不修复、不复用 |

writer 不再公开导出任何 reserve/complete 或 `testOnly` reserve/complete hook；测试夹具也必须经同一个 live Page 入口。内部 reservation 的授权性来自模块私有对象身份与私有状态；adapter 返回的一次性 capture envelope 还由 adapter 私有 `WeakSet` 绑定，writer 消费后立即失效。序列化、结构克隆或按字段伪造的对象不能取得这些 authority。任何进入 fail-closed 失败路径的生命周期违规都会使该 session 失效；同一 session 的并发重入请求只会被拒绝，不得夺取或使正在执行的合法操作失效。同一 root 不能回滚为 fresh，也不能在原地续写成另一次有效尝试。

### 3.1 Live Page adapter、实际边界时间与固定 deadline

live adapter 在实际 API 边界调用模块私有的单调 wall-clock sampler，填充既有 transcript 的十个时间字段；快速操作允许用 `max(Date.now(), previousGlobal + 1ms)` 作全进程最小单调钳制，受控延迟则必须真实反映在 request/response 跨度中。前九个边界覆盖 capture start、CDP create、pre/challenge/post request-response 与 detach；`completedAt` 的精确语义是“adapter 已构造完整 capture envelope”，不是随后 writer clone、Schema 校验、state commit 与 marker 重验全部结束的时间。时间不是调用方输入，也不再是在 decoded capture 全部完成后一次性补造固定 0..9ms 序列。这个口径只能说明当前进程在这些调用边界做了逻辑单调时间采样；时钟回拨或高频调用时它可能领先墙钟，仍不是可信时间戳或外部 chronology authority。

`newCDPSession`、pre/post CDP request、外层 Page challenge transport 与 detach 分别有固定 deadline；页内 `MessageChannel` 仍保留自身 5 秒 timeout。拒绝、超时、detach 失败或后续 transcript complete 失败都会使 writer session 永久失效，并只向调用方返回不携带原始 cause、nonce 或 decoded payload 的固定失败。若 `newCDPSession` 在 deadline 后才返回，adapter 会对晚到 session 发起另一个有界、吞错的 best-effort detach；同步 `postMessage` 异常也会立即清理 port/timer。deadline 只能防止 writer 永久等待并约束已知晚到资源的清理尝试，不能证明底层浏览器 transport 已取消，也不能把 caller-supplied Page 认证为真实 Chrome/Edge 对象。

## 4. 文件发布顺序与 held 边界

### 4.1 Fresh root 与 marker-first

`begin` 必须独占创建一个此前不存在、位于要求根目录内的真实目录。已有目录、非空目录、符号链接目录或越界路径均不是 fresh root。

`00-collector-attempt-marker.json` 使用 `wx+` 独占创建，写入后同步并从同一 handle 回读校验。该 handle 从 `begin` 一直持有至 `finalize` 完成或 session 失败/中止；每次 reservation、tuple complete、transcript 发布前以及外层复验后都要再次核对其 bytes、SHA-256 和文件身份。

### 4.2 现有 transcript：8 tuple + manifest-last

只有八条 tuple 全部按固定 phase-major 顺序完成后，`finalize` 才调用现有 transcript writer，在新的 `api-transcript/` 中发布八个固定 tuple 文件，并将 `bundle-manifest.json` 作为该嵌套 bundle 的最后文件写入。嵌套 loader 随后按现有 transcript 契约复验九文件 exact set、八条 tuple、manifest、bundle identity、digest 和其四项来源绑定。

### 4.3 Receipt-last

外层 receipt 把 `00`、由终态签名整体覆盖的八项 tuple hash chain、transcript manifest、`bundleId`、`bundleDigest`、`derivedEvidenceDigest`、`sourceSetDigest` 和六项来源绑定合并到同一终态记录中。`99-collector-issuance.json` 必须在 transcript bundle 已发布并复验后才以 `wx+` 独占创建、同步和 held；它是成功树的最后发布文件。

写入 `99` 后还必须复验外层 exact root set，调用 outer held loader，并再次通过原 `00`/`99` handles 回读及核对终态目录。`99` 的存在只表示这个临时自签协议到达终态，不表示发布准入。

## 5. attempt-local Ed25519 自签与终态覆盖链

每次 `begin` 都生成一把新的 Ed25519 密钥；私钥只存在于 active session 的进程内状态，公钥以 canonical SPKI DER base64 和由其 SHA-256 派生的 `issuerKeyId` 写入 `00`。

同一把临时私钥只直接签署两个域分离的终端：

1. 自签 attempt marker；
2. 自签 terminal receipt，并把 marker binding、完整 tuple hash chain 与 transcript bundle binding 收口。

八项 tuple issuance 本身不各带一份 Ed25519 signature。它们按固定 1 至 8 顺序组成 predecessor-linked hash chain；每项绑定项目、phase、slot、各级 nonce、transcript path、raw byte size、raw-byte SHA-256、record digest、前项 digest 和本项 digest。terminal receipt 将完整数组纳入自己的 digest 后再签名，因此临时私钥对八项链提供的是终态整体覆盖，不得表述成“逐条独立签署”。

签名输入使用域分离后的 canonical document digest，并对 SHA-256 的原始 32 bytes 做 Ed25519 签名。公钥、签名和 JSON 字段均受严格 canonical/shape 校验。

这个链只能机械证明“当前候选中的 marker signature、八项 predecessor-linked issuance digest 和 receipt signature 可由同一把临时自签密钥的终态覆盖关系闭合，且内部绑定未发生可见漂移”。它没有外部 trust anchor、身份绑定、可信时间戳或历史吊销登记，不能证明是谁、在哪台机器、通过哪个浏览器或在何时进行了真实采集。

## 6. 六项来源绑定

marker 与 receipt 必须以固定角色、固定路径、raw byte size、raw-byte SHA-256 和 JSON digest 绑定以下六项来源；顺序、角色、路径、文件身份或 bytes 变化均 fail-closed：

1. `collector-issuance-policy`：`docs/release/sw-ab-update-runtime-collector-issuance-candidate-policy.v1.json`；
2. `collector-issuance-schema`：`docs/release/sw-ab-update-runtime-collector-issuance-candidate-v1.schema.json`；
3. `api-transcript-policy`：`docs/release/sw-ab-update-runtime-api-transcript-candidate-policy.v1.json`；
4. `api-transcript-schema`：`docs/release/sw-ab-update-runtime-api-transcript-candidate-v1.schema.json`；
5. `runtime-capture-policy`：`docs/release/sw-ab-update-runtime-client-capture-policy.v1.json`；
6. `runtime-capture-schema`：`docs/release/sw-ab-update-runtime-client-capture-v1.schema.json`。

其中后四项同时由现有 transcript loader 按其内层契约复验；外层 receipt 再绑定 transcript 的 manifest 与 source-set 结果。这是嵌套验证，不得把内层四项和外层新增两项误算成彼此可替代的来源证明。

## 7. Outer held loader 的当前机械边界

外层 loader 在同一验证窗口内同时打开并持有：`00`、嵌套 transcript 的九个文件、`99` 和六个来源文件。它至少执行以下 fail-closed 检查：

- outer root 仅允许 `00`、真实 `api-transcript/` 和 `99`，嵌套目录仅允许固定八 tuple 加 manifest；
- 拒绝符号链接、非普通文件、路径越界、可检测的 hardlink/physical alias 和跨角色文件身份复用；
- JSON 采用严格解析、exact-key/schema 约束，拒绝 BOM、非法 UTF-8、重复 key、accessor/prototype 形状混入和非预期字段；
- size 与 SHA-256 均针对实际 held raw bytes，JSON digest 针对规范化值，两者不能互相替代；
- 调用现有 transcript loader 后，将其结果与外层已持有的九文件 bytes、tuple bindings、manifest、bundle identity/digests 及四项内层来源绑定逐项对照；
- 终点再次通过同一 handles 回读，并复核外层与嵌套目录集合和文件身份。

这建立的是一个重叠的 held-file 验证窗口和终点一致性检查，不是从首次采集到最终读取期间覆盖全部证据文件的连续 mutation epoch。外层 loader 的读取结果中，`attemptMarkerHandleHeldAcrossIssuance` 仍为 `false`；该字段只有 writer 自己在成功 finalize 返回时才能陈述为 `true`。

## 8. 固定 v13 与无 epoch

本切片继续固定：

```text
channel = default-v13
dbGeneration = legacy-v13
targetSchema = 13
migrationId = null
mutationEpochCapability = absent_schema13
epoch = null
```

不得从时间戳、nonce、签名链、held handles、mtime、文件身份或目录终点快照伪造 mutation epoch。`continuousMutationEpochVerified`、`samePermissionMutationExcluded`、`intervalMutationExcluded` 和 `abaExcluded` 均保持 `false`。本切片不授权 schema promotion，也不改变 legacy-v13 的发布身份。

## 9. 机械可证明与不可证明分账

| 账本 | 本切片能给出的机械结论 | 不得外推的结论 |
| --- | --- | --- |
| 候选结构 | 当前终点符合 outer exact set、nested 9-file exact set 和固定八 tuple 顺序 | 采集发生于真实外部环境 |
| live 生产接线 | 终态 tuple 只能经 exact `{session,page}` 入口，内部 reservation nonce、单 CDP session、MessageChannel、实际边界时间与固定 deadline 被机械覆盖 | caller Page 是可信浏览器对象、CDP wire bytes 已捕获、底层超时操作已取消或真实 Chrome/Edge 已运行 |
| 自签与 hash chain | marker 与 receipt 由同一 attempt-local key 自签，receipt 整体覆盖八项 predecessor-linked issuance digest | 八项 issuance 分别具有独立签名、签发者身份可信、主机可信或密钥受外部托管 |
| 内容绑定 | 当前 held raw bytes、SHA-256、JSON digest、manifest/bundle/source bindings 相互一致 | bytes 的事实含义、业务真值或权威性正确 |
| mutation 边界 | writer 持有 `00` 跨越本次签发；loader 建立重叠 held-file 复验窗口与终点快照 | 连续 mutation epoch、同权限并发修改排除、区间不变或 ABA 排除 |
| v13 身份 | 候选固定为 `legacy-v13 / targetSchema 13 / migrationId null` | v15/v16 或任何 schema promotion 获准 |
| CLI | 有效候选可被机械识别，但仍返回 `NOT_ADMITTED` 与 exit 1 | runtime evidence、candidate assembly 或正式 Release Evidence 通过 |

## 10. 必须保持为 false 的外部账本

整包复制仍然可能保留全部内部签名和 digest；掌握相同生成逻辑的一方也仍可创建新 key、重建并重签一个内部自洽的新包。由于没有外部身份、时间、nonce registry 或受信采集服务，当前 loader 无法区分这些情形。因此以下各账必须全部保持 false：

- external attempt freshness 与 historical replay resistance；
- trusted collector/provider/host identity 与 runtime collector provenance；
- browser object、browser binary、browser runtime、browser transport 和 real-browser execution provenance；
- Chrome/Edge、双客户端、Service Worker、offline transport 或 OS process restart 的真实运行证明；
- 选定公开 HTTPS origin、公开主机、部署执行、PWA/Service Worker 上线与回滚确认；
- `deploymentReady`、`releaseReady`、正式 Release Evidence、公开部署或公开发布授权；
- 内容真值、专家结论、来源权利或法律结论；
- schema promotion 与任何其他 authority promotion。

即使文件、签名、来源和嵌套 bundle 全部有效，CLI 也必须以 exit 1 结束。任何把有效候选改写成 exit 0、`READY`、allowlist member 或授权 receipt 的行为，都是 authority promotion，应 fail-closed。

## 11. 失败、中止与 discard-required root

任何异常、非法 capsule、次序错误、nonce 重用、Page/CDP/MessageChannel 拒绝或超时、detach 失败、签名错误、来源漂移、transcript binding 不符、文件集合变化、物理 alias 或终点复验失败，都会使当前 session 失效并关闭 held handles。超时后的底层 Promise 可能仍由浏览器或驱动在后台自行收尾；当前机械边界只保证 writer 不再等待或复用该 issuance session，不声称 transport cancellation 已被证明。

失败或显式 `abort` 后，writer 不删除、不覆盖、不回滚、不续写已有 root；内存 session 永久失效，该 root 不能恢复成 fresh root，也不能成为下一次尝试的输入。缺少 `99` 的 marker-only 或 `00 + api-transcript/` 是 loader 可机械识别的 `discard-required` 不完整 root。

当前 v1 格式没有在 `99` 之外再设置受信 commit marker 或持久 discard tombstone。因此，如果 `99` 已成功发布后 writer 才因终点复验或本地运行错误返回失败，独立 loader 在未来只能按当时的 exact set、held bytes、签名和 binding 重新判断当前端点；只要这些当前值机械有效，它仍可能返回一个 `attemptMarkerHandleHeldAcrossIssuance=false`、freshness/replay/runtime authority 全关闭的候选结果。该结果不证明原 writer 调用成功返回，也不保存进程内失败历史。调用方若已观察到 finalize 失败，操作规程仍应把该 root 整体废弃并在新的 fresh root 重试；但“失败历史可由当前磁盘包持久强制识别”不是本切片已证明的性质，更不能据此声称区间 mutation 或 ABA 已排除。
