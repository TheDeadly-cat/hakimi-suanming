## 2. 已落盘的源码机制

### 页面代际锁存

- `apps/web/src/lib/release-controller-takeover-write-fence.ts` 提供单向、不可解除的页面代际 latch。
- `apps/web/src/main.tsx` 在处理精确的 `FREEZE_RELEASE_CONTROLLER_TAKEOVER_WRITES_V1` 时，先同步 latch，再解析身份、冻结 release-control coordinator，最后动态加载 ResearchDatabase 并排空在途写入。
- `controllerchange` 再次同步 latch；已锁页面不能通过一次失败重试或旧 runtime 状态解除。
- 同一已锁页面允许新的、身份完全一致的接管请求重新执行 drain，避免一次可恢复 NACK 永久毒化重试。

### ResearchDatabase / Dexie 写边界

- `packages/storage/src/index.ts` 的 DBCore mutate 中间件在每一次实际 mutation 前动态读取 controller-takeover fence；检查位于 migration privilege 之前。
- 显式 runtime lock 与 controller fence 按 OR 组合；migration privileged write 不能绕过页面代际锁。
- `drainControllerTakeoverWrites()` 使用覆盖全部表的 readwrite 排序事务，等待更早的冲突事务终局。
- 双连接、多步事务测试覆盖“第一步已写、latch 后第二次 mutate 被拒、整个事务回滚、另一连接 drain 等待、drain 后两连接继续拒写”。

### release-control 写边界

- `apps/web/src/lib/release-database-coordinator.ts` 在 controller takeover freeze 时同步禁止新的 boot commit，并等待已经开始的 boot commit 终局。
- freeze ACK 的顺序固定为：release-control commit drain 完成，再导入 ResearchDatabase，再完成 ResearchDatabase drain。

### active A 与 waiting B 协议

- 只允许 source 和 target 的完整 release descriptor 相等；跨 Schema descriptor 继续走独立 migration 协议。
- waiting B 只接受当前 active ServiceWorker 来源、一次性 256-bit challenge、精确 request/source/target tuple。
- waiting B 的 PREPARE 通过 `event.waitUntil` 保活，直到 commit、abort 或 60 秒过期；challenge 不再只依赖可被提前回收的空闲 worker 全局状态。
- 若 B 已实际生成 `CHALLENGE_ISSUED` 但回执丢失，A 只允许同一 active worker、同一 requestId 以 `targetBuildVersion=null / challengeNonce=null / PREPARATION_ACK_NOT_OBSERVED` 做认证取消；B 立即释放该 pending，而不是只能等待 60 秒自然过期。
- active A 使用 `clients.matchAll({ type: "window", includeUncontrolled: true })` 做稳定 client census；任一 NACK、timeout 或 client 集合不稳定均不 commit。
- A 在 commit 前先持久化 restart-safe navigation hold，再重新枚举并冻结 client；最终稳定 census 到 commit `postMessage` 之间没有 await。
- 明确且认证的 `PROTOCOL_MISMATCH` / `SKIP_WAITING_FAILED` 表示 B 没有启动 skipWaiting，可安全清除 hold 并重试；timeout、畸形 ACK、post 失败或其他响应均记为 outcome unknown，A 永久保持内存和 CacheStorage hold，直到被 B 替换。
- 页面使用独立生产调度器，只对白名单中的瞬态 `known_not_committed` 原因按 1 秒、4 秒重试，最多 3 次；成功或 `commit_outcome_unknown` 都全页关闭调度并清除其他 waiting worker 的 timer，controller/worker/epoch 改变也取消旧回调。

### 跨 Schema source resolution 与接管 drain

- `PREPARE / RENEW / ABORT / FINISH` 统一绑定有界 requestId、migrationId、source/target 完整 tuple 与调用 WindowClient；上一终局 requestId 不能被新 PREPARE 复用。
- peer 的冻结状态保存 requestId、source/target tuple 和当时的 controller；ABORTED/COMMITTED 只有从同一当前 controller 到达且完整身份精确相等才生效，旧会话迟到消息不能解冻新会话。
- resolution 先枚举冻结快照 peers，最后重读 release-control receipt；最终 epoch 检查到同步 `postMessage` 循环之间没有 await。租约到期会 supersede 卡住的旧 resolution，并在其完成前继续占有 session，禁止旧 ABORT 晚于新 COMMITTED。
- resolution ACK 在清除 live session 前发送；ACK 丢失后同一认证请求只重放 bounded terminal receipt，不重复广播。未知/损坏 control receipt、client census/dispatch 失败继续 NACK，保持 fail closed。
- coordinator 的 journal failure transition 是 sticky 单次尝试；可重建的 finalizer 只重试同一 requestId 的 worker resolution，不能再次调用 `failMigration`。controller takeover drain 会等待 prepare、commit、cancel、显式 failure finalizer 与 SW commit acknowledgement 的终局。
- controller takeover 单 client timeout 已从 5 秒调整为 15 秒，以覆盖在途 heartbeat 最长 7 秒加 resolution ACK 3 秒的既有预算；更长的未决迁移仍会超时并失败关闭，不会被强行越过。

### 导航与 holding 文档

- A 在导航入口和每个可能返回 A shell / network response 的末端都重检 takeover hold；接管前已开始的慢导航不能迟到返回 A 壳。
- marker 持久化与 abort cleanup 串行，避免 timeout 先删、迟到 `cache.put` 再恢复旧 marker。
- 精确 A 回滚重新 install 时删除自己旧的 uncertainty marker；B activate/claim 后清除其他代 marker。
- holding 文档不加载产品 bundle，也不访问研究仓储；它只在当前 controller、requestId、A/B build 和双端完整 descriptor 均精确匹配时，经私有 MessagePort 返回 `WRITES_DRAINED`。
- holding 文档不再每 2 秒刷新并制造新的 WindowClient；controllerchange、安全解除通知或 65 秒有界 fallback 才重载。

### 页面错误语义

- `apps/web/src/pages/case-library-page.tsx` 对真实 `ReleaseDatabaseWriteLockedError` 单独处理，明确显示“本次案例写入未执行”。
- 该精确拒绝不再被归入“提交结果未知”，也不会错误要求用户执行写入 reconciliation。
- 浏览器 fixture 已把断言收紧到该精确中性文本，但 fixture 本轮没有执行。

## 5. 范围限制与后续 B 阶段停止线

当前写栅栏只覆盖：

- ResearchDatabase / Dexie mutate；
- release-control boot commit；
- 由上述生产仓储路径触发的案例写入。

它不证明 `localStorage`、`sessionStorage`、任意 Cache Storage 或其他未接入副作用都已冻结，也不提供 Schema 13 不存在的 mutation epoch。端点 snapshot 相等仍不能证明区间无 ABA。

21 文件集合同样只是 `bounded_critical_source_set_not_transitive_closure`：它不证明 bundler 的完整依赖闭包，也不把源码 SHA 外推为构建产物 SHA。双 worker VM 使用 fake MessagePort、fake clock、fake CacheStorage/client 与 fake IndexedDB；它不执行 `main.tsx` wrapper，也不是浏览器 ServiceWorkerRegistration、structured clone、原生 CacheStorage、真实 skipWaiting/controllerchange 或多标签证据。v3 已提供本地夹具产物逐字节绑定机制，但本轮没有运行构建或浏览器，所以不能把机制实现写成当前项目 artifact 已捕获，更不能写成真实 HTTPS/deployed artifact 已验证。

后续必须在用户提供或选择 canonical HTTPS origin、provider、精确 A/B 不可变 artifact、授权操作者和浏览器环境后，另账执行真实 Edge/Chrome 多标签矩阵、正式仓储事实核验、部署与 A→B→A 回滚。即使这些工程证据未来通过，也不能替代来源许可、内容真值、现实专家真值、法律判断或公开发布授权。
