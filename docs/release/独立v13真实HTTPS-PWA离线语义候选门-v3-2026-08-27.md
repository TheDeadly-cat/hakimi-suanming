# 独立 v13 真实 HTTPS / PWA 离线语义候选门 v3（2026-08-27）

## 当前结论

v3 新增的是 PWA 可安装性与 Manifest 候选证据的机械一致性门，不是新的通过线。它继续固定 `legacy-v13 / targetSchema 13 / migrationId null`，继续只接受未受信的 host/browser/provider candidate envelope，并固定返回 `status=not_admitted`、`executionAdmission=closed_missing_https_origin`、`strictGatePassed=false`。`publicDeploymentAuthorized=false`、`publicReleaseAuthorized=false`、`expertClaimsAuthorized=false` 均未改变。

这里的 host/provider envelope 是 v3 Schema 内部冻结的候选形状，不等于当前独立 producer 已经可以提供同型输入。现实代码中的 host producer/loader 输出 `deployed_host_http_receipt_candidate_v1`，provider producer/loader 输出 `provider_deployment_receipt_candidate_v1`；v3 verifier 则要求 `deployed_pwa_host_receipt_candidate_v3` 与 `deployed_pwa_provider_deployment_receipt_candidate_v3`。两组类型目前不可直接组合，且不得把 v1 loader 固定为 false 的 network provenance、real-host、provider-authenticated 或 operation claims 映射成 v3 输入中的 true。详见 [B 阶段 v1 候选与 PWA v3 组合边界](./B阶段v1候选与PWA-v3组合边界-2026-08-27.md)。

当前已实现独立 composition v1，能够亲自重跑 host v1 loader、provider v1 loader 与本 v3 verifier，并比较共同 artifact、scope、deployment 与候选文档时序；它仍只输出 `untrusted_candidate_composition / not_admitted / usableForAdmission=false`。这不是 v1→v3 adapter：本地 happy-path fixture 只能证明三个独立候选包可以诚实地指向同一机械投影，不能证明 v1 producer 可信地产生了 v3 所需的 true-shaped host/provider envelope，producer trust mismatch 仍未解决。

本轮没有选择托管平台或 canonical HTTPS origin，没有生成当前正式 artifact/lock，没有运行网络、Chrome、Edge、部署、PWA 安装、A→B 更新或回滚。v3 的本地测试只能证明离线 Schema、验证器和候选 writer 彼此遵守同一合同。

## 为什么新增 v3

v2 已冻结为精确八附件浏览器候选合同，能够绑定浏览器版本、fresh profile、五条在线/离线路由、Service Worker controller/source/远端字节与 Case/Revision 只读指纹，但没有保存浏览器的 installability 结果，也没有把浏览器处理后的 Manifest、远端 Manifest 原始字节和锁定 artifact Manifest 分账绑定。因此不能原地修改 v2；v3 保留其关闭语义并新增独立版本。

v3 的浏览器 attachment 顺序精确为：

1. `browser-version`
2. `profile-preflight`
3. `browser-manifest-audit`
4. `remote-pwa-manifest-body`
5. `network-events`
6. `controller-script-meta`
7. `controller-source`
8. `remote-service-worker-body`
9. `case-revision-before`
10. `case-revision-after`

`browser-manifest-audit` 只保存 CDP `Page.getInstallabilityErrors` 与 `Page.getAppManifest` 的浏览器报告；`remote-pwa-manifest-body` 只保存经独立 HTTP request 取得的原始 bytes。二者不能相互代填。

## Manifest 独立复核

离线 verifier 对 Edge 与 Chrome 分别执行以下检查：

- installability errors 与 Manifest parse errors 必须为空，Manifest URL 必须精确等于候选 canonical origin 下的 `/manifest.webmanifest`；
- 浏览器返回的 Manifest `data` 按严格 UTF-8、无 BOM、无重复 key 的 JSON 解析，并与远端原始 Manifest JSON 做 canonical 语义比较；
- 原始 Manifest 固定 `id/start_url/scope='/'`、`display='standalone'`；浏览器 processed manifest 固定为相同 origin 的绝对 `id/startUrl/scope` 和 `display='standalone'`；
- 浏览器内容 SHA-256、规范化语义投影 SHA-256、远端原始字节 SHA-256 在 receipt 中分别重算，不能混账；
- 远端 Manifest attachment 的 bytes、size 与 SHA-256 必须和锁定 artifact inventory 中的 `manifest.webmanifest` 完全一致；
- candidate origin 必须是 canonical 公网 DNS HTTPS origin，拒绝 IP、localhost、`.localhost`、`.local`、单标签、端口、路径、凭据、query 与 fragment；
- browser run、五条 route 与前后 Case/Revision capture 的时间必须是 canonical UTC ISO；五条 route 必须严格递增，并保持 `before < case route < after` 且全部位于 run interval；
- 十个 attachment 的路径、角色、大小、摘要与集合摘要必须精确且全局不重用。

新增 semantic gate 名称为 `pwaInstallabilityAndManifestCandidateConsistent`。即使该 gate 与其余 candidate consistency gates 全部为 true，也只表示输入字节内部一致；它不能建立受信 writer/parser、真实浏览器执行、现实主机、部署操作、OS 安装、发布就绪或公开授权。

## 运行入口与隔离

- 离线合同测试：`npm.cmd run test:deployed-pwa-evidence-v3`
- 离线候选复核：`npm.cmd run verify:deployed-pwa-evidence-v3 -- --input <private-root 内 JSON> --artifact-root <artifact-root> --receipts-root <receipts-root> --private-root <private-root>`
- 浏览器候选采集器测试：`npm.cmd run test:deployed-pwa-candidate-collector`
- 浏览器候选采集器定向类型检查：`npm.cmd run typecheck:deployed-pwa-candidate-collector`
- 三包 composition 合同测试：`npm.cmd run test:deployed-pwa-host-provider-composition-candidate`
- 三包 composition CLI：`npm.cmd run verify:deployed-pwa-host-provider-composition-candidate`；即使机械一致也固定 `exit 1`，不得作为绿色 admission 命令。

v3 verifier 只读取显式隔离且互不嵌套的 artifact、receipts、private roots；不运行 Git、formal verifier、网络、浏览器、部署或回滚。它仍被精确排除在默认 v13 正式 pre-deployment Release Evidence receipt allowlist 之外；把 v3 命令直接或间接别名接入该 allowlist 必须由治理检查拒绝。

composition 两个 npm scripts 同样不在 `test:release-evidence`、正式 receipt allowlist、根 npm lifecycle、Release workflow 或 runbook 中，因此从正式 npm/lifecycle/workspace 命令图不可达、不是正式 receipt。其源码仍由全仓 `sourceTreeDigest` 绑定；源码身份绑定不等于正式执行、正式闭包通过或授权。

截至当前验证，本地结果为：采集器 18/18、v3 43/43、composition v1 12/12、v2 回归 20/20、Release Evidence 工具聚合 185/185、release governance 150/150；v3 + composition 在 `--test-isolation=none` 同进程下精确执行 55/55。共享 fixture 已独立成非测试模块，三处消费者的导入方向与 direct-entry guard 禁令由 release governance 冻结；fixture 清理前复核物理临时根与随机 workspace 身份。采集器定向 TypeScript、静态生产边界与离线 lockfile dry-run 的既有结果保持通过。composition 没有并入 185 项正式证据工具聚合；新增结果只证明测试发现完整、清理目标受约束，以及 receipt/file-set 初末端点闭集与三包机械投影一致，这些数字仍只属于工程合同证据。

## 与其他 B 阶段通过线分账

- 当前 artifact 的真实 HTTPS Chrome/Edge 运行仍未执行；本地合成数据不代替现实浏览器回执。
- 当前 single-generation runner 不含 baseline/candidate 双 artifact、双标签 controllerchange、浏览器进程重启或 A→B→A；不得外推为 SW 更新与回滚证据。
- [默认 v13 正式仓储边界候选矩阵 v1](./默认v13正式仓储边界候选矩阵-v1-2026-08-27.md) 已建立 Edge/Chrome 采集器、严格候选 reporter 与独立离线 verifier，并通过本地合同测试；它把六项可观察 UI 操作与四项 deferred boundary 分账，固定 Schema 13 的 mutation epoch 为能力缺席与 `null`。但当前没有 artifact lock、canonical HTTPS origin 或真实浏览器回执，四项 deferred boundary 也未执行，因此仍不是正式仓储边界通过。
- 内容真值、专家真值、来源许可、法律权利判断、发布就绪和公开发布授权继续使用各自独立账本。
