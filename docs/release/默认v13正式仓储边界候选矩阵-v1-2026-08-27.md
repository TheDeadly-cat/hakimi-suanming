# 默认 v13 正式仓储边界候选矩阵 v1（2026-08-27）

## 当前结论

本轮建立了默认 v13 仓储边界的独立候选合同、Edge/Chrome 采集器、严格候选 reporter 与离线 verifier。它固定 `legacy-v13 / targetSchema 13 / migrationId null`，能够在未来绑定同一份锁定产物，对六项可观察操作形成浏览器候选回执，并把四项尚无合格执行入口的边界明确冻结为 deferred。

这不是正式仓储边界通过。当前仍固定：

- `trustClass=untrusted_candidate`
- `status=not_admitted`
- `executionAdmission=closed_deferred_boundaries`
- `matrixComplete=false`
- `strictGatePassed=false`
- `publicDeploymentAuthorized=false`
- `publicReleaseAuthorized=false`
- `expertClaimsAuthorized=false`

本轮没有运行真实 Edge/Chrome，没有启动应用、构建或部署，也没有生成当前 artifact lock。离线测试只证明候选合同、writer、reporter、verifier 与发布治理边界彼此一致。

## 固定的 v13 仓储身份

物理 IndexedDB 固定为 `hakimi-bazi-research`、Dexie version 13、native version 130，并要求精确存在以下 16 个 store：

1. `appSettings`
2. `attachments`
3. `birthFingerprints`
4. `candidateSets`
5. `cases`
6. `citations`
7. `eventTimeMigrationReceipts`
8. `events`
9. `knowledgeDocuments`
10. `researchNotes`
11. `researcherProfiles`
12. `revisions`
13. `ruleRegistry`
14. `savedViews`
15. `sourceRights`
16. `tzdbMigrationReceipts`

逻辑完整备份固定为 format `1.2.0` 与 16 个 partition。它包含逻辑分区 `revisionCalculationReceipts`，但 Schema 13 物理库必须没有同名 store；内部物理 store `birthFingerprints` 则不得作为逻辑备份分区输出。物理 16 与逻辑 16 因此不是同一集合，不能用数量相等代替逐名核验。

Schema 13 没有 calculation receipt 或 mutation epoch 能力，候选回执必须原样记录：

- `calculationReceiptCapability=absent_schema13`
- `mutationEpochCapability=absent_schema13`
- `epoch=null`

不得把缺席能力伪造为 epoch 0，也不得把 v15/v16 的语义反向投射到默认 v13。

## 六项已建模操作

候选浏览器矩阵只观察以下六项生产 UI 操作：

| 操作 | UI 路径 | 候选机械关系 |
| --- | --- | --- |
| create | `new-demo-save` | `birthFingerprints/cases/revisions` 分别 `+1/+1/+1` |
| edit | `derive-revision-save` | `birthFingerprints/cases/revisions` 分别 `+1/0/+1` |
| delete | `cases-trash-permanent-delete` | `birthFingerprints/cases/revisions` 分别 `-2/-1/-2` |
| export | `settings-data-full-zip` | 前后物理库不变；逻辑 backup 的 15 个共有分区计数等于 `after_ui_read` 物理快照 |
| restore | `settings-data-preflight-safety-gate-restore` | 目标 preflight 不变；安全备份完整预检后才允许勾选；commit 后精确等于 backup baseline |
| cancel | `settings-data-restore-preflight-cancel` | 前后物理库不变，且无下载事件 |

每个浏览器必须生成精确 15 个 capture，ID 全局唯一、顺序固定、时间位于同一 run interval 内。浏览器侧 snapshot 先用 `indexedDB.databases()` 证明 native v130 数据库已经存在，再在一个只读 transaction 中读取精确 16 个 store；不得由候选读取器创建、升级或修复数据库。

create→edit 与 edit→delete 的相邻快照必须逐字段完全一致，防止在两个已声明操作之间夹带未记录写入。下载事件也按浏览器实际事件计数：export 恰好 1 次、restore safety backup 恰好 1 次、cancel 为 0 次、整轮总计 2 次；export 文件名必须是 `hakimi-full-backup-YYYY-MM-DD.zip`，restore safety backup 必须是 `hakimi-before-restore-YYYY-MM-DD.zip`。任何下载均以持有句柄、BigInt 文件身份、读前/读后大小和额外字节探针复核，并受生产备份合同相同的 120 MiB archive 上限约束。

export 与 restore 仍必须携带完全相同的逻辑 backup 投影；此外 runtime 与独立 verifier 现在各自把 export 投影的 15 个逻辑/物理共有分区计数交叉绑定到 export `after_ui_read` 快照。因而同时把 export/restore 两份 counts 改成相同但错误的自洽值也会失败关闭；`revisionCalculationReceipts=0` 与物理专用 `birthFingerprints` 排除仍按原 v13 边界处理。

每项 operation 都必须精确携带 `safetyBackup` 键，只有 restore 可以为非 `null`。该投影在浏览器勾选“安全备份已保存”前由下载正文完整 preflight 产生，固定为 16 个 logical partitions、`revisionCalculationReceipts=0` 且不存在 `birthFingerprints`；runtime 与独立 verifier 还分别要求它与 restore `before_commit` 的 15 个逻辑/物理共有分区计数逐项一致，并要求其 `payloadDigest` 不等于恢复目标 backup。

## 四项仍关闭的边界

以下四项没有被六项操作代替，也没有因候选测试通过而获得权威：

| 边界 | 状态 | 固定原因 |
| --- | --- | --- |
| two-tab | `deferred_not_executed` | `DEDICATED_MULTI_TAB_WRITE_COORDINATION_MATRIX_REQUIRED` |
| transaction-failure | `deferred_not_executed` | `NO_PRODUCTION_DETERMINISTIC_FAULT_ENTRY` |
| read-only-recovery | `deferred_not_executed` | `REAL_OLD_V13_ARTIFACT_RECOVERY_REQUIRED` |
| rollback | `deferred_not_executed` | `NO_POST_MUTATION_ABORT_HOOK` |

这里的 `rollback` 专指一次存储 transaction 在部分 mutation 后因 abort 而完整回滚。部署 A→B→A 回滚属于另一条 Release Evidence 账，不能用部署回滚回执填充本项，也不能反向替代。

### 三项 deferred 边界的当前机械补强

`two-tab` 现新增 exact-v13 跨连接 CAS 集成先决条件：两个独立 `ResearchDatabase(name, { targetSchema: 13 })` 连接共享同一物理数据库；A 连接完成完整备份 prepare 与 verify 后，B 连接只经生产 `CaseRepository` 提交真实案例写入；A 随后的 `applyVerifiedFullBackup` 必须精确拒绝为 `CURRENT_DATA_CHANGED`。第三连接重开后会逐值确认 B 写入与原数据完整保留、incoming 没有部分落盘；无竞争控制组则通过同一正式 API 链成功恢复。两组都确认 Schema 13 物理库不存在 `mutationState` 与 `revisionCalculationReceipts`，`readMutationState()` 以 `SCHEMA_UNSUPPORTED` 失败，不把能力缺席伪造为 epoch 0。

这 2 项本地测试只证明正式 repository/backup API 在两个 Dexie 连接之间具备可重复的 v13 CAS 先决行为；它没有两个真实浏览器页面、页面生命周期、controller 接管、下载 UI 或受信执行主体。因此 `two-tab` 仍是 `deferred_not_executed / DEDICATED_MULTI_TAB_WRITE_COORDINATION_MATRIX_REQUIRED`。

`read-only-recovery` 的生产输入链已经修复此前的描述符互斥：源救援身份始终单列为 `legacy-v13 / 13 / null`，恢复执行壳只接受结构精确的 v13→v15 或 v13→v16 影子描述符；`orphaned_v13` 还必须在捕获前后精确绑定固定 reason、唯一的 `hakimi-bazi-research` 与 native v130 inventory。捕获结果对所有页面调用方都强制携带匹配的源库名称、原生版本和日期绑定文件名，不再存在可选的兼容降级开关。producer 与页面严格校验器共用同一个文件名函数，migration ID allowlist 也不调用候选数组自己的方法。现有 E2E 合同已改为“生成冻结工件→Prepared File Delivery 对话框→显式下载”，并静态列出 v15/v16 × Edge/Chrome 四个 tuple；下载后还要求独立预检 ZIP，把完整 logical payload、逐分区 counts 与 payload digest 精确绑定到捕获前的源库投影，同时要求页面收据展示同一 digest。

这些改动只证明恢复合同现在可达且能失败关闭。当前没有构建恢复壳、没有运行上述四个浏览器 tuple、没有冻结一份现实旧 v13 artifact，也没有生成下载或预检证据，所以 `read-only-recovery` 仍是 `deferred_not_executed / REAL_OLD_V13_ARTIFACT_RECOVERY_REQUIRED`。

`rollback` 已增加 Schema 13 专属事务基线：显式从 `repositories(13)` 开始，在同一 transaction 中先暂存 case alias 变更，再让 knowledge bulk write 观察到该暂存值后抛错；事务中止后对完整 Schema 13 snapshot 做逐值相等比较，并明确证明 `mutationState` 与 `revisionCalculationReceipts` 在 Schema 13 均不存在。该结果只是一项存储层单元证据；生产 UI 仍没有确定性 post-mutation abort 入口，也没有浏览器运行，因此 `rollback` 仍是 `deferred_not_executed / NO_POST_MUTATION_ABORT_HOOK`。

## 候选回执与 mutation epoch

本节记录 v1 建立时的候选执行形状：Edge 与 Chrome 各恰好一项、单次尝试、无 skip、无 retry、无 flaky，并各自生成一份严格 Schema 回执；无参数 Node wrapper 生成高熵 `attemptId`，fresh `runId` 根、双项目目录与 attempt marker 以失败关闭方式建立。v1 policy 与 receipt Schema 的原始字节及 raw/canonical SHA-256 继续冻结，v1 仍是历史未准入合同，不能原地改写、升级转换或冒充 v2。

历史实现曾在 pending summary 改名为 final 后继续执行可失败复核，再依赖条件性回退和持久 publication invalidation 收口；这一段不再描述当前通用 candidate runtime、reporter 或 verifier。当前通用入口只接受 wire-breaking v2：`PREPARED` 与 `COMMITTED` 均为精确 5 项根集合，差别仅为 `.candidate-run-summary-commit.pending` 是否经测试 seam 不可替换的原生同目录 rename 成 `candidate-run-summary-commit.sha256`。marker 原始字节精确为 final summary 的小写 SHA-256 加 LF，共 65 bytes；全部可传播失败的复核和 Windows marker handle close 都发生在终态 rename 之前，rename 后只允许 best-effort close 和返回预构结果。官方 verifier 拒绝 PREPARED、缺失/额外/旧 invalidation 条目、错误 marker、硬链接或物理身份复用，并在成功结果与 CLI 中投影 `terminalGateBinding`。完整当前语义见 [默认 v13 正式仓储语义见证候选矩阵 v2](./默认v13正式仓储语义见证候选矩阵-v2-2026-08-28.md)；即使候选采集完整，仍固定 `matrixComplete=false`、`strictGatePassed=false` 与全部 authority false。

候选回执绑定完整 artifact descriptor、build version、manifest/artifact-set/lock digest、PWA manifest、Service Worker、文件数与逐文件 inventory。采集前后必须对 artifact 重新验证并保持 verification digest 相同。输出固定在 `tmp/storage-v13-matrix-candidate/<runId>`；writer 会重新绑定 `cwd/outputRoot/runId/project/artifact/lock`，把浏览器输入先做不可变快照，并以独占持有句柄写入、同步及回读附件。artifact root 与 lock 的 `dev/ino/birthtimeNs` 以无损十进制字符串进入回执。离线 verifier 另行持有并复核源文件、summary、receipt 与附件，发现文件或目录重绑、验证期修改、额外/缺失附件、摘要漂移或 capture 时序漂移即失败关闭。

独立离线 verifier 还会复核双浏览器精确文件集合、attempt marker、候选 summary、策略、锁定本地 artifact inventory，以及固定 Schema `$id` 与 canonical SHA-256 `0cd4fe44d79d14aa3d2385f1e3f55af7d9b5f320ca8286de6f41059c7d72d8cc`。输出范围明确为 `offline_candidate_envelopes_and_local_artifact_only`，只声明 browser receipt envelopes 与本地锁定 artifact 身份一致，并固定 `remoteServedArtifactBytesVerified=false`。它只证明候选命令未进入正式 Release Evidence 的精确 13 个 decision IDs；中央发布治理另行冻结全部正式 npm/lifecycle/workspace 可达脚本闭包，不能把两项检查混写成同一结论。verifier CLI 即使证明候选内部完整，也固定以非零状态退出，防止被误当成正式准入门。

## 明确保留的候选残余风险

- artifact 稳定性是多次端点快照与精确文件系统身份复核，不是一个能证明整个区间绝无 ABA 替换的生产 mutation epoch；Schema 13 仍明确没有该能力。
- export 与 safety backup 的 ZIP 会在浏览器阶段通过持有句柄完成大小、摘要、格式、payload 与分区计数预检；离线 verifier 分别把 export projection 绑定到 `after_ui_read`、把 safety projection 绑定到 `before_commit` 的 15 个共有分区计数，但不能证明相同计数下每条记录内容都逐项相等。ZIP 正文未作为离线附件保留，因此离线 verifier 固定输出 `downloadBodiesRetainedForOfflineVerification=false`，不能独立重算 ZIP 内容，只能验证浏览器回执和其余附件链。
- candidate receipt、attempt marker 与 summary 未由受信执行主体签名；256-bit nonce 降低碰撞与预创建风险，但不能证明 wrapper 来源或阻止本地调用方重建一套内部自洽候选。因此 `trustClass=untrusted_candidate` 与离线 verifier 强制非零退出都必须保留。
- reporter 只负责双浏览器运行形状和回执集合的关闭态汇总；独立离线 verifier 仍是必需步骤，reporter 成功不能单独成为准入证据。
- storage candidate 只以页面发布身份字段绑定锁定 artifact，并不独立证明公开 origin 返回的全部应用字节就是该 artifact；真实部署字节、PWA/SW 与 deployment identity 仍由其他 B 阶段证据链负责。
- 预置的 `tmp` 或 candidate parent junction/reparse/realpath 越界现在会在任何后续子目录写入前被拒绝；但 Node 的路径式 API 仍无法证明同权限本地进程不会在“最后一次身份复核→mkdir/open/rename”之间主动替换祖先。候选输出根必须保持私有，且完成后仍必须由独立离线 verifier 检查最终路径与文件身份。该并发残余不构成正式准入，也不能被写成生产级 handle-relative/no-reparse 保证。
- Node `rename` 没有跨平台原子 `no-replace` 选项；当前 v2 在 terminal rename 前验证目标不存在，但 POSIX 上同权限写入者仍可能在最后一次 absent 检查后并发创建 terminal 目标并被 rename 覆盖。该竞态限制在私有 untrusted candidate 根内，最终仍由独立 verifier 重验精确集合、字节、单链接与全局物理身份；这不能宣称为生产级原子 no-replace 发布。
- 正式 npm 闭包摘要冻结的是可达 package script 的精确命令三元组，不递归摘要每个既有 wrapper 源文件的内容；中央治理另行冻结本候选 Node wrapper 与 global setup 的 LF-normalized 源码 SHA-256，并冻结 reporter 调用 hardened publication helper、runtime 的 PREPARED/COMMITTED 精确集合、固定 65-byte terminal binding、受限故障注入、Windows rename 前关闭句柄、原生终态 rename，以及 verifier 的 exact-set/held-file/CLI binding 语义，同时禁止旧条件回退与 invalidation 重新流入，但这仍不替代 artifact manifest、Release Evidence 与部署验证。

## 与正式 Release Evidence 的隔离

默认 v13 正式 Release Evidence 仍是精确 13 项；正式浏览器 ID 现为 `boot`、`backup`、`pwa` 与 `web-v1-flow`，四者都必须预览同一份锁定 `dist/web`。storage candidate 未加入 decisions、正式 Schema、正式 browser reporter、正式 runner、Release workflow 或 runbook。

发布治理另外从正式 13 条命令及四项正式 Playwright `webServer.command` 出发，闭包解析根包与 workspace/prefix 包中的 `npm test`、`npm run` 以及自动 `pre/main/post` 生命周期；当前冻结 32 个可达脚本三元组，其 canonical SHA-256 为 `eaba293e79453b250ce1d3520989da0dad184843e40dd28a9231c296f2bc9092`。通用 `serve:e2e / build:e2e / preview:e2e` 已不再进入正式闭包。任何命令漂移或可达脚本引入 storage candidate 身份都会失败关闭。候选 TypeScript 文件也从根 `tsconfig.json` 精确排除，只由专用 `apps/web/tsconfig.storage-v13-matrix-candidate.json` 检查。

这些隔离规则只能证明候选没有机械偷渡进现有正式证据链，不能自行作出发布、部署、专家、内容或权利结论。
