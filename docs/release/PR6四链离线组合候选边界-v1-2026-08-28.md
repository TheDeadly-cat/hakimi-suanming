# PR6 四链离线组合候选边界 v1（2026-08-28）

## 1. 结论

本 family `sw-ab-update-candidate-runtime-client-capture-collector-issuance-composition` 只建立四条既有候选链之间的**离线机械交叉绑定**：

1. SW A→B 主候选；
2. 独立 runtime-client-capture 候选；
3. issuance root 内固定 `api-transcript/` 的已解码 API transcript；
4. collector-owned、attempt-local Ed25519 临时自签 issuance candidate。

机械一致的输出仍固定为：

- `evidenceClass = offline_untrusted_four_chain_composition_candidate`；
- `producerBridgeStatus = producer_bridge_absent`；
- `trustClass = untrusted_four_chain_composition_candidate`；
- `status = not_admitted`；
- `executionAdmission = closed_missing_selected_https_origin`；
- `strictGatePassed = false`；
- `runtimeAdmissionPassed = false`；
- `admissionPassed = false`；
- `usableForRuntimeEvidence = false`；
- `usableForCandidateAssembly = false`；
- `usableForAdmission = false`；
- `formalReleaseEvidenceReceipt = false`；
- CLI 固定退出码 `1`。

这个 family 不把四个未受信候选相加成可信证据，不补出当前缺失的 producer bridge，也不进入默认 v13 的正式 Release Evidence receipt allowlist。

## 2. 旧 composition v1 冻结，新 family 不升级旧证据

既有 `sw_ab_update_candidate_runtime_client_capture_composition_v1` 及其 policy/Schema 继续作为独立、冻结的两链 v1。新 family 在 held checkpoint 内重跑其库级 composition，并保存 `compositionId`、`compositionDigest` 与 `sourceSetDigest`，但不修改、覆盖、转换或原地升级旧 v1。

新输出另有独立身份：

- `recordType = sw_ab_update_candidate_runtime_client_capture_collector_issuance_composition_v1`；
- `verificationKind = offline_four_chain_primary_input_and_issuance_overlap_v1`；
- `compositionId` 前缀为 `swab4c1-`。

因此，旧两链 v1 的既有机械结论不因新 family 而扩大；新 family 也不能反向把 transcript 或 issuance 写进旧 v1 的信任边界。

## 3. 八个显式输入与磁盘边界

组合器只接受以下八个绝对、规范、位于同一 `bindingRoot` 下的路径绑定：

1. `bindingRoot`；
2. `candidateInputPath`；
3. `attachmentsRoot`；
4. `privateRoot`；
5. `artifactARoot`；
6. `artifactBRoot`；
7. `runtimeCaptureInputPath`；
8. `issuanceRunRoot`。

CLI 对应 `--binding-root`、`--candidate-input`、`--attachments-root`、`--private-root`、`--artifact-a-root`、`--artifact-b-root`、`--runtime-capture-input`、`--issuance-run-root`，必须恰好各出现一次。transcript 不是第九个调用方可选输入；它只能来自固定的 `<issuanceRunRoot>/api-transcript`，并由 transcript loader 与 issuance loader 分别复验。

CLI 不写正式 receipt 或组合文件，只向 stdout 输出 JSON；参数、来源、文件或交叉绑定失败时也输出关闭态 failure JSON。无论机械一致或拒绝，进程都固定以 `1` 结束。

## 4. 十二个唯一 policy/Schema 来源

来源口径固定为六组、每组 policy 与 Schema 各一份，共十二个**唯一路径**：

| 组 | policy | Schema |
| --- | --- | --- |
| 新四链 composition | `docs/release/sw-ab-update-candidate-runtime-client-capture-collector-issuance-composition-policy.v1.json` | `docs/release/sw-ab-update-candidate-runtime-client-capture-collector-issuance-composition-v1.schema.json` |
| 冻结的旧两链 composition | `docs/release/sw-ab-update-candidate-runtime-client-capture-composition-policy.v1.json` | `docs/release/sw-ab-update-candidate-runtime-client-capture-composition-v1.schema.json` |
| SW A→B candidate | `docs/release/sw-ab-update-candidate-policy.v1.json` | `docs/release/sw-ab-update-candidate-v1.schema.json` |
| raw runtime capture | `docs/release/sw-ab-update-runtime-client-capture-policy.v1.json` | `docs/release/sw-ab-update-runtime-client-capture-v1.schema.json` |
| decoded API transcript | `docs/release/sw-ab-update-runtime-api-transcript-candidate-policy.v1.json` | `docs/release/sw-ab-update-runtime-api-transcript-candidate-v1.schema.json` |
| collector issuance | `docs/release/sw-ab-update-runtime-collector-issuance-candidate-policy.v1.json` | `docs/release/sw-ab-update-runtime-collector-issuance-candidate-v1.schema.json` |

旧 composition、transcript 与 issuance 的嵌套来源清单会重复引用其中若干路径。外层先按路径去重为精确十二项；同一共享路径必须与外层 held bytes 在 `size`、raw SHA-256 与 canonical SHA-256 上完全一致，不允许把同路径的不同 bytes 当成同一来源。十二个不同路径还必须保持不同物理文件身份；候选、runtime 主输入和 issuance/transcript 文件之间的非预期物理 alias 同样 fail-closed。

共享路径去重只避免重复计数，不把一次来源读取伪装成多份独立来源证据。

## 5. 四链精确交叉绑定

新 family 至少冻结并逐项核对以下投影：

- 同一个 `runId`、`attemptId` 与 canonical public-DNS HTTPS origin；
- `default-v13 / legacy-v13 / targetSchema 13 / migrationId null` 与 `absent_schema13 / epoch null`；
- A、B 各自的 `label`、`releaseEvidenceId`、`buildVersion`、`serviceWorkerSha256` 与 `artifactSetDigest`；
- candidate/runtime 两个主输入的 path、size、raw SHA-256、`evidenceDigest`、`capturedAt` 与 held physical identity digest；
- `runtimeCapture.evidenceDigest == transcript.derivedEvidenceDigest == issuance.derivedEvidenceDigest == transcript derivedProjection.evidenceDigest`；
- transcript 与 issuance 的 `bundleId`、`bundleDigest`、`derivedEvidenceDigest`，以及 manifest、八个 tuple 文件、marker、receipt、`issuanceId`、`receiptDigest` 与 endpoint fingerprint；
- 精确八项 phase-major tuple 的 `sequence`、`projectName`、`phase`、`slot`、`observedAt`、pseudonymous client/target id、challenge nonce、runtime request/response/observation digest；
- 旧两链 composition 的八项 `clientMappings` 与 transcript 完整 `derivedProjection` 逐 tuple 相等；
- 旧两链 composition 中 candidate/runtime 的 switch/browser chronology 与 transcript 派生的 runtime `capturedAt` 完全一致；issuance 则通过同一 transcript bundle 与 `derivedEvidenceDigest` 接入该投影，不额外伪造一套 chronology；
- 十二项来源 bindings 与最终 `sourceSetDigest`。

transcript 的 CDP decoded response digest 与 runtime capture 的四字段 response projection digest 属于不同摘要语义；组合器保留各自字段，不把二者改名或冒充成同一个 digest。

## 6. held-window 的真实机械边界

外层组合器先打开并持有 candidate/runtime 两个主输入与十二项 checked sources，再调用 issuance loader。issuance loader 在自己的初次验证与终点重读之间，只允许一次 phase 为 `after_initial_validation_before_terminal_reread` 的 family-owned checkpoint；run root 必须仍是同一个 `issuanceRunRoot`。

该 checkpoint 内同时启动：

1. 冻结的旧两链 composition；
2. `<issuanceRunRoot>/api-transcript` 的独立 transcript loader。

两条分支用 `Promise.allSettled` 等待；一条先失败时，另一条仍须完成后才能关闭 held window 并向外拒绝。回调结束后，issuance loader 对自己持有的 issuance/transcript/source 端点做终点重读，外层再对 candidate/runtime 主输入和十二项来源做 held-file 稳定性复核。

因此以下陈述可以为 true：

- `candidateAndRuntimePrimaryInputsHeldAcrossIssuance = true`；
- `issuanceFilesHeldAcrossOldCompositionAndTranscriptReverification = true`；
- `issuanceCheckpointCalledExactlyOnce = true`；
- `issuanceCheckpointPhaseMatched = true`；
- `independentTranscriptReverifiedInsideIssuanceHeldWindow = true`；
- `endpointStabilityVerified = true`。

但 candidate 的 attachments、private tree 与 A/B artifact roots 仍只继承旧 composition 自己的端点快照边界；并非所有证据文件从首次采集到最终组合都由一个连续 handle/epoch 覆盖。故必须同时保持：

- `allEvidenceFilesContinuouslyHeldAcrossComposition = false`。

这里的 overlapping held window 是一个真实但有限的文件验证窗口，不是浏览器采集 epoch、跨进程锁、可信事务、目录级持续监控或同权限攻击者隔离。

## 7. `producer_bridge_absent`：当前自然生产链通常不能满足摘要相等

四链组合的摘要相等要求是严格验证条件，但当前 producer 之间没有能自然产出该相等关系的正式桥：

- 现有 runtime probe 为每条 observation 现场生成 `observedAt = new Date().toISOString()`，并独立生成 capture `capturedAt`；
- collector issuance 的 `complete` 接口不接收这组 probe 时间戳，而由 `allocateTupleTimeline()` 为每条 tuple 分配另一组 host timeline；
- transcript 派生把 issuance tuple 的 `completedAt` 映射成 runtime observation 的 `observedAt`，并在 finalize 时另行生成 manifest `capturedAt`；
- transcript loader 只返回完整 `derivedProjection` 与 `derivedEvidenceDigest`，没有把完整派生 runtime evidence 作为独立、不可变文件发布；
- 新 composition 是 verifier，不是 evidence producer，不能在验证时反向制造或改写 runtime input。

所以，由当前 probe 自然生成的 runtime capture 与由当前 issuance/transcript 自然派生的 capture，通常会因 observation/capture 时间线不同而得到不同 `evidenceDigest`。当前成功样例只能依赖合成 fixture 或由调用方按 transcript 派生投影重构的输入；这不等于真实 producer 已端到端接通。

未来若要关闭此缺口，应由独立 producer bridge 在采集/签发流程中取得并原子发布 transcript loader 的完整 immutable derived evidence，再由组合器只读消费；不得让组合 verifier 自己兼任证据生成器。完成该独立设计和现实运行验证前，`producerBridgePresent` 必须为 `false`，状态必须写作 `producer_bridge_absent`。

## 8. legacy-v13 与 mutation epoch 边界

本 family 继续固定：

```text
channel = default-v13
dbGeneration = legacy-v13
targetSchema = 13
migrationId = null
mutationEpochCapability = absent_schema13
epoch = null
```

端点文件身份、held handle、mtime/ctime、digest、nonce、tuple 时间线、临时签名或 composition digest 都不能补出 Schema 13 不存在的 mutation epoch。以下字段始终为 false：

- `continuousMutationEpochVerified`；
- `samePermissionMutationExcluded`；
- `intervalMutationExcluded`；
- `abaExcluded`。

因此，本 family 不证明读取区间内无写入、不证明 A→B→A 未发生，也不授权任何 schema promotion。

## 11. 关键 fail-closed 负测边界

本 family 的聚焦合同至少覆盖以下拒绝面：

- scope、A/B artifact、三方 evidence digest、逐 tuple projection、issuance identity、transcript 终点或嵌套来源任一漂移；
- candidate/runtime/source/issuance/transcript 之间的非预期物理 alias，同时允许同一个冻结 source path 被嵌套 verifier 以相同 bytes 重复引用；
- public composer 注入替代 verifier dependency；公开 options 只允许可选的 `cwd`，测试 seam 只留在 test-only 表面；
- checkpoint phase 错误、零次调用、重复调用或 run root 漂移；
- checkpoint 一条分支失败时，必须等另一条分支 settled 后再拒绝；
- callback 后主输入被路径替换或 held bytes/identity 改变；
- failure 输出泄露未验证 runId、attemptId、原始 payload 或错误正文；
- CLI 缺少、重复或增加 flag，stderr 非空，输出非 JSON，或任何路径返回 exit 0。

这些负测只验证合成/离线合同及故障关闭，不替代真实浏览器与公开 HTTPS 的验收矩阵。
