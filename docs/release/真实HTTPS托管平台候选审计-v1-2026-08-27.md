# 真实 HTTPS 托管平台候选审计 v1（2026-08-27）

## 结论

本文件是阶段 B 的只读平台候选审计，不是平台选择、部署指令、权利判断或公开发布授权。

当前 checked-in 状态继续固定为：

```text
deploymentPlatform: unselected
canonicalOrigin: null
legacy-v13 / targetSchema 13 / migrationId null
publicDeploymentAuthorized: false
expertClaimsAuthorized: false
```

现阶段建议把 **Cloudflare Pages Direct Upload + Cloudflare 代理的专用 staging 子域**作为第一兼容性候选，把 **Netlify 原子手工部署**作为对照候选。两者都必须先经过真实 staging 探针；不能根据官方功能表直接写入 audited allowlist，也不能直接修改 hosting policy 为 selected。

本轮没有登录任何托管平台，没有创建项目、域名、Token、部署、浏览器回执或回滚记录。工作区现存旧 `dist/web` 不是当前正式 artifact，不能部署。

## 1. 当前机器门要求的平台能力

平台必须同时满足：

1. 唯一、公开、默认 443 的 canonical HTTPS origin；全部 A/AAAA 为公网地址；
2. `/`、`/sw.js`、`/release-evidence.json`、`/settings/data` 的 HTTP→canonical HTTPS 301/308，路径和 query 不丢失；
3. 已登记 SPA 深链在 canonical HTTPS 上不发生额外跳转，并逐字节返回锁定的 `index.html`；
4. 同一个 formal Release Evidence artifact 被原子部署，部署步骤不得重新 build；
5. 所有公开 artifact、Manifest、Service Worker 和 Evidence 与本地 artifact lock 的大小及 SHA-256 一致；
6. `_headers` 与 Evidence sidecar 参与本地发布单元身份，但远端必须对它们返回无跳转 404/410；
7. 每个公开 200 响应具有精确安全头、缓存、MIME 和 identity content-coding，不得注入门所禁止的行为头；
8. provider API 能返回可冻结的 account/project/environment/deployment identity，并能对 A→B→A 操作形成不同 operation ID；
9. 能恢复历史 artifact，且历史 artifact 另有长期只追加归档，不能只依赖平台默认保留期；
10. Edge 与 Chrome 能对同一 origin、同一 artifact、各自全新 profile 执行 PWA/SW/仓储矩阵。

这些是工程门。即使全部通过，也不建立内容真值、专家真值、来源许可、发布就绪或公开发布授权。

## 2. Cloudflare Pages 候选

### 2.1 可吸收能力

- Direct Upload 可把已经生成的静态目录作为部署输入，适合“下载锁定 artifact 后部署、托管端不重新 build”的边界；
- 每个预览部署有原子的 hash URL，官方说明该 URL 可在未来继续访问，除非被用户或 API 删除；
- Pages API 可读取 deployment ID、URL、环境和阶段，并提供生产部署 rollback API；
- 没有顶层 `404.html` 时，Pages 会把项目按 SPA 处理；
- `_headers` 不会作为静态文件公开，适合控制文件本地绑定、远端隐藏的要求。

官方入口：

- [Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/)
- [Preview deployments](https://developers.cloudflare.com/pages/configuration/preview-deployments/)
- [Pages deployment API](https://developers.cloudflare.com/api/resources/pages/subresources/projects/subresources/deployments/)
- [Pages rollback](https://developers.cloudflare.com/pages/configuration/rollbacks/)
- [Serving Pages](https://developers.cloudflare.com/pages/configuration/serving-pages/)
- [`_headers`](https://developers.cloudflare.com/pages/configuration/headers/)

### 2.2 当前不能直接通过的项目

1. **现有 `_headers` 不能直接用于 Cloudflare exact gate。** Cloudflare 官方说明：一个请求匹配多个规则时会继承全部规则；同名 header 被应用两次时会用逗号连接。当前 `/*` 与 `/index.html`、`/sw.js`、`/assets/*` 重复写入 `Cache-Control`，会得到重复或互相冲突的值。
2. 官方只明确 `! Header` 可以移除默认或更广规则，没有冻结“同一个命中块内先 detach 再 attach”的执行优先级；不能仅凭文档用该写法证明 exact 单值。
3. Pages `_redirects` 不处理域级跳转。HTTP→HTTPS 四类规则需要 Cloudflare Single/Bulk Redirect Rules，并冻结 Rulesets API 原始回执。
4. canonical 自有域上的精确响应头应优先使用 Response Header Transform Rules。`Set static` 会替换全部同名值，可先建立默认 no-store 和七个安全头，再由后置 `/assets/*` 规则覆盖为 immutable；规则集及顺序必须进入部署身份。
5. Transform Rules 只作用于 Cloudflare 代理的自有域，不作用于 `<hash>.pages.dev`。如果门同时要求 canonical 与 hash URL 都满足 exact header，必须分别实测，不能外推。
6. Pages 的 pretty-URL、`/index.html` 行为以及自动 Early Hints 是否导致跳转或最终响应出现 `Link`，必须通过真实原始响应确认。现有 verifier 要求 `/index.html` 不发生意外跳转，并禁止 `Link`；在证明前均保持阻断。
7. HSTS 有 Pages `_headers`、zone SSL/TLS HSTS 和 Transform Rules 三种可能来源。必须只保留一个最终权威，并以原始多值响应证明最终严格等于 `max-age=31536000`。
8. 不得引入 Pages Functions 或 `_worker.js`；官方说明 `_headers` 不适用于 Functions 响应，这会改变当前纯静态证据模型。

补充官方入口：

- [Pages redirects](https://developers.cloudflare.com/pages/configuration/redirects/)
- [Response Header Transform Rules](https://developers.cloudflare.com/rules/transform/response-header-modification/)
- [Transform Rules](https://developers.cloudflare.com/rules/transform/)
- [HSTS options](https://developers.cloudflare.com/ssl/edge-certificates/additional-options/http-strict-transport-security/)

### 2.3 Cloudflare 仅可进入兼容性 spike 的条件

- 使用专用 staging Pages project 与专用 custom domain；
- 禁用 Git 自动构建，只接受已经锁定的 artifact；
- 不使用 Functions、自动 HTML 改写或其他运行时代码；
- 冻结 Pages project、DNS、Redirect Rules、Transform Rules、Early Hints、HSTS 和 deployment API 回执；
- canonical origin 与 immutable deployment URL 分别执行原始 header 多值、redirect、MIME、content-coding 和逐字节 hash 探针；
- 任一平台附加行为无法关闭时，Cloudflare 候选失败，不放宽 verifier 来迁就平台。

## 3. Netlify 对照候选

### 3.1 可吸收能力

- 官方明确静态部署是原子的：全部文件上传完成前不会切换线上版本；
- 每个成功部署都有内容不再变化的 deploy permalink；
- 支持 `_headers`、`netlify.toml`、SPA `/* /index.html 200` rewrite 和域/协议级 301；
- Pretty URLs 可由文件配置管理，兼容性 spike 必须显式关闭，防止 `/index.html` 或 `.html` 路径被改写；
- rollback 是重新发布既有原子部署，不触发新 build。

官方入口：

- [Atomic deploys](https://docs.netlify.com/deploy/deploy-overview/)
- [Deploy permalinks and rollback](https://docs.netlify.com/deploy/manage-deploys/manage-deploys-overview/)
- [Custom headers](https://docs.netlify.com/manage/routing/headers/)
- [SPA rewrites](https://docs.netlify.com/manage/routing/redirects/rewrites-proxies/)
- [Domain-level redirects](https://docs.netlify.com/manage/routing/redirects/redirect-options/)
- [File-based configuration and Pretty URLs](https://docs.netlify.com/build/configure-builds/file-based-configuration/)

### 3.2 阻断项

1. 现有 `_headers` 的广泛规则位于具体规则之前；Netlify 的实际匹配优先级仍需用 deploy preview 原始响应确认，不能假定与 Cloudflare 相同。
2. Pretty URLs 默认开启，必须显式关闭并验证 `/index.html`、深链和尾斜杠行为。
3. Netlify 默认会在 30 天后删除部署，付费方案通常为 90 天，Enterprise 最多 365 天；deploy permalink 和 rollback 不能承担长期 Release Evidence 唯一存储。
4. 平台附加 header、压缩、post-processing、snippet injection、prerender 和自动发布必须全部关闭或证明不影响字节及响应契约。
5. 即时 rollback 只建立托管壳切换；数据库、SW controller、旧标签页写入边界和 v13 数据仍须由独立回执证明。

因此 Netlify 适合作为兼容性对照和短期回滚演练候选，但必须把正式 artifact/Evidence 永久保存在独立只追加仓。

## 4. 其他平台

### Vercel

Vercel 支持 header、rewrite、redirect、唯一部署 URL、API 与 instant rollback，可以保留为条件备选。当前已知平台默认 HSTS 与本项目精确值不一致，且仍需证明可以关闭内容转换及满足 `_headers` 隐藏语义；未完成真实 staging 前不进入 allowlist。

### GitHub Pages

GitHub Pages 可以形成 workflow artifact、稳定 page URL 和 deployment/build 状态，但当前官方产品面没有为本项目证明原生自定义 CSP/安全响应头、精确 SPA rewrite、逐部署不可变 live URL和 rollback 原语。它不适合作为当前阶段 B 的单独托管平台。

## 5. 建议的用户决策，不是默认授权

用户需要明确选择以下之一：

1. **Cloudflare Pages compatibility spike**：提供或批准专用 staging custom domain，并授权创建 Pages project、DNS/Redirect/Transform Rules 与一次 Direct Upload；
2. **Netlify compatibility spike**：提供或批准专用 staging site/domain，并授权一次原子手工部署及配置冻结；
3. **继续保持未选择**：只完成公网 runner 和 provider receipt parser，不执行任何外部写入。

未收到选择和外部执行授权前：

- 不修改 `deploymentPlatform`、`canonicalOrigin`、redirect matrix 或 CSP 状态；
- 不安装或调用 provider CLI，不读取现存浏览器登录态，不访问第三方后台；
- 不创建项目、域名、Token、Deployment、Release 或 rollback；
- 不把本地 mocked、旧 `dist/web`、候选回执或官方文档能力写成真实通过。

## 6. 选择后的精确执行顺序

```text
用户确认 provider / account / project / custom domain / 外部执行授权
→ 冻结 provider capability profile 与配置 API 回执
→ 正式 default-v13 Release Evidence 生成一次 artifact
→ 下载并复核 artifact lock，部署端禁止 rebuild
→ 原子部署并冻结 provider deployment receipt
→ 真实 host 字节/header/redirect/MIME/content-coding 验证
→ Edge + Chrome 全新 profile 的 deployed-PWA 回执
→ UI-only 正式仓储矩阵
→ A→B 的真实 SW 更新、断网、关页重开和双标签矩阵
→ A→B→A 托管与数据回滚演练
→ 长期 artifact/Evidence 归档
```

以上各项独立记账。任何一项通过，都不能自动把其他项或公开发布授权改为 true。
