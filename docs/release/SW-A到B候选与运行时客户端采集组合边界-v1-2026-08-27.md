# SW A→B 候选与运行时客户端采集组合边界 v1

日期：2026-08-27

## 结论

本组合门只把两份已经分别通过机械内部一致性检查、但仍不受信的输入交叉绑定：

- `sw_ab_update_candidate_v1` 主候选；
- `sw_ab_update_runtime_client_capture_candidate_v1` 页面目标与只读 Service Worker challenge 采集。

组合成功仍固定为：

- `trustClass = untrusted_candidate_composition`；
- `status = not_admitted`；
- `executionAdmission = closed_missing_https_origin`；
- `usableForCandidateAssembly = false`；
- `usableForAdmission = false`；
- `formalReleaseEvidenceReceipt = false`；
- CLI 固定退出码 `1`。

它不是默认 v13 的第十四份正式 receipt，也不改变正式 npm/lifecycle/workspace 闭包。

## 固定发布身份

- channel：`default-v13`
- dbGeneration：`legacy-v13`
- targetSchema：`13`
- migrationId：`null`
- mutationEpochCapability：`absent_schema13`
- epoch：`null`

组合门不得借由 A→B 更新叙事引入 Schema 14/15/16、伪造连续 mutation epoch，或把端点相等解释成区间无突变和 ABA 抵抗。

## 组合的九类机械绑定

1. runId 与 attemptId 完全一致；
2. canonical public-DNS HTTPS origin 完全一致；
3. legacy-v13 发布身份与能力完全一致；
4. A、B 各自五字段 artifact binding 完全一致且 A/B 彼此不同；
5. runtime observation 必须严格采用 `phase → project → slot` 的 8-tuple 顺序；
6. candidate `clientId` 必须等于 runtime `pseudonymousClientId`；
7. candidate `cdpTargetId` 必须等于 runtime `pseudonymousTargetId`；
8. candidate 与 runtime 的 challenge nonce 必须相等，candidate challenge response digest、runtime request/response/observation digest 分账保存，不互相冒充；
9. initial-A、一个共享 A→B provider switch、both-browser activation/claim、post-claim observation、reload 与 stale-write-rejection 的时间窗必须可组成严格无环顺序。

Candidate projection 是 browser-major，runtime projection 是 phase-major。组合器必须先按 `(projectName, phase, slot)` 建立唯一映射，再按 runtime 的 canonical tuple 顺序输出；禁止 positional zip。

## 字节、来源与 mutation 边界

组合器直接调用两套库验证器，不调用它们的 CLI。candidate 和 runtime 各执行两次权威验证，并比较输入文件身份、原始 SHA-256、证据摘要和冻结 projection 的端点快照。candidate 的 held terminal bytes 会被重新严格解析并重算 evidence digest，且须同时等于 verifier result 与 projection 中的 digest；candidate evidence 和 runtime loader 实际消费的 policy/Schema bindings 也必须分别等于本次 checked source bindings。composition/candidate/runtime 三组 policy 与 Schema 会在前后端点读取、严格解析、编译并冻结 raw/canonical SHA-256。

每次 held read 都在 `open` 后再次检查普通文件、单链接与体积上限，并比较 handle 与终点路径的 size/mtime/ctime；candidate/runtime input 单文件上限为 32 MiB，checked source 单文件上限为 8 MiB、六份合计上限为 32 MiB。时间戳、HTTPS origin 与相对路径必须采用 canonical 形式，八个 candidate/runtime/source 输入还必须保持不同的端点物理身份。这里的“绑定”只指同次 held read 或离散端点的机械关联，不代表对目录 reparse、同权限进程或两次读取之间区间的持续监控。

这些检查只证明离散端点与各次验证内的文件稳定性：

- `intervalMutationExcluded = false`
- `abaExcluded = false`
- `concurrentFilesystemMutationResistanceVerified = false`

因此不得把结果描述成连续监控、同权限攻击者隔离或 bundle replay resistance。

## 明确不证明

本组合记录不证明或授权：

- caller-supplied page adapter 的真实性；
- runtime collector、浏览器、OS 进程重启或 HTTPS 主机的可信来源；
- document generation、controller tag/change、SW install/waiting/activation、网络中断、离线冷启动、Cache API body 或 stale-A production write 的真实运行时事实；
- trusted provider、trusted host、trusted browser runtime；
- 部署就绪、发布就绪、外部部署执行、公开部署或公开发布；
- 内容真值、专家结论、来源许可或法律权利判断；
- A→B→A 回滚、连续 mutation epoch 或 ABA 抵抗。

`publicDeploymentAuthorized=false` 与 `expertClaimsAuthorized=false` 保持不变。

## 使用方式

定向测试：

```text
npm run test:sw-ab-update-candidate-runtime-client-capture-composition
```

当前 8 项聚焦测试中有一项使用合成 candidate 私有树、38 个附件、两个 artifact root 与合成 runtime capture，完整经过真实磁盘 compose API 和 CLI；它只验证文件编排、摘要、来源和 tuple 组合链。该测试没有连接 HTTPS 主机、启动 Edge/Chrome 或调用真实页面 probe，因此不能登记为浏览器/运行时证据。

合成 candidate 构造器位于独立的 `scripts/sw-ab-update-candidate-fixture.mjs`，candidate 的 32 项测试继续无条件注册，composition 不再导入 `.test.mjs`。候选与组合在 `--test-isolation=none` 同进程模式下精确执行 40/40，防止模块缓存造成静默漏测；fixture 在创建随机子目录前先验证 workspace、`tmp` 与固定 test parent 的真实路径及非链接属性，清理前再复核子目录身份。这些检查只约束测试编排与清理安全，不提升候选信任等级。

离线验证器需要七个显式绝对路径绑定：binding root、candidate input、attachments root、private root、artifact A root、artifact B root、runtime capture input。无论一致或拒绝，CLI 都退出 `1`；输出只供补充交叉检查，不能进入正式 Release Evidence receipt 集合。
