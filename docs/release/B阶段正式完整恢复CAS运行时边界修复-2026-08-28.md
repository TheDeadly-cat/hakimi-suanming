# B 阶段：正式完整恢复 CAS 运行时边界修复

日期：2026-08-28

## 结论

本切片关闭了正式完整恢复路径中的一个真实 fail-open：运行时若把已经验证的替换对象伪造成缺少 `expectedCurrentPayloadDigest`、显式传入 `undefined`，或通过 accessor/异常对象壳提供该字段，旧实现可能让仓储层把恢复解释为“无条件替换”，从而绕过 prepare/verify 之后的 current-payload CAS。

修复后，正式 `applyVerifiedFullBackup` 路径必须在任何仓储写入之前捕获一个精确的、只含自有可枚举 data property 的替换壳；CAS 摘要必须是原生 primitive string 且为小写 64 位 SHA-256。缺键、显式 `undefined`、accessor、额外键、自定义 prototype 与大写摘要都会 fail-closed。

这仍是 Schema 13 的 payload-digest CAS，不引入、推断或伪造 mutation epoch；`legacy-v13 / targetSchema 13 / migrationId null` 保持不变。

## 缺陷链

1. Worker/JavaScript 边界只能得到运行时对象，TypeScript 的 `VerifiedFullBackupReplacement` 类型不能证明必需字段真实存在。
2. 原 `applyVerifiedFullBackup` 直接读取调用方对象并把摘要交给仓储。
3. 仓储把“字段不存在”与“字段存在但值为 `undefined`”合并处理；后者可以让事务内摘要比较被跳过。
4. 因而，malformed Worker 回执或直接 JavaScript 调用可能把本应具备 CAS 的正式恢复路径退化为无条件替换。

## 三层修复

### backup 正式入口

- 新增 `captureVerifiedFullBackupReplacement`，在读取值之前检查精确自有键集合、普通或 null prototype、可枚举 data property，并拒绝 symbol、accessor 与额外键。
- 固定检查 incoming 结果壳、scope、迁移来源诊断与剩余缺口账；深层 payload 真值仍由生产仓储的 declarative capture/schema 负责。
- `expectedCurrentPayloadDigest` 必须是小写 SHA-256；`applyVerifiedFullBackup` 只消费捕获后的冻结值。
- malformed 替换对象统一以 `VERIFIED_REPLACEMENT_INVALID` 在仓储调用前失败。

### storage 最终防线

- 省略整个选项或确实没有 `expectedCurrentPayloadDigest` descriptor 时，保留其他受控调用方需要的既有无条件替换 API。
- 一旦该 descriptor 存在，其值必须是小写 SHA-256；显式 `undefined` 不再等同于缺省。
- accessor、非枚举属性、额外键和异常 prototype 继续失败。

### Worker 客户端边界

- `verified_ready.verified` 必须是自有可枚举 data property。
- 客户端复用同一运行时捕获器；malformed 回执映射为 `BACKUP_WORKER_RESULT_INVALID`，并终止 Worker。
- accessor 负例验证 getter 零调用，避免“为检查而执行不可信代码”。

## 证据边界

本切片建立的是本地工程合同与同进程、多 Dexie 连接的事务 CAS 证据。它不等于：

- 两个真实浏览器标签页、页面关闭/BFCache、Service Worker controller 接管或浏览器进程边界；
- 现实旧 v13 artifact、现实用户数据来源或迁移 provenance；
- Chrome/Edge 正式矩阵、PWA/Service Worker 真实运行、公开 HTTPS 主机；
- 部署、回滚、Release Evidence 实例、发布就绪或公开发布授权；
- 内容真值、专家真值、来源许可或法律判断。

因此 `two-tab`、现实旧 v13 artifact/data provenance、公开主机与部署回滚证据继续独立待办；`publicDeploymentAuthorized=false`、`expertClaimsAuthorized=false` 不变。
