# PR6 运行时派生证据生产桥接候选边界 v1（2026-08-28）

## 1. 结论

本 family `sw-ab-update-runtime-derived-evidence-producer-bridge` 只关闭一个离线工程缺口：它从 collector issuance 中已冻结的 decoded API transcript 重新构造完整 runtime-client-capture v1 文档，并以独立、不可覆盖的 bridge candidate root 发布该文档与 terminal publication manifest。

其机械状态固定为：

- `producerBridgeStatus = producer_bridge_present_mechanically_untrusted`；
- `evidenceClass = offline_untrusted_runtime_derived_evidence_producer_bridge_candidate`；
- `trustClass = untrusted_derived_evidence_producer_bridge_candidate`；
- `status = bridge_candidate_not_admitted`；
- `executionAdmission = closed_missing_selected_https_origin`；
- `strictGatePassed = false`；
- `runtimeAdmissionPassed = false`；
- `admissionPassed = false`；
- `usableForRuntimeEvidence = false`；
- `usableForCandidateAssembly = false`；
- `usableForAdmission = false`；
- `formalReleaseEvidenceReceipt = false`；
- CLI 固定退出码 `1`。

“mechanically untrusted”只表示本 family 确实发布了一个可复验的候选桥接包，不表示 producer、浏览器、传输、HTTPS 主机或现实运行已受信。

## 2. 固定输入、输出与来源

writer/loader 只接受同一 `bindingRoot` 下的绝对规范路径：既有 `issuanceRunRoot` 与独立 `bridgeRoot`。bridge root 不能复用已有目录，也不能位于 issuance root 内部或与输入、来源发生物理 alias。

成功的最终 bridge root 精确包含三份文件：

1. `01-derived-runtime-client-capture.json`；
2. `99-producer-bridge-publication.json`；
3. `100-producer-bridge-publication-commit.sha256`。

在 terminal commit 之前，pending root 的精确三文件集合则以 `.producer-bridge-publication-pending` 取代第 3 项。public loader 只接受成功集合中的 `100` commit marker，任何仍含 pending marker 的树都不是已提交候选。

合同来源固定为八个唯一 JSON 路径，顺序不可变：bridge policy/schema、runtime capture policy/schema、API transcript policy/schema、collector issuance policy/schema。治理分别冻结每一项的 raw SHA-256 与 canonical JSON SHA-256；相同语义但增加空白、BOM 或替换载体也属于来源漂移。

实现 family 另由七个 normalized source SHA-256 冻结：lib、Schema loader、writer、loader、独立 test fixture、test 与 verifier。fixture 独立于 `.test.mjs`，后续 consumer 不得通过导入测试模块借用样例或漏登记测试。

## 3. pending root → terminal gate 的精确真值

writer 在 `bridgeRoot` 的同一父目录创建 fresh staging directory，以排他方式写出、同步并核对 `01`、`99` 与 pending marker 的精确三文件集合。随后关闭 Windows 上不能跨目录 rename 持有的 pending marker handle，确认 final root 不存在，并把 staging directory rename 为 pending `bridgeRoot`。writer 在该 root 内再次核对 pending exact set、业务 JSON bytes、publication identity、终态 issuance 结果与合同来源端点。

terminal marker bytes 精确等于 64 位小写 `publicationDigest` 后接单个 LF。最终接受点是直接调用原生文件系统 `rename(pendingCommitPath, terminalCommitPath)`，把 `.producer-bridge-publication-pending` 在同一目录内改名为 `100-producer-bridge-publication-commit.sha256`。该 terminal rename 不经过 test dependency seam；完成后生产路径只返回预构的 committed result，并在 `finally` 中执行吞错 handle close，不再有可把成功提交改写成失败返回的 throwing work。

因此，成功根是 exact committed 3（`01`、`99`、`100`）；terminal rename 之前发生失败时，已物化的 final root 至多保持 exact pending 3（`01`、`99`、pending marker），public loader 因缺少 terminal marker 而拒绝。

因此以下窄陈述为 true：

- `issuanceFilesHeldAcrossPendingRootMaterialization`；
- `issuanceTerminalRereadCompletedBeforeTerminalCommit`；
- `bridgeOwnContractSourcesHeldAcrossTerminalCommit`；
- `allEightContractSourcesTerminalRereadCompletedBeforeTerminalCommit`；
- `completePendingSetVerifiedBeforeRootRename`；
- `sameParentPendingRootRenameCompleted`；
- `finalPendingSetVerifiedBeforeTerminalCommit`；
- `derivedDocumentProjectionAndDigestTripleMatched`；
- `terminalCommitMarkerBoundToPublicationDigest`；
- `terminalCommitMarkerPublishedLastBySameDirectoryRename`；
- `publicLoaderRequiresTerminalCommitMarker`；
- `businessOutputHandlesHeldAcrossTerminalCommit`；
- `postTerminalCommitThrowingWorkAbsent`。

但必须同时保持：

- `issuanceFilesHeldAcrossTerminalCommit = false`；
- `allEightContractSourcesHeldAcrossTerminalCommit = false`；
- `pendingCommitMarkerHandleHeldAcrossRename = false`；
- `allEvidenceFilesContinuouslyHeldAcrossCaptureAndPublication = false`；
- `crashDurabilityVerified = false`；
- `concurrentReaderSnapshotIsolationVerified = false`。

这里不能抽象宣称“原子发布已完全证明”。当前证据只证明一次具体进程内、同父目录、fresh staging、pending-root 复验与 terminal-marker rename 的文件系统路径；没有执行掉电/崩溃恢复、文件系统 durability、并发 reader snapshot isolation 或同权限攻击者隔离实验。

## 4. 完整派生文档的机械交叉绑定

bridge 不修改既有 transcript lib/loader，也不要求它们新增 export。bridge 自己持有九个 transcript 文件，复用现有 public validators 与 digest helpers 重建完整 runtime capture，并与独立 transcript loader 和 issuance loader 的结果交叉核对：

- release identity、capabilities、origin、A/B artifact identity；
- 精确八个 phase-major tuple、时间顺序、client/target continuity 与 challenge nonce；
- runtime observation digest 与完整 evidence digest；
- derived document、transcript `derivedEvidenceDigest`、issuance `derivedEvidenceDigest` 三方相等；
- transcript bundle ID/digest、issuance ID/receipt digest 与全部文件/source bindings；
- publication manifest 对 derived evidence 文件 bytes、路径、大小和 SHA-256 的绑定。

这是 decoded object projection 的确定性重构与发布，不补出 CDP wire bytes、DevTools WebSocket frames、可信浏览器对象、真实页面调用方或可信 collector provenance。

## 5. run/attempt 协调仍未完成

当前 candidate v1 没有现实 producer/coordinator；其生成入口仍是合成 fixture。collector issuance 又在自己的 begin 流程中独立生成 `runId` 与 `attemptId`。bridge-aware composition v2 已能在 injected/synthetic 输入中验证若干文件中的两个字符串相等，但这仍只能登记 `runAttemptIdentifiersMatched = true`，不能据此声称自然 producer 共享了同一次 attempt。

本轮仍必须登记：

```text
runAttemptCoordinationStatus = run_attempt_coordination_absent
runAttemptCoordinationVerified = false
candidateProducerBoundToIssuanceAttempt = false
```

这些字段现已由独立 composition v2 合同显式登记，但 coordinator 仍未实现，也未被塞入或伪装为 bridge v1 的通过项。关闭该缺口仍需要独立 run/attempt coordinator，或让现实 candidate producer 消费并绑定 issuance 创建的 opaque capability/marker；composition verifier 不得生成、选择或改写这些 ID。

## 6. legacy-v13 与 mutation epoch 边界

本 family 固定：

```text
channel = default-v13
dbGeneration = legacy-v13
targetSchema = 13
migrationId = null
mutationEpochCapability = absent_schema13
epoch = null
```

目录身份、文件 handle、mtime/ctime、digest、rename 或 publication digest 都不能补出 Schema 13 不存在的 mutation epoch。因此 `continuousMutationEpochVerified`、`samePermissionMutationExcluded`、`intervalMutationExcluded` 与 `abaExcluded` 全部为 false。

## 7. provenance、authority 与公开披露分账

policy/Schema 把 trusted immutable producer、caller page、runtime collector、browser object/binary/transport、real browser、real HTTPS host、external issuer、freshness、replay resistance 与 public redistribution 全部固定为 false。

authority 的十四项也全部为 false，包括默认 v13 receipt allowlist、正式 Release Evidence、provider/host/browser trust、deployment/release readiness、外部部署执行、公开部署/发布、内容真值、专家结论、权利法律结论与 schema promotion。

CLI 成功和失败都只输出关闭态 JSON 并以 `1` 退出；failure 只保留错误摘要，不把未验证原始 payload、raw client/target ID 或错误正文当成可公开证据。

## 8. 治理与正式闭包隔离

根 package 只允许两个 standalone 入口：

- `test:sw-ab-update-runtime-derived-evidence-producer-bridge`；
- `verify:sw-ab-update-runtime-derived-evidence-producer-bridge`。

不存在 writer/produce/capture package 入口，不允许 pre/post lifecycle、generic alias、Release Evidence aggregate alias、formal consumer import 或 CI `run`。Migration CI 仅把 policy、Schema 与本文列入 `pull_request.paths`；既有 `scripts/**` 负责脚本变更触发，但 workflow 不执行 bridge。

formal npm/lifecycle/workspace closure 会拒绝 direct、multihop、root lifecycle、跨 workspace `--prefix`/`--workspace`、`npm.cmd`、embedded shell/direct Node、`node -e`、拆分 dynamic import 与 cycle 注入。两个 standalone scripts 保持从正式默认 v13 receipt 图不可达，不改变精确 13 项 receipt allowlist。

## 9. 当前工程证据与非结论

bridge focused test 当前为 `26/26`。该测试使用真实磁盘、fresh staging、pending-root 与 terminal-marker rename、loader 终点复验和故障注入，覆盖 exact committed 3、exact pending 3、marker 的 `publicationDigest + LF` 编码、terminal issuance 漂移、terminal rename 失败、marker alias/link 与 native final rename 不可由 test seam 覆盖。但 issuance 输入仍来自工程 fixture；它证明合同实现和 fail-closed 行为，不是现实浏览器、HTTPS、Service Worker、公开主机、部署或回滚证据。

旧四链 composition v1 未修改，仍固定 `producerBridgeStatus = producer_bridge_absent`。bridge-aware composition v2 已作为独立、机械不受信任的 family 落盘，但其完整编排证据仍只来自 injected/synthetic fixture，且 `runAttemptCoordinationStatus = run_attempt_coordination_absent`。因此 bridge v1 与 composition v2 都不能提前宣称四链自然生产缺口已关闭。

本轮没有运行浏览器、网络、真实 HTTPS、公开主机、部署、全仓 typecheck 或默认 Web build，也没有取得内容真值、专家真值、权利法律判断、发布就绪或公开发布授权。`publicDeploymentAuthorized=false`、`expertClaimsAuthorized=false`。
