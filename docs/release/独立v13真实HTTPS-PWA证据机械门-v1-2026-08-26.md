# 独立 v13 真实 HTTPS / PWA 证据机械门 v1

## 当前结论

本文件定义的是后部署工程证据合同，不是部署记录。当前托管平台仍未选择，canonical origin 仍为空，没有当前正式候选产物、真实主机回执、Edge/Chrome 真实 PWA 运行时回执或外部部署授权。因此 policy 固定为：

- `status: contract_only_not_executed`
- `executionAdmission.status: closed_missing_https_origin`
- 全部 writer、parser、产物和 origin capability 为 `false`
- `externalDeploymentExecutionAuthorized=false`
- `publicDeploymentAuthorized=false`
- `publicReleaseAuthorized=false`

`closed_missing_https_origin` 是当前最早的不可越过阻断，不表示其他条件已经满足。policy 的 `blockingReasons` 同时冻结所有已知缺项。v1 合同没有通过路径；未来不得只改一个布尔值来打开准入，必须以新的 policy 版本完成独立复核。

## 与其他证据账分离

预部署 Release Evidence 回答“一份默认 v13 产物是否满足当前工程候选资格”。真实主机验证回答“公开 HTTPS origin 返回的字节、响应头、缓存、MIME、重定向和 Release Evidence 是否与候选完全相同”。真实 PWA 运行时回答“Edge 与 Chrome 是否在该 origin 上实际取得预期 Service Worker controller，并完成在线、离线冷启动和深路由”。

这三类事实不能互相替代：

- Release Evidence 不能证明任何真实部署已经发生。
- 单 URL、mocked fetch、本地 preview 或 `_headers` 文件一致性不能证明真实主机。
- Playwright 的本地 strict summary 只记录测试项目结果，不能证明远端 origin、controller script 字节或 CDP 网络事实。
- provider deployment ID 只能证明一次平台操作被记录，不能自证主机返回的字节或浏览器运行时。
- 以上全部工程证据都不能产生外部部署权限、公开部署授权或公开发布授权。

因此 deployed-PWA evidence 保持在默认 v13 的 13 项预部署回执之外，也不与后部署 A→B→A 回滚证据混为同一通过线。

## Schema-valid 不等于 verified

当前 Schema 只冻结证据词汇、字段形状、必需项和若干单字段常量。它不能单独证明跨文件或跨字段语义，例如：

- 五项 policy binding 的 role/path 是否逐项精确对应且摘要来自真实文件；
- 四个 artifact component 是否分别就是 `index.html`、`manifest.webmanifest`、`sw.js`、`_headers`；
- Edge/Chrome 的 project、channel、CDP product 是否形成精确 tuple；
- controller/active URL 是否等于同一 origin 的 `/sw.js`；
- 远端 SW、controller 执行源码与锁定 artifact SW 的 SHA-256 是否相等；
- controller build/descriptor 是否等于 artifact build/descriptor；
- case/revision 离线前后指纹是否相等；
- `status`、gates、claims、failures、evidence digest 是否由原始回执重算得到。

因此任何“Schema 可接受”的 JSON 都不是现实部署证据。v1 verifier 没有 evidence-instance 读取或通过路径；未来必须发布新的 policy 版本，并由纯离线语义 verifier 从彼此隔离的正式 Evidence、identity lock、真实 host/browser/provider 回执及原始 attachments 逐字节读取、重算和派生所有结果。不能把自述布尔值或摘要当成已验证事实。

## 固定发布身份

本合同只接受：

- channel：`default-v13`
- database generation：`legacy-v13`
- target schema：`13`
- migration id：`null`
- 浏览器项目与顺序：`msedge`、`chrome`
- host verification kind：`real-network`

Schema 13 不具备 mutation epoch 能力。本合同不会发明 epoch 0，也不会把真实 PWA 观察外推为 mutation epoch、内容真值、专家真值或权利结论。

## 未来证据实例必须绑定的四本账

### 1. 平台与 origin

实例必须绑定受审 platform profile 和无凭据、无路径、无 query、无 fragment 的 canonical HTTPS origin。`unselected`、`null`、HTTP、loopback、私网、保留域名、非默认端口或与 policy 不一致的 origin 都必须失败关闭。

### 2. 产物身份

实例必须逐字节绑定：

- Release Evidence JSON、SHA-256 与 evidence id；
- 仓外不可覆盖的 formal verification receipt；
- artifact identity lock 文件、lock digest 与 artifact-set digest；
- 完整 `legacy-v13 / 13 / null` descriptor；
- manifest digest、build version；
- `index.html`、`manifest.webmanifest`、`sw.js`、`_headers` 的路径、大小和 SHA-256。

任一摘要、版本、descriptor 或组件字节分叉都不得用“相近构建”或人工说明补齐。

### 3. 真实主机回执

未来 host receipt 只能来自真实网络入口，并必须绑定同一 platform、origin、Release Evidence 和 artifact set。它至少要证明网络完成、无意外重定向、完整路径矩阵、响应头、危险行为头缺失、cache、MIME、content encoding、远端逐字节身份和非公开控制文件隐藏。

现有真实主机验证器可作为未来生产端基础，但当前 CLI 没有不可覆盖的正式 host receipt 写出接线，也没有足以独立重算 DNS/TLS/HTTP 原始事实的可信 parser。因此 policy 中对应 writer/parser 继续为 `false`；不能把 stdout、mocked contract 或手工复制的 JSON 当成可信回执。

### 4. Edge / Chrome PWA 运行时回执

Edge 与 Chrome 必须各有且仅有一份无 retry、skip 或 flaky 的现实回执，并绑定：

- 实际 CDP 产品身份；
- runner 创建、运行前不存在且按浏览器隔离的全新持久资料目录，以及该目录绑定摘要；
- 同一 canonical origin、evidence id 与 artifact-set digest；
- 精确 `/sw.js` controller 与 active worker，二者均为 `activated`，同时不存在 waiting/installing worker；
- 远端 `sw.js` SHA-256、通过 CDP `Debugger.getScriptSource` 取得的 controller source SHA-256、build version 和完整 v13 descriptor；
- 在线根路由、离线 `/settings/data`、精确 `/cases/{caseId}/revisions/{revisionId}` 深路由，以及 `/help` 冷启动与 reload；
- Playwright `response.fromServiceWorker` 与 CDP 网络事件两条彼此独立的 Service Worker 来源观察；
- 深路由在离线前后的 case/revision 指纹一致；
- 意外外部网络请求为零；
- 原始 CDP/network attachment set 的摘要。

本地 Release Browser summary 没有这些字段，不能升级为真实 PWA receipt。当前也没有可信 writer/parser，相关 capability 保持 `false`。

## 授权分账

部署证据与部署授权是两件事：

- `externalDeploymentExecutionAuthorized` 表示是否允许执行会改变外部平台状态的 staging/production 部署；只能来自负责人明确决定。
- `publicDeploymentAuthorized` 表示是否允许候选对外可访问；不能由真实主机或浏览器技术通过自动产生。
- `publicReleaseAuthorized` 表示是否允许把产品作为公开发布版本对外宣称；它还依赖工程之外的内容、专家、权利和法律账。

Schema 将这三项以及 `releaseReady`、内容、专家和权利授权固定为 `false`。即使未来 deployed-PWA engineering gate 全部通过，本证据也只能说明一个被绑定的产物在一个被绑定的真实 origin 上满足已定义的技术观察。

## v1 失败关闭顺序

未来 verifier 接线前，v1 的唯一合法行为是：

1. 审计并编译 checked-in Schema。
2. 读取固定路径的 deployed-PWA policy、hosting policy 与 release decisions。
3. 精确确认当前 `unselected / null`、全部 capability false 和全部授权 false。
4. 以 `DEPLOYED_PWA_EXECUTION_ADMISSION_CLOSED` 停止。
5. 在停止前不得读取 evidence、artifact 或 receipt 输入，不得启动 formal verifier、网络、浏览器或部署操作，也不得写出声称通过的证据。

稳定失败账必须记录 artifact、formal verifier、network、browser 和 deployment 均未尝试，Schema 声明的 9 个工程 gate 全部为 false，12 个 claim 中只有 `engineeringEvidenceOnly=true`，其余技术、内容、专家、权利与授权 claim 全部为 false。只有完成固定 policy/hosting/decision 校验后抵达 admission stop，才能写 `executionAdmission=closed_missing_https_origin`；更早的参数、Schema 或 policy 失败必须写 `unverified`。

## 当前不成立的结论

这些 Schema、policy、工具与说明文件只建立合同和失败关闭边界。它们没有建立：

- 托管平台选择或 canonical HTTPS origin；
- 当前正式 Release Evidence 或可部署产物；
- 真实 DNS、TLS、HTTP 响应头或远端字节证据；
- Edge/Chrome 的真实 PWA、Service Worker controller 或离线证据；
- provider deployment operation 或回滚能力；
- 外部部署权限、发布就绪、公开部署或公开发布授权。

在平台、origin、当前正式产物、可信回执生产/解析和负责人授权均未取得前，阶段 B 只能登记为合同准备态。
