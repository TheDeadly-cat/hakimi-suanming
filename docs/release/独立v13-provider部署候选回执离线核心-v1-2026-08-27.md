# 独立 v13 provider 部署候选回执离线核心 v1（2026-08-27）

## 1. 结论与边界

本轮新增的是 provider-neutral、纯离线、合成 adapter 契约核心。它只能核对两份**已经存在且已经脱敏**的 raw JSON 文件与当前正式 default-v13 artifact 的内部一致性，输出固定为：

- `trustClass=untrusted_candidate`
- `admissionStatus=not_admitted`
- `networkObserved=false`，且 loader 返回的四项执行／公开授权仍全为 `false`
- `verificationKind=synthetic-offline-adapter-contract-existing-sanitized-files`
- `networkAttempted=false`
- `deploymentAttempted=false`
- `rollbackAttempted=false`

它没有选择 Cloudflare、Netlify 或其他正式 provider，没有 provider API schema、登录态、签名、可信 parser、真实部署、真实回滚、真实主机或浏览器证据。它也不能把工程证据外推为内容真值、专家真值、权利法律结论、发布就绪或公开发布授权。

本轮保持：

- `legacy-v13 / targetSchema 13 / migrationId null`
- checked hosting policy 的 `deploymentPlatform=unselected`
- checked hosting policy 的 `canonicalOrigin=null`
- `publicDeploymentAuthorized=false`
- `expertClaimsAuthorized=false`

## 3. 显式输入

环境必须显式提供：

- candidate provider 与 action（`deploy_candidate` 或 `restore_baseline`）；
- binding root；
- 独立 private raw root；
- raw action response 与 raw final readback 的绝对路径；
- 独立 output root；
- 当前正式 artifact root、artifact identity lock、Release Evidence id；
- candidate run id。

两份 raw 输入必须是 private raw root 的严格后代。private raw root、artifact root 与 output root 在词法路径和 realpath 上都必须双向不嵌套；artifact lock 必须位于 artifact/raw/output 之外。

`bindingRoot` 必须与运行时 `cwd` 指向同一个词法与物理目录。原因是 raw、receipt 与附件路径相对 `bindingRoot`，而 checked policy/identity-lock expectation 使用 `cwd`；v1 不允许混合两个路径基准。

## 4. 文件与身份防伪

首次写输出前，核心必须完成以下全部检查：

1. binding/raw/artifact 根目录的真实目录身份锁；路径各段不得经过 symlink/junction。
2. artifact tree 只允许单硬链接 regular files；使用现有 artifact identity verifier 核对完整 bytes、identity lock 与 Evidence id。
3. 使用 `loadDeployedHostExpectation` 对 `release-evidence.json`、其 SHA-256 sidecar、checked hosting policy bytes、artifact inventory、index/manifest/Service Worker locked bytes 建立 schema-validated expectation。
4. 对两份 raw 文件分别用 opened handle 读取；读前后复核 `dev/ino/birthtime/mtime/ctime/size/nlink/realpath`，要求 `nlink=1`，并要求两者的 path、realpath 和 inode 均不同。
5. raw JSON 必须是无 BOM 的 strict UTF-8、严格 JSON，AST 检查拒绝重复 key。
6. 解析前后再次读取两份 raw；再次验证 artifact identity、Release Evidence expectation、sidecar 与 policy binding，任何 rebound 或 bytes 漂移都失败关闭。

## 5. 脱敏与 synthetic adapter 契约

raw JSON 在进入 adapter 之前执行凭据扫描。key 先做 NFKC、大小写与 `-_.空白` 归一化，再拒绝 authorization/cookie/API key/token/password/secret/private key/access key/signing key/session key/credential 等精确或后缀形式；字符串拒绝 Bearer、Basic、带 userinfo 的 URL、query 或 fragment（含 percent-encoded key 与路由 fragment）中的凭据参数、JWT 形态与 PEM private key；数组键值对以及 `name`/`key`/`header`/`parameter` 等结构化名值表示也按凭据名拒绝。

字符串中的 `Authorization: ...`、`CF_API_TOKEN=...`、query parameter `access_token=...` 等带标签值也失败关闭；URL query key 会先 percent-decode，任意 URI scheme 的非空 userinfo 也拒绝。不采用“高熵字符串即密钥”的启发式，以免把 deployment id 误判为凭据。

adapter 的 action projection 与 final readback projection 必须分别明确：

- provider、account、project、environment、canonical origin；
- operation id；
- before/requested/result active deployment id；
- immutable deployment URL；
- provider terminal status 与严格时序；
- `credentialMaterialEmbedded=false`。

两份 projection 的 provider/account/project/environment/origin/operation/result-active/immutable-URL 必须精确一致。

`resultDerivation` 仅允许：

- `activated_requested`
- `provider_created_from_requested`
- `provider_assigned_new`

deploy 与 restore 分别执行非空、相异、derived-from 与 `sequenceEligible` 关系检查。该关系只证明 synthetic projection 自洽；它不证明 provider 实际执行过操作，更不证明 A→B→A 已经由真实主机 bytes 或浏览器观察闭合。

operation 的 `startedAt <= acceptedAt <= completedAt <= observedAt` 必须成立，且已经存在的 final readback 不得晚于离线采集开始时间。采集时间直接取当前进程系统时钟，不接受调用方注入时钟；这仍只是本地候选的时序边界，不是可信时间戳或 provider 签名。

## 6. 输出与写入顺序

schema 将 `attachments` 建模为五个固定、全部必需且禁止额外字段的 role 对象，避免数组中重复 role 或缺 role：

- `raw-action-response`
- `raw-final-readback`
- `synthetic-normalized-projection`
- `artifact-initial`
- `artifact-final`

2026-08-28 起，下述终态提交门取代 2026-08-27 的 receipt 发布后 tombstone 机制；`output-discard-required.json` 不再属于 provider candidate 的可接受磁盘格式。

所有附件在写前计算 size/SHA-256 并完成整份 receipt schema 校验。写入使用 exclusive temporary file + hard-link publish + 单链接复核，不覆盖既有文件；五个附件与 `provider-deployment-candidate-receipt.json` 发布后，再写入 `.provider-deployment-candidate-receipt-publication-pending`。隐藏 pending 文件固定为 65 bytes：raw receipt 的小写 SHA-256 加一个 LF。PREPARED 精确集合为五附件、receipt 与 pending marker 共七文件；writer 在该状态重新复验 raw action/readback、artifact/lock/Release Evidence/policy、各目录 identity，以及全部七文件的路径、物理身份、大小和摘要。

所有可能传播的来源、输出、Schema 和不可变返回值检查都在终态提交前完成。最后一个可能失败的步骤是同目录 native rename，把隐藏 pending marker 改名为 `provider-deployment-candidate-receipt-commit.sha256`；rename 后立即同步返回，不再执行回调、checkpoint、清理、I/O 或其他可抛错工作。COMMITTED 精确集合仍为七文件，即五附件、receipt 与 terminal marker；marker 的 `commitsReceiptSha256` 必须等于 raw receipt SHA-256。

receipt 文件名出现本身不是完成标志。终态 rename 前的异常或进程终止最多留下带 pending marker 的 PREPARED root，独立 loader 必须拒绝；CLI 的 `outputDiscardRequired=true` 只是要求调用方整体废弃该失败 root，不声称磁盘上存在持久 tombstone。rename 已完成但返回值未被调用方观察时，loader 只能证明当前 COMMITTED 端点机械有效，不能证明历史 writer 调用已被调用方观察为成功。该机制也没有证明目录 `fsync`、断电级持久性、目标名 no-replace 竞态排除、同权限连续 mutation、区间 mutation 或 ABA 排除。

writer 与独立 loader 的程序化返回值都从 JSON 文档另行克隆后递归冻结；调用方不能在 digest／integrity 结果已经给出后原地改写嵌套 claim、operation 或 attachment。磁盘包仍以独立 loader 的 opened-handle 复核为准，writer-only 返回不能替代该 mutation-epoch 证据。

candidate output 仍含已经脱敏的 provider raw bytes，以及 account/project/deployment 等标识，必须按 private/sensitive 工程证据保存，不得直接公开或作为可再分发材料。artifact expectation 附件不写出本机 identity-lock absolute realpath。

receipt 的 trusted-provider、provider-authenticated、deployment、rollback 与 public-release admission gate 全为 `false`；network/deployment/rollback/release-ready/public/content/expert/rights claims 全为 `false`。

## 7. 独立磁盘消费验证

独立 loader 不调用 writer 的私有路径、凭据或 projection 判断。它只读显式 `bindingRoot`、`outputRoot` 与固定 receipt path，并只接受五个固定附件、最终 receipt 和 terminal marker 的 COMMITTED 精确七文件集合；隐藏 pending marker、旧 tombstone、额外或缺失名字一律拒绝：

- 七个文件均以 opened handle 有界读取，前后复核目录身份、`lstat/fstat/realpath`、`dev/ino/birthtime/mtime/ctime/size/nlink=1`；物理 identity 必须两两不同，并在结束前全部重读、重枚举。
- 五附件与 receipt 共六份 JSON 均重新执行 strict UTF-8、无 BOM、重复 key 拒绝；receipt 重新通过封闭 Schema。65-byte terminal marker 必须精确等于 raw receipt SHA-256 加 LF。
- 独立重算 `receiptDigest`、`attachmentSetDigest`、固定 role→filename、每个附件 size/SHA-256/media type。
- raw copy 重新做凭据扫描；projection 重新验证 exact shape、action/readback、receipt scope/operation、时序及 deployment-ID derivation。
- initial/final artifact snapshot 重新验证 expectation digest、inventory digest、`_headers` 与 locked bytes、Evidence/lock/policy/default-v13 交叉绑定；托管 policy 以稳定 opened-handle 读取当前受检源文件，要求 raw hash、canonical hash、policy id 与完整 canonical policy 同时一致且仍关闭。

成功只表示 `candidateOutputIntegrityVerified=true`。v1 没有可信 provider parser 或 raw→projection source binding，因此结果必须同时保持：

- `rawProjectionDerivationVerified=false`
- `providerAuthenticatedReceiptVerified=false`
- `trustClass=untrusted_candidate`
- `admissionStatus=not_admitted`

静态目录消费不能证明历史 writer 返回已被调用方观察；只有 terminal marker、receipt 与五个附件同时通过独立 loader 的 exact-set、opened-handle、摘要、marker-to-receipt 和 Schema 重算，才能说明“当前七文件 COMMITTED 封包完整”，receipt 单独存在没有该含义。loader 仅重新打开当前托管 policy；它不重新打开原 private raw、Release Evidence 或 artifact lock，不能把其他三类 binding 冒充 current-source 复核。

## 8. 正式发布证据隔离

新测试没有加入 `test:release-evidence`，新 candidate receipt 没有加入 default-v13 正式 13 项 receipt allowlist，也没有修改任何正式 policy、schema、admission 或 rollback gate。未来只有在用户明确选择平台、核对当时官方 API schema、取得真实且脱敏的 raw 样本并另行审定可信 parser 后，才可新增具体 provider adapter；本文件不能作为该授权。

## 9. 两个候选包的 A→B→A 机械关系

序列 loader 同时接收 deploy 与 restore 两个已经存在的七文件 COMMITTED 候选包。在一个统一的只读文件系统验证窗口内，它持有两包十四个文件、当前托管 policy、单包 schema 与序列 schema 的稳定 opened handle；十七个受检文件必须在 `dev/ino/realpath` 上全局不同、`nlink=1`，两包根目录必须互不重叠。两包的 `terminal-commit` 固定绑定 `provider-deployment-candidate-receipt-commit.sha256`，并逐包复核 marker 与 raw receipt SHA-256。两包 initial 与 final 文档都直接通过该窗口持有的单包 schema validator。完成两包各自的独立 loader 校验和序列关系校验后，它再次调用单包 loader，并从原 handle 重读全部 bytes、重枚举目录、复核目录锁和文件元数据，任何替换、别名、硬链接、增删或变化都失败关闭；定向测试还在 initial sequence validation 后通过仅供受信任程序化测试、CLI／environment 无法注入的 checkpoint 改写临时包，确认 final pass 拒绝该 mid-window mutation。这里的“窗口”不是 Schema 13 中不存在的 application mutation epoch。

它只接受精确的合成关系：deploy 为 `deploy_candidate`，具有非空 baseline A 并得到不同的 B；restore 为 `restore_baseline`，其 before 为 B、requested 与 result 均为同一 A，`resultDerivation=activated_requested` 且 `derivedFromDeploymentId=null`。A′、no-op artifact、复用 operation id、复用／不合法 receipt id、复用 immutable URL、scope 或 adapter 漂移、以及 deploy final readback 不早于 restore start 均被拒绝。离线读取两个包的先后时间不用于冒充 provider 操作时序，因此反向离线采集顺序本身不会被误拒绝。

两个包的 candidate artifact identity 必须逐字段不同，且都继续绑定当前 `legacy-v13 / targetSchema 13 / migrationId null` policy。结果经封闭序列 schema 校验并递归冻结，固定保持 `trustClass=untrusted_candidate`、`admissionStatus=not_admitted`，网络、部署、回滚、PWA、浏览器、正式仓储、内容、专家、权利、发布就绪和公开发布等 attempts／gates／claims 全为 `false`。

序列 schema 已分别把 deploy／restore 的 `role` 与 `action` 固定为 const；但 schema 单独只能验证封闭形状和常量，不能证明跨字段相等／差异、时序、物理文件 identity 或摘要重算。那些结论只由 loader 的关系检查与 opened-handle epoch 建立；内存构造路径紧随构造执行的 package／sequence digest 重算仍只是 construction assertion。

持久化 writer 只允许在工作区 `tmp/` 私有证据范围内创建一个此前不存在、与两包双向不重叠的新 output root。它先完成一次完整 sequence composition；创建 output root 后，先以 `wx`、file sync 写入固定 `output-discard-required.json` sentinel，再以 `wx` 临时文件、file sync、hard-link no-replace、删除临时链接的顺序发布 `provider-deployment-candidate-sequence-receipt.json`。待验证阶段的精确目录集合因此是 sentinel 加 sequence 两个文件，而不是可被误认成完成态的单文件目录。sequence 随后被重开并绑定 single-link identity、size 与 SHA-256；发布后的 root `dev/ino/birthtime/realpath` 还必须与创建时 identity 完全相同。已有目录即使为空也拒绝；从 writer 自己成功创建 output root 起，任何后续失败均以 `OUTPUT_DISCARD_REQUIRED` 失败关闭，不得自动清理或复用。若失败发生在 output root 创建后、sentinel 成功同步前，结构化错误会明确 `discardSentinelArmed=false`，并不声称目录中已有完整 sentinel；此时 sequence 尚未发布，正式 exact-one verifier仍会拒绝空目录或残留的不完整文件。只有 `discardSentinelArmed=true` 才表示后续失败预期保留 sentinel。发布后取目录锁、受信 checkpoint 或独立待完成态验证失败时，sentinel 会保留；在测试平台确实允许持有文件时重命名目录的前提下，sentinel 会与 sequence 一同移动，使正式 exact-one verifier 继续拒绝该目录。CLI 只在这个结构化错误码上输出 `outputDiscardRequired=true`，并分别报告 `discardSentinelArmed` 与 `discardSentinelExpectedToRemain`；缺输入或拒绝既有目录时三者均为 `false`。

writer 先调用独立 verifier 的待完成态入口。该入口显式接收 sequence root／固定文件与 deploy／restore 两组 root／receipt 共七个路径，同时持有 sequence 与固定 sentinel handle，并要求 exact-two 输出集合；composer 完成 initial 与 final 验证后，在仍持有两包十四文件和三份当前源文件的 scoped verified consumer 中，对完整文档、固定 writer bytes、四级摘要、sequence id 与 17 个 identity 投影逐项复核。consumer 返回后 composer 再次验证两包、held schema、十七个 held files 和目录锁，外层最后再次重读 sequence、sentinel 与 exact-two root。全部通过后，writer 再复核自己的 held sequence、sentinel、root lock 与 exact-two 集合，并把删除 sentinel 作为最后一个可能失败的发布步骤；只有该 unlink 成功才返回 `sequenceCandidateWritten=true`。在已完成文件系统调用对普通进程终止保持可见的范围内，unlink 之前终止会留下 sentinel，unlink 已完成后则已有完整机械验证；这不等于断电或介质故障保证。该流程没有证明目录 fsync、断电级持久性、同权限连续 mutation 排除或 ABA 排除。

writer 的返回会诚实登记 `independentFinalOutputSetVerificationPassed=false` 与 `publicVerifierRequiredAfterWriterReturn=true`：它不在删除 sentinel 后再增加一个可能失败的异步复验窗口。调用方必须在 writer 返回后另行运行正式持久化 verifier；该入口只接受 exact-one `provider-deployment-candidate-sequence-receipt.json`，任何残留 sentinel、临时文件或额外文件都会失败关闭。正式 verifier 成功只建立其持有的 18 文件重叠验证窗口下的当前机械重组一致性，不是跨进程连续 mutation 证明。`onUnifiedEpochCheckpoint` 仍仅用于受信任 mutation 测试；`onVerifiedSequenceConsumer` 只供同进程受信任的独立 verifier；writer 的 `onOutputRootCreatedCheckpoint` 与 `onPublishedSequenceCheckpoint` 分别只用于 sentinel 布置前和 sequence 发布后的失败边界测试。四者均不能由 CLI、environment 或候选文件注入。

2026-08-28 起，sequence CLI 还把候选发布与结果呈现分账。writer 已返回后，`candidatePublicationCompleted=true`、`sequenceCandidateWritten=true` 的磁盘事实不会再因 JSON 序列化、stdout 同步异常、异步 rejection 或 stream error 被倒写为 false；呈现失败会以非零退出并登记 `stdoutPresentationCompleted=false`、`outputDiscardRequired=false`、`publicVerifierRequiredAfterWriterReturn=true`、`independentFinalOutputSetVerificationPassed=false`。该账只纠正调用方处置语义，不把 writer 返回替代为公开 verifier 通过。

同日新增的生产贯通用例不再以手工写 terminal marker 的 fixture 冒充兼容性：它分别调用 production `collectProviderDeploymentCandidate` 生成 candidate-B deploy 与 baseline-A restore 两个 COMMITTED exact-7 包，逐包验证 terminal path、65-byte bytes、marker SHA-256、`commitsReceiptSha256`、pending 缺失、single-link 与两 marker 物理身份独立，再依次通过 sequence loader、sequence writer 和 persisted verifier。该用例仍显式要求 `not_admitted`，网络／部署／回滚 attempts 与 execution／rollback／public deployment／public release authorization 全为 false。

sequence 持久化文档现在还把 deploy／restore 各自的 `fixedFiles["terminal-commit"]` 收紧为显式四字段承诺：`path`、固定 `size=65`、marker 自身 `sha256` 与 `commitsReceiptSha256`。持久化 verifier 会在摘要闭合前独立复核这四项，并直接重算 `sha256(rawReceiptSha256 + LF)`；在调用方重算全部 digest 后仍拒绝缺字段、错误 path、错误 marker/receipt commitment、错误长度或额外 identity 字段。`dev`、`ino`、`realPath` 等文件系统 identity 不得写入整份文档，17 个 held identity 只存在于同一验证窗口中；中央治理同时冻结该 sequence Schema 的 canonical SHA-256 与精确四字段结构。

rollback/provider sequence composition 现在消费 persisted verifier 的最终输出边界，并把 deploy／restore 两个 terminal gate 原样投影进自身 Schema 与 composition digest。它要求 `pending=false`、当前重组与重叠窗口为 true、最终输出集合已验证，以及 attempts／authorization 的精确关闭集合；任一 terminal marker 或 receipt commitment 漂移都会失败关闭。该组合仍固定 `not_admitted`，不能把序列机械一致性提升成真实部署、回滚或公开授权。

持久化成功也只是 `externalSequenceCandidateIntegrityVerified=true`、`currentRecompositionMatched=true` 与 `overlappingFilesystemEpochVerified=true`；文档及 verifier wrapper 仍固定 `untrusted_candidate / not_admitted`，所有权威 attempts／admission／claims／authorization 为 `false`。它不是正式 Release Evidence verification receipt，也没有进入默认 v13 allowlist 或正式治理聚合。

这项机械关系不能证明初始 A 的 artifact identity，不能证明 deployment id 与 artifact bytes 的 provider 侧关联，不能证明 raw→projection 推导、provider 身份或签名，也不能证明真实 HTTPS 主机、真实部署／回滚、Service Worker、跨标签页、Chrome／Edge、正式仓储或 schema-13 mutation epoch。正式 rollback verifier 与 Release Evidence 继续完全独立；序列候选不得进入其 allowlist、测试聚合或准入结论。
