# 运限查询专家审核协议 v0.1

## 1. 目的与边界

本协议用于把 P1-04 的“指定 UTC 瞬时点运限筛选”从工程回归推进到可由现实专家审核的版本化证据链。审核对象是：给定出生输入、确切 Revision、规则摘要、人工顺逆和 UTC 瞬时点后，某一运限轨道的状态、干支、十神、半开区间，以及该稳定事实是否满足严格 `ResearchQuery v1` 条件。

现有高级查询真值表仍是工程证据：它的 Revision 和运限节点由本项目自己的计算链生成，不能独立证明命理结果正确。内容摘要只能证明文件未变化，不能证明复核人身份、来源真实性或结论正确。

当前 `TransitSnapshot.manifest.goldCaseCount=0`、`releaseGatePassed=false` 保持不变。导出、载入或预检任何审核文件，都不得自动提高金标数或打开发布门。

## 2. 三层证据

### 2.1 内容寻址审核包

审核包格式为 `hakimi-transit-query-review-bundle@1.0.0`，至少绑定：

- candidate-only fixture 与数据集版本；
- 合成出生输入、确切 Case/Revision、规则配置和运限规则摘要；
- `ResearchQuery v1`、`queryDigest`、`dataEpoch` 和可复算的查询证据；
- transit timeline、algorithm、引擎和上游版本；
- 每条候选的稳定领域期望、覆盖单元和 `candidateDigest`；
- fixture、dataset、候选和外层审核包多级 SHA-256。

审核包不得包含真实用户案例。专家期望不包含相关度、界面排序、`matchReasons` 或其他软件内部投影；这些继续由工程测试负责。

### 2.2 两份独立复核

独立复核格式为 `hakimi-transit-query-independent-review@1.0.0`。同一候选必须由两位不同现实身份分别提交复核。每份复核绑定复核人实际看到的审核包、fixture、数据集、候选、完整快照、Revision 结果、查询、数据世代、工程结果、规则、运限规则、时间轴和算法摘要，并记录复核时间、结论、完整期望、来源和独立理由。

两位复核人不得共享同一规范 reviewer ID 或同一离线身份记录摘要。离线身份记录摘要只是提交给维护者核验的内容寻址引用，不等于本应用已经验证身份或数字签名。

最低来源要求：

- 至少一项历书或天文历表谱系，用于校核节气、日期、时辰或区间边界；
- 至少一项经典版本、可追踪方法说明或顾问书面材料谱系，用于校核顺逆、十神及运限口径；
- 来源必须记录版本、作者或发布者、定位、访问/查阅时间和冻结材料 SHA-256；
- `lineageDigest` 必须由来源类型、作品标题、发布者/保管者、版本和材料摘要重新计算，不能通过更换显示名称、URL 或 `lineageId` 制造新谱系。

### 2.3 最终裁决

最终裁决格式为 `hakimi-transit-query-adjudication@1.0.0`。它必须引用两份去重并规范排序的独立复核摘要，绑定同一个审核包、候选和全部计算身份，并明确引用两份审核中的冻结来源。裁决人 ID 与离线身份记录摘要必须不同于两位复核人。裁决只能是：

- `accept_expected`：接受候选期望，不能同时偷改字段；
- `replace_expected`：给出实际不同且完整的替代期望；
- `reject_candidate`：拒绝候选，生效期望必须为空。

裁决还需记录裁决人、时间、理由和被替代的旧裁决摘要。预检通过仅表示结构、内容摘要、绑定关系、来源谱系和时间链满足协议；维护者仍须线下核验真实身份与材料，并通过代码审查把裁决纳入新的版本化 fixture。

最终生效期望必须逐字段等于至少一份独立复核已经审核过的完整意见；裁决人若提出第三种结果，必须退回重新审核。v1 的无状态网页预检不能安全验证替代链，因此任何非空 `supersedesDecisionDigest` 都会失败关闭，须由追加式可信账本处理。

## 3. 首批候选覆盖

首批工程候选使用纯合成出生资料，隔离关系规则和用户事件，覆盖六条运限轨道及失败关闭状态：

| 轨道 | 首批边界 |
| --- | --- |
| 流年 | 立春前一秒、立春当秒 |
| 流月 | 立春前/当秒、普通交节前/当秒 |
| 流日 | 23:00 换日前一秒、当秒 |
| 流时 | 23:00 前/当秒、01:00 前/当秒 |
| 小运 | 男/女出生瞬时点、出生前不适用 |
| 大运 | 交运前不适用、未知性别无方向不支持、未知性别人工顺行 |

这 18 条只构成第一批可审核工程候选。后续发布数据集仍须补：六轨起点前 1ms/当刻/endExclusive、多轨 AND、`latest/any` 修订隔离、阴阳年干 × 男女四象限、人工逆行、DST gap/overlap、旧规则降级、节点事件正反例及稳定多结果排序。

## 4. 计数分层

必须分别报告：

- P1-01 运限领域事实 verified 数；
- P1-04 查询筛选裁决 verified 数；
- 当前引擎工程候选数；
- 已完成协议预检但尚未纳入 fixture 的裁决数。

查询布尔逻辑通过不能提高 P1-01 运限事实金标数；反过来，某个运限节点经裁决，也不能自动证明所有查询组合正确。

## 5. 失败关闭与安全门

审核文件在进入 Zod 前必须限制 UTF-8 字节、深度、节点数、键名和文本长度，并拒绝原型污染键、访问器、null/自定义原型、循环、共享对象引用、稀疏数组、未知嵌套字段及非 JSON 值。审核时间只接受规范 UTC。预检必须重新生成当前 candidate-only 数据并复算多级摘要；即使攻击者把篡改后的候选包完整重摘要为内部自洽，也要因当前 fixture、数据集、候选或审核包绑定不一致而拒绝。

SHA-256 不能独立识别“攻击者改写审核意见、身份字段和来源后再计算新摘要”。在 reviewer 公钥未登记、detached signature 未验证且首次提交摘要未进入可信追加账本前，独立审核与最终裁决预检都必须明确返回 `identityVerified=false`、`sourceAuthenticityVerified=false`、`eligibleForFixtureIntegration=false` 和 `countsAsVerifiedGold=false`。这不是实现遗漏，而是避免把普通摘要误称为身份认证的发布硬边界。

以下情况均不能计入金标：同一复核人重复、同一来源谱系伪装、旧审核包/旧候选重放、未来时间、时间顺序错误、软件实现之间的一致性、`unsupported` 冒充正证据，以及只填写姓名而没有独立意见和来源的“形式双审”。

## 6. 本地未核验审核收件箱

### 6.1 内容识别与导入边界

收件箱只接受并按 JSON 正文中的 `format` 识别以下三种工件，不使用文件名、扩展名、上传按钮或人工指定的 A/B 槽位推断类型：

- `hakimi-transit-query-review-bundle@1.0.0`；
- `hakimi-transit-query-independent-review@1.0.0`；
- `hakimi-transit-query-adjudication@1.0.0`。

导入先对原始文件执行 2 MiB 总上限和严格 UTF-8 解码；非法 UTF-8、超限文件不会落库。随后复用本协议的安全 JSON 检查、严格 Schema 与 envelope payload 摘要校验；其中独立审核和最终裁决仍受各自 512 KiB 协议上限约束，候选审核包上限仍为 2 MiB。未知 `format`、未知字段、危险对象结构、非规范时间或 payload 与 `digest` 不一致，都会在持久化前失败关闭。

只有上述内容检查通过的原始字节才会作为无业务链接的本地 Attachment 保存，媒体类型固定为 `application/json`，并使用精确标记：

```text
哈基米运限审核收件箱 · 本地未核验 · v1
```

这里保存的是导入文件的原始 UTF-8 字节，不是重新序列化或删减后的 JSON。该 Attachment 属于现有完整备份的附件分区；备份、预检和恢复继续校验字节长度、附件内容摘要及完整备份各层摘要。因此完整备份可以携带收件箱原件，但“进入备份”只表示本地文件可恢复，不表示其身份、来源或结论获得认可。

### 6.2 每次读取重新预检

收件箱只持久化原始字节和 Attachment 元数据，不持久化 `bundle_current`、“审核通过”或“裁决通过”等派生结论。每次进入页面或主动刷新时，都必须重新：

1. 按 Attachment 记录中的原始字节摘要读取并核对字节长度；
2. 严格解码 UTF-8，再按正文 `format` 识别工件并重算 envelope payload 摘要；
3. 对每个确切审核包重新生成当前 18 条 candidate-only 数据并建立仅在本次运行内有效、不可序列化恢复的预检上下文；
4. 在该上下文中重新预检所关联的独立审核和最终裁决；
5. 重新派生等待依赖、结构预检失败或“结构预检通过但仍未核验”等页面状态。

应用更新导致 fixture、数据集、候选、算法、时间轴或规则绑定变化时，旧工件会在下一次刷新自然落入相应失败状态，不得继续显示缓存的绿色结论。

### 6.3 两种摘要不得混称

Attachment 的 `contentHash` 是对导入文件**原始字节**计算的 SHA-256，用于发现本地字节缺失、截断或变化；空白、缩进、换行或 BOM 不同都可能产生不同的原始字节摘要。

envelope 的 `digest` 是对严格解析后的声明式 `payload` 计算的规范 SHA-256，用于标识协议内容并建立跨工件依赖；它不等于原始文件字节摘要。两个原始字节不同的文件可能声明同一个 envelope digest，反之任何 payload 变化都必须使 envelope digest 失配或产生新的内容身份。两种摘要都只提供内容完整性，均不是人员数字签名、来源真实性证明或首次提交账本。

### 6.4 依赖关联与乱序到达

关联只使用工件正文中的精确内容身份：

- 审核批次以候选审核包自己的 `digest` 为 `reviewBundleDigest`；
- 独立审核必须按其 `reviewBundleDigest` 绑定确切审核包，并同时按 `candidateId + candidateDigest` 绑定该包内确切候选；
- 最终裁决除绑定同一 `reviewBundleDigest + candidateDigest` 外，还必须按规范排序的 `independentReviewDigests` 精确取得它声明的两份独立审核；不得从同一候选的多份审核中任意挑选两份或按 A/B 上传顺序代替摘要关联。

收件箱允许子工件先到：独立审核可以先于审核包导入，裁决也可以先于审核包或其两份审核导入。此时原件保持在本地并显示“等待审核包”或“等待独立审核”；依赖到齐后的下一次刷新才尝试完整预检。相同候选 ID、相同 fixture 版本或相似文件名都不能替代确切摘要关系，也不能把不同生成时间、不同 `reviewBundleDigest` 的批次自动合并。

### 6.5 固定未核验边界

收件箱中的“结构预检通过”只表示本次刷新重跑了 JSON、安全边界、摘要、当前候选、来源谱系、时间顺序和工件依赖检查。无论保存、备份、恢复、刷新或全部 18 个候选都出现结构通过，投影仍必须固定：

- `evidenceBoundary="local_unverified"`；
- `identityVerified=false`；
- `sourceAuthenticityVerified=false`；
- `eligibleForFixtureIntegration=false`；
- `countsAsVerifiedGold=false`；
- `verifiedTransitFactsDelta=0`；
- `verifiedQueryAdjudicationsDelta=0`。

收件箱不得写入版本化 fixture、不得改变 P1-01/P1-04 金标计数，也不得把 reviewer 显示名、离线身份记录摘要、Attachment 内容摘要或 envelope digest 称为“专家已验证”。

## 7. 当前交付状态

设置页原有五步会话入口仍可按需导出/载入候选审核包、分别预检独立审核 A 与 B、预检最终裁决；其页面会话结果本身不写入 SavedView 或版本化 fixture。新增的本地未核验审核收件箱使用统一工件入口，把内容检查通过的原始 JSON 字节保存到 Attachment 分区并纳入完整备份；读取时再按本节协议重新派生状态。最终裁决预检继续交叉检查两个 reviewer 身份引用、来源材料谱系、候选绑定、意见支持关系和时间顺序。

真实专家身份、材料核验、可信签名/提交账本和 fixture 纳入尚未发生，因此当前仍应显示人工验证金标为 0，P1-04 保持“部分通过”。
