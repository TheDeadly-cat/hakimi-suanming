# 八字规则配置与金标准计划 v0.1

> 状态：可开发草案；用户尚未确认的取值标为“工作默认”  
> 适用：[产品方向更新 v0.2：专业研究版](./产品方向更新-v0.2-专业研究版.md)  
> 原则：先保证同一输入、同一规则、同一版本能够复算，再讨论解释观点。

## 1. 三类内容必须分开

| 层 | 含义 | 验收方式 |
| --- | --- | --- |
| 历法事实层 | 时间、时区、节气时刻、公农历转换、四柱等确定性计算 | 金标准、差分、边界与不变量测试 |
| 规则配置层 | 换年、换月、换日、真太阳时、顺逆、起运等可争议选择 | 每个配置有来源、版本、固定样例，可并列复算 |
| 解释观点层 | 旺衰、格局、调候、用神、神煞取法与文本解读 | 标注流派/作者/规则版本，不伪装成历法事实 |

AI 不进入前两层，也不能覆盖它们的结果。

## 2. `rule_profile` 数据契约

每张命盘必须绑定不可变的规则快照，而不是只保存一个可能被后来修改的配置名称。

```yaml
profile_id: ziping-working-default
profile_version: 0.1.0
status: working_default       # working_default | verified | experimental
label: 传统子平工作默认
source_refs: []               # 书名/章节/版本/顾问决定记录

calendar:
  year_boundary: lichun_exact # lichun_exact | lunar_new_year
  month_boundary: jie_exact   # jie_exact | civil_day
  day_boundary: zi_start_23   # zi_start_23 | midnight | split_zi
  zi_hour_day_stem_basis: after_day_change
  hour_basis: civil_time      # civil_time | mean_solar | apparent_solar
  timezone_source: iana
  dst_ambiguity: require_user # require_user | earlier | later
  location_precision: city    # city | coordinates

solar_time:
  enabled: false
  show_comparison: true
  longitude_source: location
  equation_of_time_model: null

luck_cycle:
  direction_rule: year_stem_yinyang_and_gender
  unknown_value_policy: require_manual_direction
  anchor: directional_jie
  start_age_method: three_days_one_year_exact_duration
  rounding: retain_duration

layers:
  hidden_stems: true
  ten_gods: true
  nayin: true
  void_branches: true
  twelve_growth: true
  stem_branch_relations: true
  shensha: false

interpretation:
  strength_rule_pack: null
  structure_rule_pack: null
  climate_rule_pack: null
  useful_god_rule_pack: null
```

字段枚举在代码中版本化；未知枚举必须拒绝导入，不能静默回退。

## 3. 当前工作默认值

这些值用于让原型和测试可以继续，不代表项目已经替研究者判定某一派正确。

| 决策点 | 工作默认 | 产品行为 |
| --- | --- | --- |
| 年柱界线 | 精确立春时刻 | 同时允许切换农历正月初一；边界前后显示差异 |
| 月柱界线 | 十二节的精确交接时刻 | 不用公历每月 1 日；显示采用的节气时刻 |
| 日柱换日 | 当地民用时 23:00 子初换日 | 同时提供 00:00 换日与早晚子时分流配置；子时附近主动提示 |
| 时辰基准 | 地点对应的民用时间 | 真太阳时默认不静默启用，先并列展示修正前后时间和可能影响 |
| DST 重复/缺失时刻 | 必须由用户确认 | 提供较早/较晚偏移或纠正时间，不自行猜测 |
| 大运顺逆 | 年干阴阳与性别组合规则 | 允许替代规则包；显示顺逆推导过程 |
| 起运 | 顺逆方向取相邻节，按实际时长折算“三日一岁” | 保留未舍入时长并展示折算过程；其他算法可切换 |
| 神煞 | 默认关闭 | 研究视图可按规则包开启，每项显示来源 |
| 旺衰/格局/调候/用神 | 无全局默认结论 | 只有选择具体解释规则包后才输出，允许并列比较 |

在用户或顾问确认之前，界面必须显示“工作默认”，导出文件也保留该状态。

## 4. 时间输入与不确定性

### 4.1 标准化输入

```text
用户输入的日期时间
+ 输入历法与闰月标记
+ IANA 时区
+ DST 偏移选择
+ 地点/经纬度精度
+ 时间准确度
→ 标准化瞬时点与输入快照
```

姓名、备注和标签不参与计算。计算服务只接收必要的时间、地点和规则配置。

### 4.2 准确度等级

| 等级 | 定义 | 行为 |
| --- | --- | --- |
| `exact_second` | 已知到秒 | 用于节气、换日等边界研究；原样保存秒，不降级为整分钟 |
| `exact_minute` | 已知到分钟 | 正常计算，并保留来源说明 |
| `hour_range` | 只知道一个时辰或时间段 | 标注范围；边界跨柱时生成候选盘 |
| `unknown_hour` | 不知道时辰 | 生成不依赖时柱的主视图，可选 12 时辰对照 |
| `date_only` | 只知道日期 | 不输出依赖时柱或精确起运时刻的确定性结论 |

任何降级都不能用 AI 猜出一个“最可能时辰”再冒充用户输入。

## 5. 每张命盘必须保存的复算元数据

- 原始输入及其历法类型；
- 标准化民用时间、UTC 瞬时点、IANA 时区与实际偏移；
- 地点精度、经纬度来源和 DST 选择；
- 真太阳时修正前后值与采用状态；
- `engine_name`、精确版本、上游提交和完整性哈希；
- `tzdb_version`；
- 完整 `rule_profile` 快照及其哈希；
- `chart_schema_version`；
- 计算时间、应用版本与迁移记录；
- 不确定字段、警告和候选盘关联。

只保存最终四柱而不保存这些元数据，不能算可复现。

## 6. 金标准案例：首发 360 例

| 分类 | 数量 | 必须覆盖 |
| --- | ---: | --- |
| 普通稳定日期 | 30 | 不靠近边界；覆盖不同年代、季节、干支、昼夜与地点 |
| 公农历转换 | 24 | 大小月、闰月、春节前后与双向往返 |
| 节气天文时刻 | 36 | 不同年代和时区；节气前一秒、当刻、后一秒 |
| 时区、DST 与日期线 | 30 | 历史偏移、半/四十五分钟区、重复/缺失时刻、UTC±14 |
| 界年规则 | 18 | 立春与春节不重合区间、精确边界和配置差异 |
| 界月规则 | 36 | 十二节各取前、当、后三个时刻 |
| 换日与时辰 | 48 | 23:00、00:00、十二时辰边界、早晚子时和包含规则 |
| 真太阳时 | 30 | 极端经度、时区边缘、均时差正负峰值、校正后跨时辰/日 |
| 顺逆排运 | 18 | 阴阳年干、出生性别、手动覆盖和未知值 |
| 起运与大运切换 | 36 | 顺逆、临近节令、秒级差值、折算与交运时刻 |
| 未知、模糊与非法输入 | 18 | 未知时辰、时间范围、缺时区/坐标、DST 异常时间 |
| 派生关系与神煞 | 36 | 命中/不命中、模块开关、不同规则集与来源差异 |
| **合计** | **360** | 每例有期望结果、来源、复核人和适用规则版本；预计断言超过 900 条 |

金标准不能只从一个商业 App 截图抄录。每例的证据优先级：

1. 经确认的权威历书、天文/时区资料与明确公式；
2. 命理顾问对具体规则包的书面判定；
3. 两个以上独立实现的差分结果作为线索；
4. 商业 App 只用于发现分歧，不作为最终真值。

## 7. 随机差分与不变量测试

### 7.1 差分集合

- 每次发布在强校验年份范围内生成至少 20,000 个分层随机瞬时点，夜间任务可扩大到 100,000 例；
- 覆盖多个 IANA 时区、DST、半小时时区和日期线；
- 比较 `lunar-typescript`、`lunar-java`、`tianji` 等候选实现能共同表达的基础字段；
- 同源移植库的一致不能算独立证据；
- 每个分歧进入分类队列：输入标准化、历法边界、规则不同、库缺陷或测试错误。

### 7.2 不变量

- 公历 → 农历 → 公历在适用范围内往返一致；
- 同一 UTC 瞬时点换时区再换回，瞬时点不变；
- 同一输入、规则快照和引擎版本的结果哈希稳定；
- 切换展示语言、主题和视图层级不改变计算结果；
- 关闭神煞不改变四柱与基础关系；
- AI 开关和网络状态不改变确定性排盘；
- 导出再导入后，结果、元数据、规则快照和关联笔记保持一致。

## 8. 规则包验收

每个新增规则包必须同时提交：

- 唯一 ID、语义版本和兼容的 Schema 范围；
- 适用流派、作者/顾问和来源引用；
- 全部参数及默认值；
- 至少 1 个正例、1 个反例和所有边界例；
- 与已有规则包的已知差异；
- 输出字段及“不适用/无法判断”行为；
- 变更日志和升级迁移说明；
- 自动测试与人工复核记录。

导入第三方规则包时先做静态 Schema 校验。v1 不执行任意 JavaScript 规则代码，避免规则包成为远程代码执行入口。

## 9. 发布门

只有同时满足以下条件，排盘模块才能标为 v1 稳定：

- 360 个金标准全部通过；
- 随机差分的每个未一致结果都有分类和处置记录；
- 所有时间、节气、DST 和换日边界测试通过；
- 规则配置、结果与导出文件均能显示版本和工作/验证状态；
- 同一命盘可以在新会话和离线状态复算出同一结果哈希；
- 引擎升级前后差异报告经过复核；
- 未经选择的解释规则不会生成旺衰、格局、调候或用神结论。

## 10. 仍待用户确认

1. 是否接受“传统子平工作默认 + 其他规则并列”的结构；
2. 日柱默认采用 00:00、23:00，还是早晚子时分流；
3. 真太阳时是否保持“默认不静默采用、始终显示对照”；
4. 强校验年份先定为 1900～2100，还是首版必须扩展到古代命例；
5. 谁负责对规则来源与争议样例做最终签字。
