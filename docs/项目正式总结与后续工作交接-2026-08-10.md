> 日期：2026-08-10  
> 性质：当前工作区的正式交接基线  
> 适用范围：产品方向、已实现工程、验证证据、发布边界与后续路线

## 1. 执行结论

哈基米八字研究台已经不是一个简单的“算命页面”样机，而是一套规模较完整的本地优先八字研究工作台工程。当前代码已覆盖排盘、校时、未知时辰候选、不可变修订、六层运限、事件、专业检索、多盘对照、本地知识与引用、来源权利审计、导入导出、十六分区备份、离线 PWA、升级回滚和诊断帮助等主要研究流程。

但项目仍不能称为 Web v1，更不能称为 Android App 已完成。主要原因不是“页面数量不够”，而是三个发布级闭环尚未完成：

1. **专业真值闭环未完成**：360 个金标准案例目前为 60 个候选、0 个现实核验通过，仍缺两位独立复核人、第三方裁决、规则顾问签字和更完整的边界覆盖。
2. **Schema 16 发布闭环未完成**：安全的 mutation epoch/CAS 快速启动已经实现，并在固定 Edge 的第二次 clean boot 达到 1.115 秒，但默认发布仍为 v13；v13→v16 多标签自然升级竞态、完整故障矩阵、Chrome 和 Android 复验仍是红灯。
3. **跨平台发布闭环未完成**：Firefox、固定 Android Chrome/WebView、真实安装窗口、人工读屏、原生文件/分享/返回/打印及 Web↔APK 数据往返尚未验收。

因此当前最准确的项目状态是：

> **专业研究工具的主体工程已经形成，当前处于 Web/PWA 发布收敛与专业真值建设阶段；Schema 16 是隔离发布候选，Android 尚未进入产品壳阶段。**

## 2. 已锁定的产品方向

### 2.1 一句话定位

**哈基米八字研究台是一款可离线使用、规则可追溯、支持多盘对照与案例记录的专业八字研究工作台。**

### 2.2 目标用户与平台

| 项目 | 当前决定 |
| --- | --- |
| 核心用户 | 所有学习和研究八字命理的人，以简体中文使用者为主 |
| 核心流派 | 传统子平作为首个工作基线，其他流派以后作为独立规则包 |
| 首发形态 | 响应式 Web/PWA；桌面研究效率优先，手机浏览器功能完整 |
| 移动顺序 | Web v1 通过后，以同一 TypeScript 内核封装 Android APK |
| 暂缓范围 | iOS、付费、会员、广告、积分、社区、真人大师市场、云账号 |
| AI 定位 | 可插拔研究助手，不参与确定性排盘裁决；当前尚无 Provider |
| 使用边界 | 首版公开使用建议 18+；不输出医疗、投资等高风险决定 |

### 2.3 产品气质与原创边界

视觉方向为原创的现代东方研究工具：温暖纸白、墨色、玉青为主，小面积朱砂用于时间和差异提示；强调清醒、温暖、专业和好奇。

可以学习问真八字处理复杂信息的通用机制，但不得复制其品牌、图标、文案、截图、像素布局、专有数据、课程或备份格式。项目不做黑金、金龙、罗盘、八卦阵和仿古卷轴式的老派视觉。

## 3. v1 的完整研究闭环

```text
出生信息录入与校时
  → 可复现排盘
  → 规则包与参数切换
  → 大运、小运、流年、流月、流日、流时
  → 案例标注、事件验证与多盘对照
  → 典籍、规则与来源依据溯源
  → 本地保存、检索、备份与导出
```

“功能做全”的含义是把上述闭环做可靠，不是首版承诺所有门派、全部古籍、全部历史年份或所有解释观点。

## 4. 当前已经实现的主体能力

### 4.1 排盘、时间与复现

- 公历、农历和闰月输入及转换；
- 地点、经纬度、IANA 时区和 DST 语义；
- 民用时间与真太阳时并列，不静默改写原输入；
- 未知时辰以 13 个代表性探针对照，不冒充出生时刻推断；
- 四柱、藏干、十神、五行、纳音、空亡、十二长生和干支关系；
- engine、RuleProfile、规则包、tzdb 与结果摘要锁定；
- 精确匹配历史执行器时的只读复演和失败关闭。

### 4.2 案例、修订、事件与运限

- Case 与不可变 Revision；历史修订不覆盖，只能派生新版本；
- 案例与 CandidateSet 的标签、收藏、回收站、恢复和删除边界；
- 大运、小运、流年、流月、流日、流时六轨运限；
- 粒度、筛选、选中节点和 URL 前进/后退恢复；

- DST gap 拒绝、overlap earlier/later 显式选择；
- Event 与运限节点的双向定位及追加式迁移回执。

### 4.3 专业研究、对照和知识

- `/cases/research`：严格 ResearchQuery、SavedView、执行摘要和来源诊断；
- `/compare`：2～4 个精确 Revision 的正式字段对照和同步运限；

- 研究笔记、结构化引用、研究者资料和本地应用设置。

### 4.4 导入、导出、备份和本地安全

- CSV 字段映射、预检、错误行、重复策略和未知时辰导入；
- 分块读取、严格 UTF-8、取消/重试和数据量限制；
- 单盘 Markdown、CSV、PNG、打印/PDF 链路；

- 默认本地保存、无账号、无出生资料上传；
- `/settings/data` 数据管理和 `/help` 安全边界说明。

### 4.5 Web/PWA 与响应式界面

- React + Vite 响应式应用壳；
- 桌面侧栏、手机顶栏和五项底部导航；

## 5. 当前工程架构

项目是 npm workspaces 单仓库，版本标记为 `0.2.0-p0`。

| 层 | 主要目录 | 职责 |
| --- | --- | --- |
| 应用层 | `apps/web` | React/Vite Web/PWA、页面、Service Worker、发布协调器和浏览器门 |
| 契约与完整性 | `contracts`、`integrity`、`chart-integrity` | 版本化数据契约、规范摘要、命盘完整性 |
| 时间与排盘 | `time-core`、`tzdb-core`、`bazi-core` | 时间归一化、固定时区工件、确定性排盘适配 |
| 规则与运限 | `rule-profiles`、`rule-packs`、`relations-core`、`luck-core`、`transit-core` | 规则快照、声明式规则包、关系、起运和六轨运限 |

确定性核心尽量不依赖 DOM；文件、分享和保存已经通过平台接口隔离，为 Android 后续封装保留了边界。

## 6. 发布代际的真实状态

### 6.1 默认发布

- 当前普通 `npm run build` 仍输出 `legacy-v13`，目标 Schema 为 13；
- `dist/web` 是默认发布目录；
- 不允许因为 storage 包最大支持 16，就把当前 Web 版本误报成 v16。

### 6.2 Schema 15

- v15 是非默认候选，增加 Revision 下游计算收据；
- v14→v15 和 v13→v15 已有隔离迁移工程证据；
- 它没有被正式提升为默认发布代际。

### 6.3 Schema 16

- v16 增加内部 `mutationState`，不进入用户 full backup；
- 每个业务 `readwrite` 事务原子推进一次 epoch；
- 全量审计读取 payload、birth fingerprint 关系和 epoch 的一致快照；
- 审计后只有在 epoch 未变化时才能 CAS 标记 clean；
- generation、schema、build、完整备份协议和 verifier 身份必须全部匹配，才允许 `cache_hit`；
- 当前只维护 v13→v16 直升候选，不能同时长期维护多条公开 pairwise 路线。

正确结论是：

> Schema 16 已完成固定 Edge、数据未变化、第二次 clean boot 的安全快速启动子门；默认仍为 v13，v13→v16 自然升级和正式发布尚未完成。

## 9. 最高风险与未关闭事项

### 9.1 v13→v16 多标签自然升级竞态

在 10,000 条数据的慢审计期间，一个已经完成 `BOOT_OK` 的旧 v13 标签页可能先促进 v16 worker；另一个仍在审计、尚未完成 `BOOT_OK` 的 v13 页面随后向新 worker 发送旧代回执，被拒绝并进入 fail-closed。

目前没有观察到数据损坏，但自然升级体验门仍为红灯。专用 clean-start 容量门绕开该竞态，只证明 clean cache 子门，不能替代正式升级门。

### 9.2 性能结论不能扩大

- 默认 v13 真正可交互仍约 17 秒；
- v16 首次迁移与全审计约 43 秒；
- 只有未变化 v16 的第二次 clean boot 达到 5 秒内；
- CandidateSet-heavy、长备注、复杂 ResearchQuery、真正取消、内存峰值、long task、存储报告和固定中端 Android 仍未验证。

### 9.3 专业真值和规则签字

- 360 个金标：60 candidate、0 verified、剩余 300；
- 20,000 随机差分能证明工程一致性，不能替代命理正确性；
- .NET 差分仍有 7 条未解决的一日差异和 161 条范围外输入；
- 传统子平内置工作配置尚未完成顾问签字；
- 小运、历史执行器和更多流派仍有明确边界。

### 9.4 内容与权利

用户本地知识库和引用能力已实现，但合法随包典籍正文仍为 0。任何古籍整理、现代注解、竞品知识库、图片、字体和案例数据都必须有来源与权利证据。

### 9.5 仓库可追溯性

当前 `master` 没有任何提交，工作区的项目文件全部处于 untracked 状态。它们仍是用户数据，不能清理、覆盖或直接整仓提交。后续应在核对范围、生成物和敏感文件后，单独建立受控初始基线。

### 9.6 文档口径漂移

README、旧进展文档和验收矩阵中仍有“mutation epoch/CAS 尚未实现”或只写 v15 为最新候选的旧表述。后续必须统一为：v16 Edge clean 子门已通过，但 P2-05 总门与默认升级仍未通过。

## 10. GitHub 开源复用结论

当前没有适合整站原样搬运并直接作为 Web v1 基座的 GitHub 项目。可复用策略是“窄依赖 + 自有适配层 + 自有金标和发布门”：

- `lunar-typescript`：固定版本，放在自有 `time-core` / `bazi-core` 之后使用；
- `fflate`：只用于 ZIP 编解码，备份结构、摘要、安全检查和迁移由项目自己控制；
- `saju`、`tianji` 等：只作为诊断与差分候选，不能当独立真值；
- 移动 UI 库：可以评估通用组件，但主题、命盘结构和品牌表达必须原创；
- 无明确 LICENSE、GPL 与当前分发策略不兼容、来源不明或夹带高风险预测内容的仓库不得搬运。

任何外部代码进入项目之前，都必须锁定 commit、核对许可证和资产权利、记录来源和修改、运行安全/契约/浏览器回归，并保留版权声明。能看到或能 fork 不等于有权商用。
