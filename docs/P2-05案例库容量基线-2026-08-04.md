# P2-05 案例库容量基线（2026-08-04）

> 状态：**部分完成**  
> 环境：固定 Microsoft Edge 工作站  
> 自动门：`npm run test:e2e:capacity`；隔离 Schema 16 clean-start 门：`npm run test:e2e:schema-v16-clean-start-capacity`

## 1. 本轮结论

当前 Web 案例库已经在一份精确的 10,000 Case 数据集上完成首个真实浏览器容量基线：列表使用每页 50 条的稳定 keyset 分页，显示精确总数，并可完成生命周期、收藏、关键词检索和单案例打开。实现复用了现有 `updatedAt`、`deletedAt` 索引，**没有提升 Dexie Schema**。

这关闭的是固定 Edge 工作站上的首个 10,000 正式案例工程子门，不等于 P2-05 全部通过。当前数据集中没有 CandidateSet，也没有覆盖超长备注、专业 ResearchQuery、固定中端 Android、内存峰值或主线程长任务。

## 3. 已建立的容量机制

- 案例库每页最多返回并挂载 50 条记录，使用 `updatedAt DESC → id ASC → kind` 的稳定游标顺序；同一时间戳边界会完整处理 tie group，静态数据集翻页不重复、不遗漏。
- 非收藏路径利用现有 `updatedAt` 索引取有界页候选；精确总数由同一只读事务中的表计数与 `deletedAt` 索引计数得到。
- `kind=all` 时 Case 与 CandidateSet 各自取得有界候选后再稳定归并；返回页之外的 CandidateSet 不做昂贵的完整摘要复核。
- 收藏筛选因当前没有 `favorite` 索引，仍保留全表扫描但只持有有界结果；本轮 104 个活跃收藏已通过 10,000 Case 门。
- 关键词搜索返回有界页、精确总数和稳定下一页游标；旧列表与旧搜索 API 保持兼容。
- 分页与检索优化本身没有数据库迁移或 Schema bump；默认 `legacy-v13`、历史 v14/v15 候选和隔离 v13→v16 候选的发布身份均不因此改变。

## 4. 固定 Edge 工作站观测

| 指标 | 最终门禁 | 当前观测口径 |
| --- | ---: | --- |
| 案例库内容渲染完成 | 2.443 s | 同一固定 Edge 工作站的已留存观测范围约为 **0.55–2.45 s**；此时内容仍位于 `inert` 容器，不能称为可交互 |
| 常用关键词检索 | 0.481 s | 10,000 Case 数据集，结果仍按 50 条分页 |
| 稀有命中后打开案例 | 0.395 s | 从单一稀有命中进入案例页 |
| 页面真正解除 `inert` 并可交互 | 16.671 s | 与全库、备份级完整性启动审计完成基本同一时刻；**未达到 5 s 目标** |

口径纠正：`2.443 s` 只证明表格已经渲染，不能证明用户可以操作。默认 v13 的 `RootApp` 在启动审计完成前会给整个页面内容设置 `inert` 与 `aria-hidden`；因此该轮真正的交互就绪时间是 `16.671 s`。此前把它描述成“后台审计、不阻塞页面”是不准确的。Schema 16 隔离候选现已用原子 mutation epoch / clean-cache 协议把未变化数据库的第二次启动收敛到 5 秒内，但普通构建仍是 v13，不能凭同一 build、旧摘要或候选子门提前发送 `BOOT_OK`。

这些数字是固定 Edge 工作站观测，不是跨设备 SLA。此前旧 UI 会物化完整结果集合的风险只做过代码结构推断，**没有实际执行并留存旧 UI 红灯日志**，因此本记录不提供虚构的变更前性能对比。

### Schema 16 隔离 clean-start 双浏览器复测

物理 v13 的 10,000 Case + 10,000 Revision + 10,000 fingerprint 通过生产 shadow protocol 直升 v16；测试数据只在物理 v13 通过受限 helper 写入，未用绕过 mutation epoch 的 raw IndexedDB 写入伪造 v16 数据。

| 指标 | Edge 实测 | Chrome 实测 |
| --- | ---: | ---: |
| 首次 v13→v16 migration + `full_audit` 实际交互就绪 | **37.692 s** | **35.498 s** |
| 首次 materialize 后 mutation state | `epoch = verifiedEpoch = 1` | `epoch = verifiedEpoch = 1` |
| 第二次未变化 clean 启动实际交互就绪 | **1.072 s** | **1.066 s** |
| 第二次完整性判定 | `cache_hit` | `cache_hit` |

两浏览器第二次 clean 启动均达到 5 秒目标；精确总数、收藏、回收站、稀有检索、打开行为和 Case → latestRevision → fingerprint 关系保持。该结果关闭隔离候选的 **clean 数据安全快速启动子门**，不改变默认 v13 的阻塞全审计口径，也不把 v16 提升为默认版本。

### 多标签自然升级已收敛

独立 v13→v16 门现已稳定覆盖“双旧 v13 页，其中一页已 `BOOT_OK`，另一页仍在 10k 慢审计，新 v16 worker 接管”的原始失败条件。修复后，新 worker 不接受旧代回执来确认 v16，而是向尚未绑定目标代的合法旧页返回代际收敛信号；旧页保持 `inert` 和写锁，自动 reload 后只绑定已提交 v16，再完成自己的 `BOOT_OK`/ACK。

`test:e2e:cross-schema-v13-v16` 在 Edge 通过 **12/12（约 4.2 分钟）**、Chrome 通过 **12/12（约 6.6 分钟）**。除慢审计竞态外，完整矩阵还覆盖全新首装、富数据与 dirty→clean、多个旧页写锁、容量不足、目标启动/完整性审计失败、Dexie 事务中止、`BOOT_OK` 中断、陈旧 target、CAS 竞争，以及同 ID 终态隔离与新 ID 长期重发。失败路径保持 v13 源不变，不生成可写半代。

`test:e2e:web-v1-flow:v13-to-v16` 又在 Edge 与 Chrome 各通过 1/1、共 **2/2（约 2.5 分钟）**，覆盖十六个用户分区全部非空、断网报告、全量清空、全新 context 恢复和稳定二次导出。这里的工程复现、查询命中与哈希一致不增加命理金标或专家验证计数。

## 6. 尚未闭环

P2-05 继续标记为 **部分完成**。隔离 v16 候选的 Edge/Chrome clean 5 秒子门、自然升级矩阵和 2026-08-11 的 Edge 浏览器重数据集门已经通过，但发布签字前至少还需要：

1. CandidateSet-heavy 数据集：存储层精确保存、分页与快照 60 组，Edge + Chrome 真实浏览器恢复门均已通过（60 候选组经生产恢复路径进入 v13 并完成查询）；仍缺更大候选盘规模；
2. 超长案例备注、研究笔记和多关键词文本负载：存储层已验证 40 条 6000+ 字符长备注，Edge + Chrome 浏览器已覆盖单关键词与多关键词（AND）双跑摘要稳定及负向 0 命中；多关键词在不同 scope 的组合负载仍未单独建门；
3. 严格专业 ResearchQuery 的组合条件与结果摘要容量门：存储层已验证 `ADVANCED_CASE_QUERY` 真值表与摘要稳定，Edge + Chrome 浏览器已覆盖文本与组合条件（月令/干支关系/规则快照/运限/事件绑定）双跑摘要稳定，并新增正向命中门（真实构造案例经生产恢复后在两浏览器均精确命中 1 且摘要稳定）；跨 scope 组合负载仍未单独建门；
4. 统一取消：专业 ResearchQuery、完整备份 ZIP/JSON 生成、CSV 导入、知识导入、恢复均已可取消；2026-08-11 新增统一取消契约单测、10,000 条真实浏览器导出取消门（Edge + Chrome，无下载、无写入、计数不变）与 5,000 行 CSV 真实浏览器预检取消门（Edge + Chrome，零写入）；知识导入是单文档流程，Worker 中止由契约单测覆盖；
5. 浏览器内存峰值、主线程 long task、存储占用与连续深翻报告：Edge + Chrome 深翻探针与重数据集门已记录存储/堆/long task 探针；仍缺多轮峰值对比与冻结预算；
6. 固定中端 Android Chrome/WebView 的同构 10,000 Case、clean/dirty epoch、CAS 与恢复验收（方案与证据模板见 [P2-05 固定 Android 验收门](./P2-05固定Android验收门-2026-08-10.md)，当前未开始，等待固定设备）。
