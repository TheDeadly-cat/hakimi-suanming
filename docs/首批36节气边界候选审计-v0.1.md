## 3. 证据状态门槛

| 状态 | 含义 | 能否计入金标 |
| --- | --- | --- |
| `candidate` | 当前引擎冻结快照或单一来源线索 | 否 |
| `cross_checked` | 至少两个真正独立实现得到一致线索 | 否；仍可能共同采用错误表或不同流派 |
| `verified` | 有权威来源、复核人、复核时间和可追踪裁决记录 | 是 |

Schema 会拒绝缺少上述字段却声明为 `verified` 的条目。商业 App 截图只用于发现差异，不作为权威来源。

## 4. 人工复核流程

1. 为每个交节时刻登记权威历书/天文资料的版本、页码或稳定链接，并明确使用时标。
2. 把权威时刻统一转换为 UTC 和固定 `+08:00`，记录转换过程，不直接抄墙上时间。
3. 分别核对前一秒、当刻、后一秒的年柱、月柱、日柱、时柱。
4. 对“当刻是否归入新月柱”及大雪 23 点后的日柱口径形成顾问书面裁决。
5. 两人复核输入、期望值与引用；生成不可变裁决记录后，才把对应执行行升级为 `verified`。
6. 任一期望值变化都新增数据集版本，不覆盖旧签字记录。

工程已提供严格的双人裁决记录预检：每条记录绑定候选摘要和规则摘要，要求两个不同复核身份、权威来源定位、决定与理由；篡改、跨候选套用和“接受同时改值”都会被拒绝。这里的 SHA-256 是内容完整性摘要，不是身份签名。网页预检通过后仍不会增加金标计数，维护者必须线下核验身份与来源，并把裁决纳入版本化 fixture。

建议裁决记录至少包含：

```text
case_id:
authority_source_ref:
authority_time_scale:
expected_four_pillars:
rule_profile_id_and_digest:
reviewer:
second_reviewer:
reviewed_at:
decision:
reason:
```

## 5. 本批次没有覆盖

- 其他年份、历史时区与 DST；
- 农历/闰月输入与往返；
- 23:00/00:00/早晚子时全部换日组合；
- 真太阳时改变时辰或日期；
- 未知时辰候选持久化；
- 顺逆、起运与大运交接；
- 干支关系表、神煞与解释规则；
- 多 IANA 时区、DST、日期线和完整四柱的外部差分；固定 `UTC+08:00` 的 20,000 例内部确定性与公农历字段差分已另行完成，不能外推到本批节气真值。

因此本批次完成后仍只是 360 例总计划中的“界月规则”一类，不能代表排盘模块 v1 完成。
