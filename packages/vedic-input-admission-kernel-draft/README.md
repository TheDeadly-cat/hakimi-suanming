# Vedic input admission kernel draft

This private package is an isolated, dependency-free engineering draft. Its package exports are empty and production import is forbidden.

It is listed only in the downstream isolated-draft registry. The upstream registry raw-bound by the readiness candidate remains unchanged, so this package cannot backlink into or silently re-sign its own readiness digest.

It implements one non-rejection candidate transition only:

`uninstantiated --freeze_packet--> packet_frozen_receipts_incomplete`

The input is a canonical UTF-8 governance-policy packet. The parser checks the byte limit before allocation, takes a species-free snapshot, and rejects SharedArrayBuffer-backed or extra-own-property byte views. It also fails closed on a BOM, malformed UTF-8, duplicate keys (including escaped-key aliases), unknown or missing fields, noncanonical JSON, oversized bytes, unsafe objects, non-`Uint8Array` views, cross-system/v13 identity, exact-set drift, and digest drift. The packet fixes the current upstream readiness and transition-contract digests, the exact 13 requirement IDs, 26 invariant IDs, 8 condition IDs, and the exact ten review-content digest fields. Only those ten allowlisted governance digest field names are accepted; personal fields, explicitly person-derived digest fields, arbitrary references, and free text are outside the schema. This structural allowlist cannot verify the semantic origin or source provenance of an opaque digest, and the packet fixes both `digestSemanticOriginVerified` and `privacySourceProvenanceEstablished` to `false`.

The sole non-rejection result is named `draft_transition_candidate`. It proposes deterministic next state, chain, and consumed-nonce heads with `afterEpoch = beforeEpoch + 1`, but it is not a persisted success receipt: `acceptedReceipt`, `commitObserved`, and `mutationEpochRuntimeEstablished` are all `false`, `authorityEffect` is `none`, and every truth, authority, release, deployment, and public-release flag remains false.

`seal_pre_snapshot_evidence_manifest` is now a recognized, executable fail-closed path, not a positive transition. With the correct from-state and no replay or epoch-overflow marker it returns `PRE_SNAPSHOT_MANIFEST_SEAL_BLOCKED` with the exact four upstream guards. A positive candidate is forbidden in this version because the legal-authority-disposition receipt cardinality is still `required_undefined`, none of the eleven success receipt families has an executable accepted-receipt schema or verified instance, and no runtime revocation-head recheck exists.

The separate `inspectVedicPreSnapshotEvidenceManifestCandidate` API parses a closed, local diagnostic projection and computes a domain-separated candidate digest. It can report projected packet identity, known fixed cardinalities, duplicate IDs, output or unknown kinds, lifecycle-reference emptiness, and revocation-head equality. It always fixes `candidateManifestClosed=false`, `legalAuthorityDispositionCardinalityDefined=false`, `runtimeRevocationRecheckEstablished=false`, and all authority flags to false. The transition request deliberately remains the original exact three fields and never accepts this projection as payload, so a caller-supplied projection cannot enter transition or rejection identity. The local `vedic-receipt/<hex>` pattern and 512-reference limit are diagnostic choices, not upstream normative requirements.

The three still-unimplemented positive transitions, a wrong from-state, a replay/idempotency marker, or epoch overflow return a deterministic `transition_rejection_receipt`. Draft schema revision 2 binds the admission cycle plus packet schema, ID, digest domain, packet digest, and packet-manifest digest in addition to the ledger generation, operation ID, idempotency key, and generation-scoped nonce. A rejection keeps state, epoch, state digest, chain head, revocation head, and consumed-nonce head exactly unchanged; it does not consume a nonce and has no `targetReceiptId`. This pure response does not establish that any ledger persisted the rejection or that a mutation-epoch runtime exists.

The rejection object is an isolated kernel failure-response schema, not a complete executable instance of the upstream `transition_rejection_receipt` envelope. It still lacks the full upstream common envelope, protected reason context, issuer/signature/trust-anchor material, persistence, and runtime proof. Its `receiptDigest` is only the deterministic digest of this closed draft response. Its JSON Schema `$id` is independently versioned as `0.1-draft.2`; the retained `v0.1.0.schema.json` workspace filename is only a local compatibility path and is not a public or stable schema locator.

This package does not establish a Vedic input contract, a sealed pre-snapshot manifest, accepted receipt instances, personal-input handling, an owner or signer, a digital signature, expert or content truth, rights/legal conclusions, a runtime ledger, formal admission, release evidence, deployment, or public authorization. `productSystemId=vedic-astrology` is only the research-system label; `independentProductId`, `targetSchema`, `migrationId`, and `releaseIdentity` remain `null`. It does not inherit Bazi `legacy-v13`, target schema, migration, release, or storage identities.
